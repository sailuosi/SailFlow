11 月 3 日发了第一篇介绍，意外收获了大量阅读。那段时间写的是「为什么要做 SailFlow、架构赌注押在哪」——`UseXxx`、pure/ext/biz、待办人双时刻、Gate/Hook/Notifier。

## 从「能讲清楚」到「能接上宿主」

第一篇里的架构，本质是一套**边界承诺**：

- 引擎只管流转语义与插槽；鉴权、菜单、办理台留给宿主；
- 一项能力一个 `UseXxx`，不引用就不拖重依赖；
- 选人、事件、通知分线，禁止 if-else 堆内核。

骨架要「立住」，光有分层图不够。真正过关的标志是：宿主能用同一套语言把产品缺口**接上**，而不是每次需求都回到 Mediator 里加分支。

这段时间最扎实的一块，就是把产品侧一批高频缺口接到了引擎契约上（接线已归档，联调仍在进行）：

| 块 | 落地要点 |
|----|----------|
| 空人 / 同人 / 超时 | Host EmptyAction / Filter + 超时 Job；空人默认拒绝推进（明确 ReasonCode，不静默改人） |
| 转办 | `TransferProcess`：本节点交人、不发生节点流转（≠ 委派） |
| 退回两维 | 目标维 × 再发送维正交落盘（`sendBackTarget` × `resubmitMode`） |
| 字段权限 | `editable` / `readonly` / `hidden` / `masked` 四码统一 |
| 表单生命周期 | `ISailFormBizHandler` + 同意/退回/终态回调 |
| 办理条分发 | 统一 `ButtonsOperation` Dispatcher，动词进码表、进 Handler |

同时刻意**暂缓**了一批「引擎有 API、产品未要」的项：Cancel / Suspend、委派、承办认领按钮等。骨架阶段宁可少承诺，也不空壳上码表。

第一篇讲的是「中国式 OA 不硬套 Flowable」；这一轮做的是：把那套说法**接到办理条和宿主管道上**。

## 对象寿命：A / B / C / H，治的是「对象乱复用」

OA 引擎里还有一类隐性坑：Manager、Mediator、Runner、Context 谁能共享、谁必须用完就扔，说不清就会出现「第二次请求脏状态」「单例里扣着本次用户」这类玄学 bug。

为此把对象寿命收成四档：

| 档 | 一句话 |
|----|--------|
| **A · 应用级** | 同寿于一个 `SailClient`：方言、注册表、工厂、Gate/Hook |
| **B · 请求/命令级** | 入参袋 / 编排袋（Runtime、Mediator）：用毕即弃或 Clear |
| **C · 纯工具** | 无策略纯变换，可并发 |
| **H · 壳** | `WorkflowService` 薄转发，不扣请求态 |

口诀很简单：**长寿不能持短寿可变态；变化进 Context，别塞进 Client。**  
`WorkflowService` 不再扣 `_wfAppRunner` 一类字段——壳只转发，命令态跟请求走。

这不是炫技命名，是给后续插件作者和宿主接入定的**红线**：扩展挂在 A 槽，命令态走 B 袋，别再发明第三套生命周期。

## 下一跳也做成管道：Prepare + 求值 + Filter

第一篇重点写了「谁来办」（Assignee）。现实里另一半坑是「下一步走哪」。

结构演算可以产出多个候选节点，前端再选；业务又要：

- 演算前补条件袋（金额、部门码……）；
- 条件表达式可换求值引擎；
- 演算后按权限裁剪 / 标注候选。

于是定型了 **下一跳节点计算管道** `UseNextStepRoute`（S0–S2 已落地）：

```text
IfCondition* / Prepare  →  写条件袋
IConditionEvaluator     →  求值（默认可 ≡ ExpressionParser；可替换）
INextStepFilter         →  裁剪/标注候选
```

几条硬约束值得单独拎出来：

- **预览 ≡ 发送同源**，禁止「界面有、发送无」两套逻辑；
- 改「走哪几个节点」≠ 改「谁来办」≠ Gate 合规拒绝——三线分离；
- And 并行支路禁止静默删；收成 0 个候选要可诊断，不得偷偷挑一条。

和待办人管道一样：奇葩需求往管道上挂，**不改结构内核 / Mediator**。

## 业务字段与发号：标题 ≠ 流程名，Id 可替换

嵌入业务系统时，还有两件「看起来小、接多了必炸」的事。

**1）流程名称 ≠ 流程标题**

历史上实例上的 `ProcessName` 常被当成列表标题；业务主键、通道、表单码又挤在 `AppInstanceId` / `AppName` 一类字段里，跨宿主对不齐。

现已收口（NuGet **0.1.2**，含迁移）：

- `ProcessName`：定义名快照，只表示流程名称；
- `Title`：实例对外标题（待办、列表、门户）；
- `BizPK` / `BizType` / `BizCode` / `BizChannel` / `BizName`：业务标识组；
- 创建 Hook：实例拼装后、落库前，业务可改标题与 `biz*`；启动可注入 `BizDataDto`。

**2）主键发号契约化**

行主键、流程设计键 `ProcessId`、BPMN `process@id` 形态，拆成可替换契约：`ISailIdSource` + `ISailBpmnIdCodec`。默认 Guid 字符串；宿主可覆盖（Guid7 / Yitter / 流水等），禁止再散落 `new Guid` 与静态 Helper。

嵌入系统时，「业务单据怎么挂到实例上」「Id 策略跟不跟宿主一致」，终于有了正典入口。

## 宿主侧：能力包语言开始统一

引擎再干净，宿主 `Program` 里若仍是大段 `if (enabled) addHook…`，骨架也会被组合根拖垮。

约定已经写进最佳实践：

**一项可开关能力 = 一个 `UseXxx`；启用判定、建表、注册、Drain 内聚进扩展。**

真实宿主（如 api8 / sleveen-admin）已按清单挂载：`UseBizAssignees`、`UseFormBizLifecycleHook`、`UseBizMirrorHook`、`UseNodePolicyTimeoutStamp`、门户待办 Notifier 等。有实现未挂的也会明示——**组合根可读、可审计**，而不是「不知道线上到底开了啥」。

异步方面也清掉了假 `Task.Run` 冒充 `*Async` 的坑：令牌可传、重 IO 再 await；换线程留给宿主外层。Outbox 可靠旁路与 IO 异步是两维，不再混称「异步」。

## 现在处于哪一阶段？

用成熟度语言说更清楚：

| 层 | 状态 |
|----|------|
| 分层与 `UseXxx` 语言 | **骨架稳定** |
| 办理动词 / 待办人 / 事件三线 | **可用，持续打磨** |
| 产品缺口接线（转办、退回两维、字段四码、表单生命周期……） | **已接线，联调验证中** |
| 下一跳管道 / 寿命规范 / 业务字段与发号 | **首包落地，跟宿主对齐中** |
| Cancel/Suspend、委派、真并行会签深债等 | **暂缓或仍有债** |

所以标题才是：**骨架已立，进入打磨验证**——不是宣布生产就绪，而是宣布「扩展点与主路径已经够接宿主；接下来用联调与真实场景把棱角磨掉」。

适合继续关注的同学：

- 要把引擎嵌进自有 .NET 后台，而不是买一套成品 OA；
- 愿意跟破坏性变更，一起把中国式办理场景打磨实；
- 关心扩展点是否干净：敢不敢不改内核、只挂管道就接新需求。

仍不适合：零代码开箱即用、无法接受迭代期 break change、直接上生产。

## 写在最后

第一篇的赌注是：**稀缺的不是功能清单，是干净的扩展点。**

这一轮没有推翻那个赌注，而是把它钉进了更多具体面上——

- 产品动词接到码表与 Dispatcher；
- 选人之后，下一跳也管道化；
- 对象寿命有档位，业务字段与发号有契约；
- 宿主能力包与引擎同一套 `UseXxx` 语言。

骨架立住之后，最有价值的反馈不再是「再加一个按钮名」，而是：

> 我这种奇葩选人 / 下一跳 / 退回返送，能不能只挂扩展、不动 pure？
