**把中国式 OA 办理台上常见的那一排按钮，收成引擎里可复用的动词；并在宿主上做了第一轮真人点验。**

一句话进度：

| 面 | 状态 |
|----|------|
| 日常办理动词（通过 / 驳回 / 退回 / 加签三型 / 转办 / 沟通 / 抄送 / 撤回 / 返送…） | **引擎 + 办理条基本齐** |
| 改签族补齐（减签、加人、委派等） | **引擎齐；部分码表默认关，节点可开** |
| 管理向（跳转 / 关闭 / 终止 / 作废…） | **引擎齐；部分默认关或暂缓产品按钮** |
| 真人初测（简单直线流转） | **通过、加签三型、转办、沟通、驳回、退回、返送等 ✅** |
| 网关叠用、加签递归、减签/改派等边界 | **仍在清单上** |

不是宣布「OA 做完了」，而是宣布：**动词面已经够用、够对照；简单流转初测已通（含并加签、转办）；剩下是复杂叠用与系统债。**

## 这两周在补什么缺口

11 月 14 日先做了一份相对常见 OA 引擎的**能力对照审计**：哪些已经对齐、哪些是「引擎有、产品未挂」、哪些是 Sail 刻意不跟（比如承办认领按钮）。

随后几天，按那张对照表把缺口往引擎里收：

- **沟通**进核心动词（参与者 + 等待硬锁），不再跟加签/抄送糊成一团；
- **委派 / 减签 / 改派 / 催办 / 加人**在引擎侧落齐；
- **前 / 后 / 并加签**按「席位临时子规则」重落语义，并在宿主上点验；
- 办理动词做成**产品解说表**，按钮文案与引擎命令能对上号。

系统侧（统一动作骨架、同事务信封、钩子自锁治理）同期落地，技术圈写法见 [解说-动作骨架与同事务.md](./解说-动作骨架与同事务.md)。本文只回答：**办理人在台上能点什么、点了会发生什么。**

## 初测过了什么（诚实版）

宿主 `sleveen-admin`，范围默认是**简单直线用户任务**（无分支、无网关）。2026-11-21 起归档的真人点验：

| 场景 | 结果 |
|------|------|
| 通过 / 同意 | ✅ |
| 前加签、后加签、加签后发送出节点 | ✅ |
| **并加签**（双方都过才出节点；中间席不出节点） | ✅ |
| **转办**（同节点交人、不还回） | ✅ |
| 沟通发送、被沟通人阅办发送 | ✅ |
| 驳回 | ✅ |
| 退回上一节点、返送退回人 | ✅ |
| 减签 / 改派 / 加签递归、网关叠用等 | ⬜ 另轮 |

所以对外口径建议写成：**简单流转下日常办理主路径（含加签三型、转办）初测正常。**  
复杂叠用（或签节点上加签、网关上退回等）刻意放到下一轮，不拿「简单流转绿了」冒充「全场景绿了」。

## 关键办理动词在干什么

下面不讲类名与调用链，只讲**业务上一句话 + 它解决什么混淆**。更细的场景解说见仓库 `doc/helps/解说-办理动词.md`。

### 主路径：把单子往前推 / 打回去

| 动词 | 一句话 | 解决什么问题 |
|------|--------|--------------|
| **通过** | 我同意，按图继续往下走 | 与「会签还要等别人」并存：过的是**我这票**，出不出节点看办理模式 |
| **驳回** | 我不同意，按驳回路径处理 | 不等于整单作废；也不等于「退回让他改」 |
| **退回** | 打回，让他改完再来 | 目标 × 再发送两维正交；改完怎么回来，靠返送/重发规则，不靠口头约定 |
| **返送 / 重发** | 改完了，按规则再送出去 | 常见「退回后回到退回人」有独立语义，不跟普通通过糊在一起 |
| **撤回** | 我刚批的，收回来 | 已办侧纠错；和退回（待办侧打回）不是同一按钮 |

### 临时改「谁来审」：加签 / 加人 / 减签

口语里的「加签」在 Sail 里拆清楚了：

| 动词 | 一句话 | 解决什么问题 |
|------|--------|--------------|
| **前加签** | 我先不审，让他先审 | 临时插入审批顺序，不改流程图 |
| **后加签** | 我先批完，再让他补一刀 | 本人办结后不直接出节点，先走加签人 |
| **并加签** | 拉他进来跟我一起审 | 临时并行；**不是**节点上预先配好的会签 |
| **普通加人** | 扁节点上追加一个普通办理人 | 跟节点 Leave 走；**≠ 并加签、≠ 加批生新段** |
| **减签** | 这个人不用审了，拿掉 | 多人节点拿掉未办完的人；至少留一人 |

加签三子型解决的是「办理中临时插人」；普通加人解决的是「当前节点名单少一个人」。两者都**不是**改未来节点预选——未来节点换人走预选表，不另造一堆 `*FutureAssignee` 按钮。

### 交人：转办 ≠ 委派 ≠ 改派

| 动词 | 一句话 | 解决什么问题 |
|------|--------|--------------|
| **转办** | 这事交给他，我不办了 | 本节点交人、**不还回**；最容易和委派搞混的那个 |
| **委派** | 请他代办，办完还得还给我 | 办结**自动回转**原人；否则请用转办 |
| **变更处理人 / 改派** | 管理员把当前节点换成这批人 | 管理态差量换全集；不是办理人自己转一手 |

选型口诀：**不还回 → 转办；要还回 → 委派；管理换名单 → 改派。**

### 知情 / 问询：抄送 ≠ 沟通

| 动词 | 一句话 | 解决什么问题 |
|------|--------|--------------|
| **抄送** | 让他知道一下，不用他审 | 知情通道；不进审批票数 |
| **沟通** | 问他点事，他回我就行 | 参与者**无审批权**；发起后源待办硬锁，避免「问着人、自己又点通过」把单子推走 |

沟通解决的是「临时征询」；抄送解决的是「知会」。两者都不要拿加签冒充。

### 管理向收口（摘要）

| 动词 | 一句话 | 备注 |
|------|--------|------|
| **跳转** | 别管图了，直接跳到那里 | 管理纠偏 |
| **关闭** | 正常把这张单收掉 | 管理向结束 |
| **终止 / 作废** | 强掐 / 作废件 | 引擎有；码表常默认关 |
| **催办** | 提醒他还没办 | 不改状态；引擎有，产品按钮仍弱 |
| **挂起 / 恢复 / 取消** | 暂停或整单取消 | 引擎有；产品码表暂缓 |

「引擎齐」不等于「办理条默认全开」——不少管理按钮刻意默认关，节点或宿主显式打开再暴露。

## 办理模式不是按钮

会签 / 或签 / 抢办 / 顺序会签，是节点上的 **Leave（怎样才算离开本节点）**，不是办理条上的一个键。

容易踩的坑：

- **并加签** ≠ 会签节点：前者是办理时临时拉人；后者是设计时配好的多人模式；
- **通过** 在或签节点上可能一人过就走，在会签节点上只是一票；
- 加签默认**不改**节点原来的 Leave——临时规则落在「发起加签的那一席」上（细节留给系统篇）。

## 现在可以怎么用这句话对外说

适合说：

> 中国式日常办理动词（通过、驳回、退回返送、加签三型、转办、沟通、抄送、撤回等）在引擎与办理条上已经齐备；简单流转下通过 / 加签三型 / 转办 / 沟通 / 驳回 / 退回 / 返送已真人初测通过。

不适合说：

> 全场景生产就绪；网关叠用与所有边界已验绿；管理按钮全部开箱即用。

上一篇的赌注没变：**稀缺的不是按钮名清单，是扩展点干净。**  
这两周做的是：把按钮名背后的**业务语义**钉清楚，并让简单流转主路径在真人点验里跑通。
