产品篇讲「按钮齐了、初测过了」。这篇只回答三件事：

1. **新办理特性怎么加，才不会复制一整段 Gate→Hook 样板？**  
2. **一次同意 / 发起 / 退回，为什么必须落在同一 DB 事务里？越界会怎样？**

## 0. 结论先行

| 编号 | 口径 |
|------|------|
| **A1** | 共同父类 = **工具箱**；族群基类 = **固化钩子时序**；动词子类 = **只写 Core** |
| **A2** | 事务 + 实例锁 **仅** `WorkflowService.RunAction` / `CommitOnSuccess`；Action / Manager **禁止**自开 |
| **A3** | Sync Hook FailFast 参与回滚；Async = Outbox **同事务入队**、提交后 Drain |
| **A4** | 有主事务 kit 时，同库读写必须吃 `ctx.Kit` / `kit.useSQL()`；`UseRunSQL()` 碰未提交行 → 自锁 |
| **A5** | 有 kit 也打 Sync **BEGIN/END**；钩子级软超时（返回后必抛）；不做 `Thread.Abort` / AsyncLocal 禁连 |
| **A6** | `SignForward` 归 Transition；外层 Leave **不改写**；子帧 Passed → 折合一票上浮再问父 Leave |

扩展配方一句话：

```text
FlowOperation + 选对族群的 XxxAction(TryLoadContext + ExecuteCore)
  → Service 薄壳 RunAction
  → Host Handler / 码表（有命令再进办理条）
```

## 1. 动作骨架：为什么「命令管道」被吸收掉

早期有过「命令执行管道」草案：想在入口再挂一层横切。落地后发现——

- Gate / Hook / Notifier **产品语义已在能力管道**；
- 真正重复的是各族动词自己抄 `BuildGate → AfterSuccess`；
- 事务边界若散落在 Action 里，同事务契约立刻碎。

于是定型为三层，**不再并列一条 Command Pipeline**：

```text
                         FlowActionBase（工具箱）
                         │  TryGate / OnFireFlowHook / Build*Context
                         │  不排全家桶时序；无事务/锁
                         │
     ┌───────────────────┼───────────────────┐
     │                   │                   │
AssigneeActionBase  TransitionActionBase  LifecycleActionBase
 Load→Gate→Core→Hook  Load→Gate→Core→Hook  Load→Gate→Core→Hook
 （可选 TaskLifecycle） （可持 Runtime）      （PI 为主）
     │                   │                   │
 Transfer / Consult…    Run / SendBack /     Suspend / Terminate…
                        SignForward…
```

| 族 | 业态 | Context 红线 |
|----|------|--------------|
| **Assignee** | 实例仍跑、活动通常不变；改 Task / 办理人 / 沟通参与者 | **无** `WfRuntimeManager` |
| **Transition** | 活动集合或办理位置变化（含加签拓扑） | **可**持 Runtime（internal） |
| **Lifecycle** | 改 `ProcessState` | 以 PI 为主；人点 Suspend ≠ WaitToken Resume |

入口形状（代码：`WorkflowService.ProcessExecution.cs`）：

```text
XxxProcess*
  → RunAction / RunActionAsync
       → CommitOnSuccess(kit => {
            beginTransaction
            InstanceExecutionLock.Acquire(实例键)
            new XxxAction(Sail, kit, runner).Execute()
                 族群：Gate → ExecuteCore → OnFireFlowHook
         })
```

**审查清单（新动词 PR）**——写进专题里的那几条，技术评审直接用：

- 枚举 `FlowOperation` + 正确族群  
- 未手写 Gate / AfterSuccess 样板  
- 非 Transition 不塞 Runtime  
- Action 内无 `beginTransaction` / 无自抢实例锁  
- 命令级 Success Hook **只**在基类 `OnFireFlowHook` 打一次；路径内 Notifier 已覆盖则勿再抄  

`Copyto` 刻意不进三族（Host + `ICopytoNotifier`）。Assignee Resolve / Leave 与骨架**正交**——算人管道不塞进 Action 继承树。

## 2. 同事务信封：半成功不是「可补偿的默认语义」

流程引擎最贵的生产事故，往往不是「功能没有」，而是：

| 半成功形态 | 残局 |
|------------|------|
| 待办已办结，活动未推进 | 人点了同意，节点停原地 |
| 活动已推进，下一待办未生成 | 空转无人办 |
| 引擎终态，业务表未回写 | 列表仍「审批中」 |
| 引擎回滚，外部已推送 | 幽灵待办 |
| 父已写子，子另连接失败 | 父子不一致 |

Sail 的立场：**关键写路径严格同事务**；旁路副作用可以晚、可以丢、可以重试——但**不得**成为「关键路径只完成一部分」的借口。

### 2.1 决策表（压缩）

| ID | 决策 |
|----|------|
| **T1** | `CommitOnSuccess`：仅 `Status==Success` 才 `commit` |
| **T2** | 事务边界仅在 Service |
| **T3** | 同事务可写 = 引擎运转表 + 同库 Sync 业务写 + Outbox INSERT Pending |
| **T4** | Sync 异常 / 软超时 → FailFast → 不提交 |
| **T5** | Async：账本同事务入队，Drain 在提交后短事务消费 |
| **T6** | kit 传递是契约：`kit` 或 `kit.useSQL()`；禁止另开连接碰未提交行 |
| **T7** | Gate Reject ≠ 事故：应无推进副作用或干净回滚 |
| **T8** | 可观测是同事务护栏（见 §3） |
| **T9** | `OnTransactionCommitted` / `OnTransactionFailed` 在**信封外**；`Kit=null`；仅 Sync BestEffort |

### 2.2 信封内 / 外

```text
信封内                          信封外
────────                        ────────
PI / AI / Task / 变量 / 流转写   Outbox Drain → HTTP / IM
Sync Hook 同库业务回写           BestEffort 日志 / 对账 Job
Outbox / Notifier 入队行         已提交后的重试 / Dead
CreateHook 落库前改 Title 等     Tx 生命周期钩子（不可当强一致写回）
```

强一致业务状态回写：**不得**只丢进 Outbox 当唯一保障。Sync + 同库 kit 才是「跟流转同生死」的通道。

示意（非逐行抄源码）：

```csharp
kit.beginTransaction();
try {
  var result = action(kit);           // Gate → Core → Sync Hook(kit) → Enqueue Outbox
  if (result.Status == Success) {
    kit.commit();
    FireTxLifecycle(OnTransactionCommitted); // BestEffort, Kit=null
  } else {
    FireTxLifecycle(OnTransactionFailed);
  }
} catch {
  FireTxLifecycle(OnTransactionFailed);
  throw; // 连接释放 → 回滚
}
```

实例锁 `InstanceExecutionLock` 防的是**同实例并发交错写**；它**不替代**事务。锁防交错，事务防半成功。

## 3. 钩子自锁：1121 三案与「有 kit 也要超时」

### 3.1 故障指纹

2026-11-21 发起路径卡死，典型形态：

```text
Conn1 (流转 kit)                 Conn2 (UseRunSQL / 无 kit API)
  beginTransaction 成功
  INSERT PI / Task / Var…
  RunSyncHooks
       │                           SELECT/UPDATE 未提交行
       │◄──── 等待 Conn1 提交 ──────┤
       │ 等待钩子返回
       ▼
     自锁 / SQLite 5·6 / SQL Server 锁等待
```

调试表现：堆栈停在宿主 `IFlowHook.Handle`「无响应」；强制终止后库写锁残留，下次 `beginTransaction` 再挂。

收录三案（`专题-Bug治理-Sync钩子同事务自锁.md`）：

| 案 | 根因 | 修法 |
|----|------|------|
| **A** ExtraStarted 写变量 | 无 kit 的 `SaveProcessVariable` | 变量 API kit 重载；钩子走 `ctx.Kit` |
| **B** 选人/相对人 | Resolve/Filter `UseRunSQL` 读刚插 PI | `AssigneeInvokeRequest.Kit` |
| **C** 子流程 Execute | `subKit = Sail.UseRunSQL()` | `subKit = kit.useSQL()` |

### 3.2 为何以前极难排

旧调度在 `kit != null` 时直接 `Handle`，**旁路**全局 `SyncHookTimeoutMs`，又无进度日志：

```csharp
// 旧行为（已改）
if (timeoutMs <= 0 || kit != null)
    hook.Handler.Handle(ctx);   // 有 kit → 无超时、无 BEGIN/END
```

C# 无法安全打断任意同步 `Handle`（`Thread.Abort` 已不可用；有 kit 的连接也不可跨线程杀）。  
所以排障主手段不是「硬杀」，而是：

| 手段 | 口径 |
|------|------|
| **进度日志** | 每个 Sync：`开始` / `结束` / `偏慢` / `失败`（经 `SailClient.Log`） |
| **软超时** | `Handle` **返回后**看耗时；超时必抛 `FlowSyncHookTimeoutException` → FailFast |
| **钩子级 TimeoutMs** | `FlowHookBase` 默认 30s；`≤0` 不限制（仍打 BEGIN/END） |
| **kit 复用** | **建议 + 评审检查单**；本期**不做** AsyncLocal 运行时禁连 |

卡死读法：日志最后一条是某钩子的 `开始` 且没有 `结束` → 卡在该钩子（或其同步依赖）内。

### 3.3 Sync vs Async 选型（宿主自检）

| 必须读写**未提交**流程数据 | → Sync + `ctx.Kit` |
| 可延后副作用 | → AsyncOutbox（同事务入队） |
| 仅观测 | → BestEffort / 文件；**不要** Sync 堵主路径 |
| Sync 里同步长 HTTP | → 改 Outbox |

接口 XML（`IFlowHook` / `FlowHookContext.Kit` / `HookMode.Sync`）已加死锁警示；新钩子 PR 按检查单过一遍即可。

## 4. 加签运行时：席位 AI 即容器（Transition 内核）

产品篇说「前/后/并加签初测过了」。引擎侧对应的是一次语义纠偏：

**废止**：整节点升级虚拟空壳、加签改写节点 `ai_leave_*`、子帧 Passed 直接 `ContinueForward`。  

**现行**：

```text
建 AI：设计 Leave → 节点 ai_leave_*（快照，加签永不改）
SignForward：发起人自己的 AI 升级为容器 + 写子规则 Leave；加签人建子 AI
办结：TryCanLeave(容器) → Waiting 唤醒 / Passed 折合发起人一票 → TryCanLeave(父)
外层 Race 旁人过 → 递归淹没未完成加签子树
```

同级子元素分母 = **直属 Task ∪ 直属子 AI（折合席）**。  
并加签踩过的坑很典型：宿主硬编码 `count/1` → 容器阈值变成 1；`IsLastTask` 未计发起人直属 Task → 一人即出 / 「无匹配后续节点」。修法是宿主只传子型、引擎 Parallel 强制 Percentage=1、末席计入发起人打开待办——这是**契约与宿主接线**对齐问题，不是再堆一个按钮。

`SignForward` 落在 **Transition** 族（拓扑变了），`AddAssignee` 落在 **Assignee** 族（扁节点增量加人）。两者命令不同、Leave 语义不同——技术上禁止再揉成一个 `SignForwardType`。

实现锚点：`NodeMediatorSignForward*` · `LeaveSeatProjector` · `TryCanLeave`；契约见 `专题-节点实例临时子规则.md`。

## 5. 刻意不做的事（本期边界）

技术文容易写成「我们什么都做了」。反过来列边界更有用：

| 不做 | 原因 |
|------|------|
| Action 内统一排全家桶 Gate→Hook | 各族钩子模式不同；工具箱 ≠ 时序上帝类 |
| 跨库 Saga 冒充同事务 | 首期只保证引擎库关键路径 |
| Sync 期间 AsyncLocal 禁 `UseRunSQL` | 排障靠日志；正确性靠 kit 重载 + 评审 |
| `Handle` 加 `CancellationToken` | 破坏面大；软超时 + BEGIN/END 先落地 |
| 用工作线程强杀阻塞 SQL | 有 kit 时连接/事务不可跨线程 |
| 把 Copyto / 算人管道塞进动作骨架 | 正交机制，硬揉只会胖 Context |
| `UseAction<T>` 注册表替代 Service `new XxxAction` | **仍开放**；现行为显式薄壳 |

## 7. 写给要提 PR 的人

若你准备加一个办理动词：

1. 先判断业态 → 选 Assignee / Transition / Lifecycle（开新族要改专题正文）。  
2. 子类只实现装载与 Core；事务交给 `RunAction`。  
3. Sync 钩子写引擎库 → `ctx.Kit`；可延后 → Outbox。  
4. 加签类拓扑变化 → 想清楚 Leave 落在哪一帧，禁止默默改节点快照。  
5. 本地把 `Sail` 日志调到 Debug，跑一次发起/办理，确认 Sync `开始/结束` 成对出现。

产品篇的初测绿，依赖的正是这套信封没把「半成功」漏出去、钩子没把自己锁死。
