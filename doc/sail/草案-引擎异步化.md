## 0. 已决口径（写进实现前先遵守）

| # | 决议 |
|---|------|
| **A1** | **禁止**引擎内用 `Task.Run` / 线程池 offload 冒充 `*Async` API。 |
| **A2** | 真异步 = **API 传 `CancellationToken`** + **仅在数据库 / HTTP / 文件 / MQ 等等待点 `await`**；纯内存逻辑保持同步。 |
| **A3** | 若调用方只想「别堵 ASP.NET 请求线程」，在**宿主业务层**自行 `Task.Run` / 队列；**不是**引擎职责。 |
| **A4** | 已有 **`HookMode.AsyncOutbox`**（可靠旁路）与本专题的 **IO 异步（线程不阻塞等待）** 是两维，禁止混称「异步」而不加定语。 |
| **A5** | Gate **默认仍仅 Sync、短路径**；Gate 内禁止慢外部调用（或严格超时）。需要慢 IO 的校验 → 预检 API / 外置服务，不塞进 Gate。 |
| **A6** | 同步 `Start` / `Run` / … **长期保留**；`*Async` 逐步变为「同语义 + `ct` + IO await」，过渡期可内部仍调同步（但**不得**再 `Task.Run`）。 |
| **A7** | **mooSQL 暂不改**。阶段 0/1 不得为「真 await」去改 Clip/Builder 或绕道大改访问层；**阶段 2 以 mooSQL 先扩展异步 API 为前置**，引擎再接续 Manager 热点 IO-await。 |
| **A7** | **mooSQL 暂不动。** 阶段 0/1 只改引擎表面与旁路令牌，**不**为异步去改 Clip/Builder、**不**在引擎侧用「绕过 Clip 改调 Builder async」当捷径。阶段 2（Manager / 办理热路径 IO-await）**以前置：先扩展 mooSQL（Clip/`ct`）再接续引擎**。 |

## 1. 一句话

把引擎 `*Async` 从「换线程跑同步栈」改成「**可取消的 IO 异步**」：轻逻辑不动，重等待点传令牌；插件按轨区分 **Sync / AsyncOutbox /（可选）IO-async 接口**；换线程留给宿主。  
**DB 层异步能力由 mooSQL 先行扩展；引擎阶段 2 再接续，期间不动 mooSQL 仓。**

## 2. 问题：假 Async 与真正要解决的事

### 2.1 现状（反面教材）

```csharp
public async Task<WfExecutedResult> RunProcessAsync(WfAppRunner runner)
{
    return await Task.Run(() => RunProcess(runner)); // 无 ct；整段同步含 DB
}
```

同类：`StartProcessAsync`、`SendBackProcessAsync`、… 以及 Query 侧部分方法。

| 现象 | 后果 |
|------|------|
| 无 `CancellationToken` | 请求取消 / 作业停止无法中止库操作 |
| `Task.Run` 占线程池 worker | 高并发时饿死其它续体；Job 内再套一层更糟 |
| 看起来像异步引擎 | 排障误判；宿主以为「已异步化」 |
| 引擎替宿主做 offload | 职责错位；JobWorker 已在后台线程却仍 offload |

### 2.2 本专题要解决的

1. **契约诚实**：`*Async` = 可取消 + IO 边界不阻塞线程（或明确过渡语义）。  
2. **伸缩**：并发发送时少占线程，瓶颈回到连接池 / DB（与已做的模型缓存、Outbox SQL 下推正交）。  
3. **插件规则**：Gate/Hook/Notifier/Assignee 各自何时 Sync、何时 Outbox、何时 IO-await，写死红线。  
4. **分阶段**：先去假 Async + 令牌表面，再下沉 Manager/Clip 的 await，最后才是 Mediator 深链。

### 2.3 本专题不解决的

- 用 async 替代 **AsyncOutbox** 可靠性模型（崩溃补调仍靠 Outbox）。  
- 分布式事务 / Saga。  
- 把 Assignee Resolve/Leave 全改成异步（无 IO 则不必）。  
- 强制所有宿主立刻弃用同步 API。

## 3. 两个「异步」必须分开说

```text
┌─────────────────────────────────────────────────────────────┐
│ 维度 1 · 可靠旁路（产品已有）                                  │
│   HookMode.AsyncOutbox / Notifier Outbox                      │
│   主路径只入队 → 提交后 Worker 执行；可重试 / 死信             │
│   目的：不拖垮办理事务、进程崩溃可补调                         │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ 维度 2 · IO 异步（本草案）                                     │
│   CancellationToken + await DB/HTTP                            │
│   目的：等待时不占用线程；可取消                               │
│   Outbox Drain、Notifier HTTP、将来的 RunProcessAsync 都属此维 │
└─────────────────────────────────────────────────────────────┘
```

| 场景 | 应用哪一维 |
|------|------------|
| 企微推送 / 审计写外部 | **AsyncOutbox**（已拍板） |
| Drain 消费 Outbox 时调 HTTP | Outbox 语义 + **IO-async**（`NotifyAsync(ct)` 已具备形态） |
| 办理 API `RunProcessAsync` | **IO-async**（本草案）；**不要** `Task.Run` |
| 财务发送前校验 | **Gate Sync**；慢校验不要进 Gate |

文档与评审中禁止只说「改成异步」——必须说 **Outbox 异步** 或 **IO 异步**。

## 4. 目标形态（引擎主路径）

### 4.1 API（示意）

```csharp
// 长期保留
WfExecutedResult RunProcess(WfAppRunner runner);

// 目标：可取消；实现内仅在 IO 边界 await
Task<WfExecutedResult> RunProcessAsync(
    WfAppRunner runner,
    CancellationToken cancellationToken = default);
```

过渡期允许：

```csharp
public Task<WfExecutedResult> RunProcessAsync(WfAppRunner runner, CancellationToken ct = default)
{
    ct.ThrowIfCancellationRequested();
    // 过渡：仍同步实现，但禁止 Task.Run
    return Task.FromResult(RunProcess(runner));
}
```

下一阶段再把 `Run(kit)` 换成 `RunAsync(kit, ct)`，把 `query` / `doUpdate` 换成带 `ct` 的 await。

### 4.2 执行栈切分

```text
RunProcessAsync(runner, ct)
  ├─ 轻：参数校验、拼 GateContext、锁 key          （同步）
  ├─ IO：开连接 / 事务 / 查 Running / 读变量       （await + ct）
  ├─ 轻：ProcessModel 缓存命中、算下一跳、Leave    （同步）
  ├─ 轻/短：TryGate                                 （同步；A5）
  ├─ IO：Insert AI/Task/Transition、Assignee 查库   （await + ct）
  ├─ 轻：Sync Hook（短）                            （同步）
  ├─ IO：写 Outbox 行                               （await + ct）
  └─ commit                                         （await + ct）
```

**原则：** 没有 `await` 的方法不要仅为「看起来异步」而改成 `async Task`（避免状态机空开销）；有 IO 的层级才向下传 `ct`。

### 4.3 与实例锁

本机实例串行锁（`InstanceExecutionLock` / 原 Semaphore）**继续需要**。  
IO-async 不取消串行语义：同一 `AppInstanceId` 仍互斥；只是持锁期间等待 DB 时尽量不堵死线程池（锁实现需选可 async 等待的原语，见 §8 开放题）。

## 5. 插件如何异步

### 5.1 总表

| 扩展点 | 现行接口 | IO 异步策略 | Outbox | 说明 |
|--------|----------|-------------|--------|------|
| **IFlowGate** | `Validate(ctx)` 同步 | **保持 Sync** | 否 | 短校验；慢 IO 禁止（A5） |
| **IFlowHook** Sync | `Handle(ctx)` 同步 | 默认 Sync；禁止自行 `Task.Run` | 否 | 短写库可；重外部 → 改注册为 AsyncOutbox |
| **IFlowHook** AsyncOutbox | Worker 调同一 `Handle` | Worker 侧可再 IO-await | **是** | 可靠旁路主路径 |
| **ITaskNotifier** | 已是 `NotifyAsync(ctx, ct)` | **已对齐本草案** | 默认是 | Drain 必须传 `ct` |
| **IAssigneeResolver / Filter / LeaveJudge / EmptyAction** | 同步 | 默认同步；查库 Resolver 二期可加 `*Async` 可选接口 | 否 | 见 §5.3 |
| **BPMN Action/Service/Script** | 同步主路径 | 一期不动；外调应短超时或改 Outbox/Job | 视实现 | 不借异步化扩大图内慢调用 |
| **宿主 OperationHandler** | 常 `return wf.RunProcessAsync` | 改调带 `ct` 的 API；Job 内优先同步或真 async | — | 去掉套娃 `Task.Run` |

### 5.2 Gate / Hook 红线（与回调设计一致并加严）

```text
Gate.Validate
  ✅ 读业务库快照、内存规则、短 SQL
  ❌ HttpClient 无超时、长事务、Task.Run「偷偷异步」

Hook Sync.Handle
  ✅ 同事务短写
  ❌ 调企微/钉钉（应 AsyncOutbox）

Hook AsyncOutbox
  ✅ 主路径只写 Outbox；Worker 内可 await HTTP(ct)
  ❌ 假设 Worker 仍持有办理请求的同一 SQL 事务
```

**可选演进（非一期必做）：**

```csharp
// 仅当确有 Sync Hook 必须 await 短 IO 时再引入；默认不鼓励
public interface IFlowHookAsync
{
    string Name { get; }
    Task HandleAsync(FlowHookContext ctx, CancellationToken ct);
}
```

注册时与 `HookMode` 正交：Sync+IO-async 仍占办理事务，必须超时预算；多数场景继续用 AsyncOutbox。

### 5.3 Assignee 管道

| 组件 | 建议 |
|------|------|
| Pipeline 编排、Filter 改列表、Leave 计算 | 保持同步 |
| `RoleGroup` / 宿主 `deptBoss` 等查库 Resolver | 二期：可选 `ResolveAsync(ctx, ct)`；Pipeline 优先调 async 重载，无则调同步 |
| AutoApprove Job | **已有** `ProcessPendingAsync`；继续传 `ct`；内部 `RunProcess` 改为带 `ct` 的 API；**Job 内不要**再 `Task.Run` |
| PolicyBag 缓存 | 保持；与异步无关的性能项 |

R10「后置≠Resolve Type」守卫仍后议，与本专题正交。

### 5.4 Notifier / Outbox Drain（已部分到位）

- `ITaskNotifier.NotifyAsync(ctx, ct)`：**形态正确**，实现方必须尊重 `ct`。  
- `HookOutboxWorker.ProcessPendingAsync(..., ct)` / `Dispatch*Async`：继续作为 **IO 异步样板**。  
- DrainLoop 里的 `Task.Run(RunAsync)` 仅用于**启动后台循环**，不等于办理 API 假 Async；文档中单独说明，避免误杀。

### 5.5 插件作者检查清单

1. 我要的是「办理返回后再推送」→ **AsyncOutbox / Notifier**，不是把 Gate 改成 async。  
2. 我要的是「可取消的 DB/HTTP」→ 实现里 `await` + `ct`，不要 `Task.Run`。  
3. 我只是怕堵 HTTP 线程→ 在**宿主** Controller/Application 层 offload，或等引擎真 IO-async。  
4. Sync 路径禁止隐藏线程；超时用 `CancellationTokenSource.CancelAfter`。

## 7. 分期建议与代价

### 阶段 0 · 诚实化（可立即）✅ 已落地 2026-11-05

**做：**

- 全部办理/查询 `*Async`：**删除 `Task.Run`**；改为 `Task.FromResult(同步)` 或直接同步包装，并增加 `CancellationToken ct = default`（先只 `ThrowIfCancellationRequested`）。  
- XML/文档标注：过渡语义 =「尚未 IO-await，但不再假换线程」。  
- 宿主 Job：**优先调同步** `RunProcess`，避免无意义 async。

**落地备注：** `WorkflowService.ProcessExecution` / `Query`；`IWorkflowService`；sleveen-admin `Wf2XmlController.Runtime` / `Operations/Handlers` / `SailFormBizHost` / `SailNodePolicyJobWorker`；引擎 `AutoApproveAnchorWorker`。

**代价：** 极低。ASP.NET 若依赖「旧假 Async 挪开请求线程」，需在宿主显式 offload（A3）——这是职责归位，不是功能回退。

**收益：** 去掉线程池套娃；契约开始诚实；为真异步让路。

### 阶段 1 · 令牌贯穿旁路 + 表面 — **已落地 2026-11-05**（DB 仍同步，按 A7）

**做（已完成）：**

- Notifier / Outbox Drain / AutoApprove：`ct` 在 Drain → `ProcessPending` → Dispatcher → `NotifyAsync` 贯穿；认领前后 `ThrowIfCancellationRequested`。  
- `IWorkflowService` 所有 `*Async` 统一带 `CancellationToken`（阶段 0 已齐）。  
- 基线文档增加「假 Async 禁止」条文（[特性说明-引擎能力基线.md](./特性说明-引擎能力基线.md) §3）。  
- **未做（等 1.5）：** 办理热路径 DB 真 await（仍同步 Clip）。

**代价：** 小。插件实现需检查是否忽略 `ct`。

### 阶段 1.5 · mooSQL 扩展 — **最小验收面已落地 2026-11-05**

**做（mooSQL 仓）：**

- SQLBuilder：`queryAsync`/`doUpdateAsync`/`doInsertAsync`/`doDeleteAsync`/`exe*Async` 增加 `CancellationToken` 虚重载；StepBuilder 下传 ADO。  
- SQLClip：`queryListAsync` / `queryUniqueAsync` / `doUpdateAsync` / `doDeleteAsync`。  
- 升级说明：mooSQL `SQLBuilder-Clip异步与CancellationToken.md`；SQLite 执行测覆盖匹配/取消/更新。

**已知边界：** 单列 FirstField / 尾投影 / `queryUnique` 深度 ct 仍可后续补；**不阻塞**引擎阶段 2 开工（实体多列读 + 更新已够 Manager 热点换轨）。

### 阶段 2 · Manager 热点 IO-await — **首包已落地 2026-11-05**

**前置：** 阶段 1.5 验收通过（§6.3）。

**已做：**

- Manager：`GetRunningNodeAsync`、`GetByIdAsync`（AI/PI）、`GetRunningActivityInstanceListAsync`、`GetTaskViewAsync` / `GetTaskOfMineByActivityInstanceAsync`、`GetVariableListByActivityAsync`。  
- `InstanceExecutionLock.AcquireAsync(ct)`；`StartProcessAsync` / `RunProcessAsync` / `RunProcessAutoAsync` await 锁后再走同步 Core（Mediator 暂未换轨）。  
- 同步 API 全保留。

**未做（留给 2 续 / 3）：** Insert Task/AI 的 Repo async；Mediator `Execute` 内热点改调 Manager async；其它办理动词 Async 入口同样 await 锁。

**代价：** 中。双轨 sync/async 维护一段时间。  
**禁止：** 绕过 Clip 私自拼 Builder async（A7）。

### 阶段 3 · Mediator / 锁深链（可选大版本）

**做：**

- `ExecuteWorkItem` / 网关汇聚等传 `ct`。  
- 实例锁改为可 async 等待。  
- Assignee 查库 Resolver 可选 async。

**代价：** 大。回归面 = 全办理动词 + 会签/子流程/自动节点。  
**收益：** 高并发下线程占用明显下降（在连接池允许范围内）。  
**前置：** 阶段 2 已稳定。

## 8. 开放问题（立项前拍板）

1. **阶段 0 是否立刻改宿主 Controller**：去掉对「假 Async 挪线程」的依赖后、真 IO-await 尚未就绪前，高延迟办理是否由宿主 `Task.Run` 兜底？
