# 10 · 流程业务钩子与待办推送（设计论证）

> 状态：**设计稿 / 未实施**  
> 目的：在写代码前充分论证「自定义业务逻辑钩子」与「待办消息推送」的边界、同步异步、失败补调、按流程过滤与注册形态  
> 关联现状：`EventFireTypeEnum` / `WorkflowService.Subscribe` / `EventExecutor`、BPMN Action·Service·Script、`TaskManager.SendTaskEMails`、`ISailEventHub`（stub）、`SailClient` 插槽模式（`useRuleEngine` / `useActionMethod` / `useMessageQueue`）  
> 前置讨论结论：现有能力**不够**覆盖系统级、可过滤、可异步、可补调的业务扩展；需新特性，而非仅修 `Subscribe`

---

## 1. 问题陈述

业务系统在流程运行时常需要：

1. **待办变化**时推送消息（邮件 / 企微 / 钉钉 / 站内信 / App Push），且**不得拖慢**流程主路径。
2. **实例流转**时插入自定义业务逻辑（写业务表、同步状态、校验、改变量），部分要求**高及时性**，部分允许延后。
3. 钩子常只针对**某几个流程**；若全局广播所有注册处理器，会浪费 CPU 并放大故障面。
4. 外部调用可能失败，需要**失败记录与补调**；与「失败是否回滚流程事务」必须分开定义。

本文件论证：要不要建新插槽、如何分层、如何过滤、如何异步与补调、分几期落地。

## 2. 现状盘点与缺口

### 2.1 已有能力

| 机制 | 作用域 | 同步性 | 按流程隔离 | 失败/补调 | 适合作什么 |
|------|--------|--------|------------|-----------|------------|
| `WorkflowService.Subscribe(EventFireType, Func)` | **单次** `WfAppRunner` | 同步，在流转路径上 | 仅「这次调用」；无全局白名单 | 无统一落库/重试；返回 `bool` 基本不被消费 | API 调用方临时挂钩 |
| BPMN Action / Service / Script | **流程定义内**节点 | 同步（主路径） | 天然按图隔离 | 异常通常影响节点执行 | 图内编排的业务扩展 |
| `TaskManager.SendTaskEMails` | 全局开关 `SendEmailFlag` | 异步发信，但仍在创建任务后直接触发 SMTP 客户端 | 无（全开或全关） | 无补调表 | Demo 级邮件 |
| `ISailEventHub` | Client 级 | stub `Emit` | 无 | 无 | **不可用**于生产扩展 |
| Message/Signal + `IMessageQueueService` | BPMN Message/Signal | 发 MQ | 主题级 | MQ 侧 | 跨流程消息协同，**不是**待办推送钩子 |

### 2.2 关键缺口

1. **无全局、可过滤的业务钩子注册表**（对齐 `UseBizRules` / `UseBizAction` 那种 Client 挂载方式）。
2. **`OnTaskCreaed` / `OnTaskCompleted` 枚举存在，但引擎未在待办创建/完成处 Invoke**。
3. **`EventExecutor.Execute` 仅对部分 `EventFireType` 真正调用订阅回调**；大量 Process*ing/*ed 类型「点了名」却可能不执行 handler（实现债）。
4. **无推送抽象**：邮件写死在 `TaskManager`，无法插 IM/站内信，也无法统一走 Outbox。
5. **无失败补调模型**：没有 hook/notify 执行日志与重试调度约定。
6. **无 Mode（Sync / AsyncOutbox）与 OnFailure（FailFast / RecordAndRetry）一等公民选项**。

### 2.3 为何不能「只加强 Subscribe」

| 方案 | 为何不够 |
|------|----------|
| 每次 `Run` 前 `.Subscribe(...)` | 业务系统要在**启动时**注册，而不是每个 API 记得挂；也难统一补调 |
| 全局静态事件 | 与「禁止静态取库 / Client 下传」方向冲突；难测、难多租户 |
| 只用 BPMN Action | 跨多个流程的同一推送/同一套业务规则会重复画图；运维侧难统一开关 |
| 回调里 `Task.Run` | 仍占线程、无持久化、进程挂了就丢；**不是**可靠异步 |

结论：需要 **Client 级正式特性**，与现有 Subscribe / BPMN Action **并存、职责切开**。

## 3. 目标与非目标

### 3.1 目标

- 提供两类可注册能力（**刻意拆开**，避免一个接口既推送又改业务）：
  - **Workflow Hook**：流程/活动/任务生命周期上的业务扩展。
  - **Task Notifier**：待办创建/完成/转交等通知旁路。
- 支持 **Sync** 与 **AsyncOutbox**；推送默认 AsyncOutbox。
- 支持注册时 **ProcessCode / ProcessId 白名单**；未命中不调用。
- 支持 **FailFast**（影响主事务）与 **RecordAndRetry**（落库补调）。
- 注册形态对齐 `SailClient` / `UseXxx` 管道，业务包可扩展。
- 与现有 `Subscribe`、BPMN Action **兼容**：不强制迁移。

### 3.2 非目标（本特性首期不做）

- 不替换 BPMN Action/Service/Script。
- 不实现完整企业消息中台（只定义引擎侧契约 + 默认可落库的 Outbox 形状；具体企微/钉钉适配在 biz/ext）。
- 不在首期做分布式事务（Saga）；Async 与主流程至多「同库 Outbox 同事务写入」。
- 不把 `ISailEventHub.Emit` 直接升级为唯一事件总线（可后续再统一命名；本特性先独立契约，避免 stub 语义污染）。
- 不首期做可视化钩子编排器。

## 4. 核心论证：为何拆成 Hook 与 Notifier

```
流转主路径
  ├─ 写库（实例 / 活动 / 待办）          ← 必须成功
  ├─ Sync Hook（白名单命中）             ← 可选；FailFast 可回滚
  ├─ 写 Outbox（Async Hook / Notify）  ← 与业务库同事务最佳
  └─ 返回 WfExecutedResult
后台 Worker
  └─ 消费 Outbox → 调外部 HTTP / 推送 → 失败则重试
```

| 维度 | Workflow Hook | Task Notifier |
|------|---------------|---------------|
| 典型用途 | 写业务状态、校验、改变量、审计 | 待办提醒、渠道推送 |
| 默认同异步 | 可 Sync 或 Async | **默认 AsyncOutbox** |
| 失败默认 | 由注册选项决定 | **RecordAndRetry**（不因推送失败回滚流程） |
| 触发点 | Process / Activity / Task 事件 | 以 Task 生命周期为主（可订阅子集） |
| 性能敏感 | Sync 必须短；重活改 Async | 禁止同步打外部网关 |

混成一个 `IWorkflowEventHandler` 会导致：推送被误配成 FailFast、或业务校验被误配成 fire-and-forget。**拆开是产品语义，不是多写两个接口那么简单。**

## 5. 同步 vs 异步

### 5.1 定义（本特性用语）

| Mode | 含义 | 主路径行为 |
|------|------|------------|
| **Sync** | 在当前流转调用栈内执行 handler | 等待完成；异常按 OnFailure 处理 |
| **AsyncOutbox** | 主路径只持久化「待执行记录」 | 不调用外部系统；提交后由 Worker 执行 |

明确反对：

- 在 Sync handler 内自行 `Task.Run` / `ThreadPool.Queue` 当作「异步」（不可靠、难观测）。
- 在 `TaskManager.Insert` 后同步 `HttpClient.Post` 推企微。

### 5.2 选型建议

| 场景 | 推荐 Mode | OnFailure |
|------|-----------|-----------|
| 待办推送 | AsyncOutbox | RecordAndRetry |
| 必须与流程同事务的业务写库 | Sync | FailFast |
| 及时性高但可补调的外部同步 | Sync 短超时 **或** AsyncOutbox + 高优先级队列 | RecordAndRetry |
| 审计日志 | AsyncOutbox | RecordAndRetry |

### 5.3 事务边界（推荐默认）

- **理想**：流程写库与 Outbox insert **同一 `SQLBuilder` 事务**；提交后 Worker 才可见 → 避免「流程回滚了还推送」。
- **可接受退化**：若首期 Worker 未就绪，Async 可先「内存 Channel + 进程内消费」，但文档必须标明**进程崩溃会丢**，不得标为生产默认。

## 6. 按流程注册与性能

### 6.1 过滤必须是一等公民

注册选项概念：

```text
HookRegistration / NotifyRegistration
  - Id / Name
  - Events: EventFireTypeEnum[]   // 或 Notifier 专用 TaskNotifyKind
  - ProcessCodes: string[]        // 推荐业务稳定键
  - ProcessIds: string[]          // 可选；与 Codes 为 OR
  - Match: Whitelist | All        // 默认 Whitelist；All 需显式
  - Mode: Sync | AsyncOutbox
  - OnFailure: FailFast | RecordAndRetry
  - Order: int
```

分发伪逻辑：

1. 从 `EventContext` 取 `ProcessId`，必要时解析 `ProcessCode`（可缓存）。
2. **先按 Process 白名单过滤**，再按 Event 过滤。
3. 未命中 → **零分配或极少分配后返回**（禁止先创建重型 `EventService` 再判断）。
4. 命中列表按 `Order` 执行 Sync；Async 只写 Outbox。

### 6.2 为何默认 Whitelist

- 业务系统往往 80% 流程无自定义钩子；全局 `All` 会让每次流转扫一遍宿主里所有 handler。
- 白名单把成本收敛到「配置了钩子的流程」。
- 若确需全局审计，显式 `Match = All` 且优先 AsyncOutbox。

### 6.3 与 BPMN Action 的分工

| 手段 | 何时用 |
|------|--------|
| BPMN Action/Service | 逻辑属于**该流程版本定义**的一部分，随 XML/JSON 发布 |
| Client Hook 白名单 | 逻辑属于**业务宿主横切**（多流程共用一套推送/一套状态机同步） |
| `Subscribe` | 单次 API、测试、临时诊断 |

三者可叠加；文档约定：**同一业务不要在三处各写一份**。

### 6.4 性能预算（建议验收指标）

- 无命中钩子的流转：相对基线额外开销 &lt; 可测量噪声（目标：仅几次字典查找）。
- Sync 单钩子：建议硬超时（如 2s）可配置；超时视为失败并走 OnFailure。
- Async：主路径 Outbox insert 批量可后续优化；首期单条 insert 即可。

## 7. 失败、记录与补调

### 7.1 OnFailure 语义

| 策略 | Sync | AsyncOutbox |
|------|------|-------------|
| **FailFast** | 抛错 → 参与当前事务回滚（若在事务内） | 不适用（或仅表示「写入 Outbox 失败则回滚」） |
| **RecordAndRetry** | 捕获异常 → 写失败记录 → 主流程继续（需产品确认是否允许「业务未执行完流程仍成功」） | Worker 执行失败 → 更新重试状态 |

**产品警告**：Sync + RecordAndRetry 意味着「流程已成功推进，但业务钩子没跑成」。只适用于弱依赖；强一致必须 FailFast。

### 7.2 执行日志 / Outbox 表形状（逻辑模型，非最终 DDL）

建议字段（可合并为一表 `wf_hook_outbox`，用 `kind` 区分 hook/notify）：

| 字段 | 说明 |
|------|------|
| id | 主键 |
| kind | Hook / Notify |
| handler_name | 注册名 |
| event_type | 事件枚举或字符串 |
| process_id / process_code | 过滤与排查 |
| process_instance_id / activity_instance_id / task_id | 关联 |
| payload_json | 幂等重放所需快照（控制体积） |
| status | Pending / Succeeded / Failed / Dead |
| attempt | 重试次数 |
| next_retry_at | 退避 |
| last_error | 截断错误信息 |
| created_at / updated_at | |

### 7.3 幂等

- 补调必须可重入：handler 应用业务幂等键（如 `task_id + handler_name + event`）。
- Outbox 消费用 `status` CAS 或租约，避免双 Worker 重复成功旁路（推送可接受「偶发重复」时需渠道侧去重）。

### 7.4 退避与死信

- 指数退避 + 上限；超过 `max_attempts` → `Dead`，人工或运维 API 重放。
- 首期可不做管理 UI，但要有查询与「重置为 Pending」的扩展点。

## 8. 事件模型与触发点

### 8.1 复用 `EventFireTypeEnum`，先修触发完整性

短期：

- Hook 继续复用 `EventFireTypeEnum`，避免两套枚举。
- 实施时必须：
  - 在待办创建/完成（及如有：转交、撤回任务）处触发 `OnTask*`（并修正拼写 `OnTaskCreaed` → `OnTaskCreated`，保留旧名 Obsolete）。
  - 收紧或修复 `EventExecutor`：凡对外宣布会 Invoke 的类型，必须真正调用 handler；或文档标明「仅下列类型有效」。

Notifier 可用更窄枚举，避免与流程事件混淆：

```text
TaskNotifyKind: Created | Completed | Cancelled | Entrusted | ...
```

### 8.2 上下文

统一上下文（概念）应包含：

- 应用：`AppInstanceId`、`AppName`
- 流程：`ProcessId`、`ProcessCode`、`ProcessInstanceId`、`Version`
- 节点/任务：`ActivityId`、`ActivityInstanceId`、`TaskId`、指派人
- 资源：只读访问 `IEventService` 能力（变量读写是否允许 Sync Hook 需单独约定；建议 Sync Hook 可写变量，Async 默认只读快照）

Async 只能依赖 **payload 快照**，不能假设 Worker 里还能拿到同一请求级 `SQLBuilder` 事务。

## 9. 注册与管道形态（对齐 SailClient）

### 9.1 推荐 API 形态（设计级，非最终签名）

```csharp
// 业务宿主
builder.Services
    .UseBizHooks()                    // 或逐个 UseWorkflowHook(...)
    .UseBizTaskNotify(o => { ... });  // 邮件 / 企微 等

// 过滤示例
services.UseWorkflowHook(new LeaveStatusSyncHook(), o =>
{
    o.ProcessCodes = new[] { "leave", "leave- entourage" };
    o.Events = new[] { EventFireTypeEnum.OnActivityExecuted, EventFireTypeEnum.OnProcessCompleted };
    o.Mode = HookMode.Sync;
    o.OnFailure = HookFailure.FailFast;
});

services.UseTaskNotifier(new WeComTaskNotifier(), o =>
{
    o.ProcessCodes = new[] { "leave", "purchase" }; // 也可 All
    o.Mode = HookMode.AsyncOutbox;                 // 强制或默认
    o.OnFailure = HookFailure.RecordAndRetry;
});
```

挂载点：`SailClient` 上 `WorkflowHooks` / `TaskNotifiers` 注册表（类似 `ActionMethods`，但是带过滤选项的列表，不是按 enum 单槽覆盖）。

### 9.2 与现有 Subscribe 关系

| | Subscribe | Client Hook/Notify |
|--|-----------|---------------------|
| 生命周期 | 单次 Runner | Client 生命周期 |
| 过滤 | 无（本次全有） | Process 白名单 |
| 补调 | 无 | 有（Async / RecordAndRetry） |
| 去留 | **保留** | 新增 |

迁移建议：宿主横切逻辑迁到 Client 注册；调用方临时逻辑继续 Subscribe。

### 9.3 包边界建议

| 内容 | 位置 |
|------|------|
| 契约、注册表、分发器、Outbox 抽象 | `engine`（或未来 `sailflow.hooks` 契约包） |
| 默认同库 Outbox 存储 + Worker 宿主扩展 | `engine` 或 `sailflow.msg` / 新 `sailflow.hooks` |
| 企微/钉钉/邮件 Notifier 实现 | `biz` 或 `ext` |
| 业务 Sync Hook 实现 | 业务系统程序集 |

是否新建 `sailflow.hooks` 扩展包：**论证倾向独立包**（与 action/msg/bizRule 一致），避免 engine 引用各通知 SDK；engine 只留契约与分发。邮件可从 `TaskManager` 迁到 `ITaskNotifier` 的 Mail 实现，`SendEmailFlag` 变为「是否注册默认 MailNotifier」。

## 10. 安全与稳定性

- Sync Hook **禁止**长时间占用；需超时与（可选）电路熔断。
- Payload 脱敏：通知内容勿默认塞完整表单；Outbox 注意个人数据留存周期。
- 权限：补调 API 仅运维；Worker 使用专用凭证。
- 多租户：若未来多 `SailClient`，注册表必须在 Client 实例上，禁止静态列表。

## 11. 方案对比（决策记录）

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 只修 Subscribe + 文档 | 改动小 | 无全局注册/过滤/补调 | **否** |
| B. 单一 IEventHandler 全局列表 | 实现简单 | 推送与业务耦合；易误用 Sync | **否** |
| C. Hook + Notifier 双轨 + 白名单 + Outbox | 语义清、可演进 | 首期工作量大 | **采纳** |
| D. 全部靠 MQ Topic | 天然异步 | 强一致业务难；运维重；小项目过重 | 仅作 Async 传输可选实现，不作唯一模型 |

**选定 C**。Async 传输首期用**同库 Outbox**；已有 `sailflow.msg` 时可作 Outbox 消费者通知渠道，但不强制业务钩子都进 RabbitMQ。

## 12. 分期实施建议（论证后的落地顺序）

> 本节是实施路线图；**在本文评审通过前不写业务代码。**

### Phase 0 — 文档与契约评审（当前）

- 评审本文件：Sync/Async、FailFast 语义、白名单默认、是否独立 `sailflow.hooks`。
- 确认拼写修正 `OnTaskCreated` 的兼容策略。

### Phase 1 — 最小可用（MVP）

- engine：`IWorkflowHook` / `ITaskNotifier` + 注册表 + Process 过滤分发。
- 在 `TaskManager` 创建/完成处触发 Task 事件 / Notifier。
- Sync + FailFast / RecordAndRetry（Record 可先写日志表简化版）。
- **AsyncOutbox 可先接口预留**，MVP 允许 Notifier 仅「注册后进程内队列」并打警告；或直接做同库 Outbox 表（更推荐一步到位若表结构已有规范）。
- 默认邮件改为 Notifier；`SendEmailFlag` 兼容映射。
- 修复/收窄 `EventExecutor` 行为与文档一致。

### Phase 2 — 可靠异步

- 同库 Outbox + Worker（HostedService 或外部 Job）。
- 退避、死信、幂等键约定。
- biz：`UseBizTaskNotify` 示例（Mail + 一个 IM 可后续）。

### Phase 3 — 体验与治理

- 补调查询 API、指标（成功率、延迟）。
- 可选：与 `ISailEventHub` 命名统一。
- 性能测试：无钩子基线 vs 白名单未命中 vs 命中 Sync。

## 13. 验收标准（评审用）

1. 未注册任何 Hook/Notifier 时，主路径行为与今日一致（邮件开关行为可兼容映射）。
2. 仅注册流程 A 的 Hook 时，跑流程 B **不进入**该 Hook（可用计数器测）。
3. Notifier 默认不因外部 HTTP 500 导致 `Run` 失败（AsyncOutbox + RecordAndRetry）。
4. Sync + FailFast Hook 抛错时，流程事务回滚（在有事务的路径上）。
5. Outbox 记录在流程提交前写入；回滚后 Worker 不可见该条。
6. 文档明确：Subscribe / BPMN Action / Client Hook 三者职责，无「三处重复实现」的鼓励性写法。

## 14. 开放问题（实施前需拍板）

1. **Sync + RecordAndRetry 是否允许？** 还是 Sync 只允许 FailFast，弱依赖一律 Async？  
   - *倾向*：Sync 仅 FailFast；弱依赖强制 AsyncOutbox，减少「流程成功、业务没跑」的灰区。
2. **ProcessCode 从何处解析？** 实例表是否总有 Code，还是要查定义缓存？  
3. **Outbox 是否首期就落表？** 还是 Phase1 内存队列 + Phase2 表？  
   - *倾向*：有现成库规范则首期落表，避免两次协议变更。
4. **独立程序集名**：`sailflow.hooks` vs 放入 `sailflow.msg`？  
   - *倾向*：`sailflow.hooks`（msg 侧重 MQ；hooks 侧重生命周期扩展）。
5. **变量写入**：Async Hook 是否禁止写变量，仅 Sync 可写？  
   - *倾向*：是。

---

## 15. 总结

- 现状的 `Subscribe`、BPMN Action、邮件发送**不能**满足「按流程注册、推送不堵主路径、失败可补调」的系统级需求。
- 采纳 **Workflow Hook 与 Task Notifier 双轨**：过滤白名单、Sync/AsyncOutbox、FailFast/RecordAndRetry。
- 性能靠 **注册时白名单 + 分发器前置过滤**；可靠性靠 **同库 Outbox + Worker**，而不是 `Task.Run`。
- 与现有管道对齐：`SailClient` / `UseXxx`；实现可落在未来的 `sailflow.hooks`，业务通知适配在 biz/ext。
