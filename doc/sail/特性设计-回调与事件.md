## 1. 问题陈述

业务系统在流程运行时常需要：

1. **待办变化**时推送消息（邮件 / 企微 / 钉钉 / 站内信 / App Push），且**不得拖慢**流程主路径。
2. **实例流转**时插入自定义业务逻辑（写业务表、同步状态、校验、改变量），部分要求**高及时性**，部分允许延后。
3. **发送/同意真正执行前**做业务校验（财务等严谨场景）：失败须**中止推进**，并把原因经流程 API 回传前端；与「通过后计算」必须拆开。
4. 钩子常只针对**某几个流程 / 节点**；若全局广播所有注册处理器，会浪费 CPU 并放大故障面。
5. 外部调用可能失败，需要**失败记录与补调**；与「失败是否回滚流程事务 / 是否仅校验拒绝」必须分开定义。

本文件论证：要不要建新插槽、如何分层（含 Gate）、如何过滤、如何异步与补调、分几期落地。

## 2. 现状盘点与缺口

### 2.1 已有能力

| 机制 | 作用域 | 同步性 | 按流程隔离 | 失败/补调 | 适合作什么 |
|------|--------|--------|------------|-----------|------------|
| `WorkflowService.Subscribe(EventFireType, Func)` | **单次** `WfAppRunner` | 同步，在流转路径上 | 仅「这次调用」；无全局白名单 | 无统一落库/重试；返回 `bool` 基本不被消费 | API 调用方临时挂钩 |
| BPMN Action / Service / Script | **流程定义内**节点 | 同步（主路径） | 天然按图隔离 | 异常通常影响节点执行 | 图内编排的业务扩展 |
| `TaskManager.SendTaskEMails` | 全局开关 `SendEmailFlag` | 异步发信，但仍在创建任务后直接触发 SMTP 客户端 | 无（全开或全关） | 无补调表 | Demo 级邮件 |
| `ISailEventHub` | Client 级 | stub `Emit` | 无 | 无 | **不可用**于生产扩展 |
| Message/Signal + `IMessageQueueService` | BPMN Message/Signal | 发 MQ | 主题级 | MQ 侧 | 跨流程消息协同，**不是**待办推送钩子 |

### 2.2 关键缺口

1. **无全局、可过滤的业务钩子注册表**（对齐 `UseBizRules` / `UseBizAction` 那种 Client 挂载方式）。
2. **`OnTaskCreaed` / `OnTaskCompleted` 枚举存在，但引擎未在待办创建/完成处 Invoke**。
3. **`EventExecutor.Execute` 仅对部分 `EventFireType` 真正调用订阅回调**；大量 Process*ing/*ed 类型「点了名」却可能不执行 handler（实现债）。
4. **无推送抽象**：邮件写死在 `TaskManager`，无法插 IM/站内信，也无法统一走 Outbox。
5. **无失败补调模型**：没有 hook/notify 执行日志与重试调度约定。
6. **无 Mode（Sync / AsyncOutbox）与 OnFailure（FailFast / RecordAndRetry）一等公民选项**。
7. **无发送前 Gate**：缺少「推进前校验 → 结构化拒绝 → `WfExecutedResult` 回前端」的一等时机与结果形态；仅靠抛异常会与系统故障混淆，且触发点可能已过早落库。

### 2.3 为何不能「只加强 Subscribe」

| 方案 | 为何不够 |
|------|----------|
| 每次 `Run` 前 `.Subscribe(...)` | 业务系统要在**启动时**注册，而不是每个 API 记得挂；也难统一补调 |
| 全局静态事件 | 与「禁止静态取库 / Client 下传」方向冲突；难测、难多租户 |
| 只用 BPMN Action | 跨多个流程的同一推送/同一套业务规则会重复画图；运维侧难统一开关 |
| 回调里 `Task.Run` | 仍占线程、无持久化、进程挂了就丢；**不是**可靠异步 |

结论：需要 **Client 级正式特性**，与现有 Subscribe / BPMN Action **并存、职责切开**。

## 3. 目标与非目标

### 3.1 目标

- 提供三类可注册能力（**刻意拆开**）：
  - **Workflow Gate**：发送/流转**真正落库推进前**的同步校验；可 `Reject` 并回传前端。
  - **Workflow Hook**：通过校验并推进后的业务扩展（回写、汇总、结束出单等）。
  - **Task Notifier**：待办创建/完成/转交等通知旁路。
- 支持 **Sync** 与 **AsyncOutbox**；推送默认 AsyncOutbox；Gate **仅 Sync**。
- 支持注册时 **ProcessCode / ProcessId / ActivityCode 白名单**；未命中不调用。
- Hook 支持 **FailFast**（影响主事务）与 **RecordAndRetry**（落库补调）；Gate 失败为 **Reject**（业务拒绝，非事故异常）。
- 注册形态对齐 `SailClient` / `UseXxx` 管道，业务包可扩展。
- 与现有 `Subscribe`、BPMN Action **兼容**：不强制迁移。

### 3.2 非目标（本特性首期不做）

- 不替换 BPMN Action/Service/Script。
- 不实现完整企业消息中台（只定义引擎侧契约 + 默认可落库的 Outbox 形状；具体企微/钉钉适配在 biz/ext）。
- 不在首期做分布式事务（Saga）；Async 与主流程至多「同库 Outbox 同事务写入」。
- 不把 `ISailEventHub.Emit` 直接升级为唯一事件总线（可后续再统一命名；本特性先独立契约，避免 stub 语义污染）。
- 不首期做可视化钩子编排器。
- **不**用本特性承担「谁来办」：待办人算人/流出见 [特性说明-待办人管道.md](./特性说明-待办人管道.md)；**Notifier ≠ Assignee ConfigPair**。
- **不**把抄送并进 Notifier 或 Assignee：抄送为**独立通道**（产品表/自有事件）；即便引擎日后内置抄送，也须独立事件，禁止与待办推送、算人配置混用（对齐待办人管道 **R5**）。

## 4. 核心论证：为何拆成 Gate / Hook / Notifier

```
流转主路径（Run / 发送 / 同意）
  ├─ 1. Gate（OnValidating）              ← 仅 Sync；Reject → 中止，零推进或干净回滚
  ├─ 2. 写库（完成待办 / 推进实例）        ← Gate 通过后才执行
  ├─ 3. Sync Hook（白名单命中）           ← 回写、汇总等；FailFast 可回滚
  ├─ 4. 写 Outbox（Async Hook / Notify）← 与业务库同事务最佳
  └─ 5. 返回 WfExecutedResult
后台 Worker
  └─ 消费 Outbox → 调外部 HTTP / 推送 → 失败则重试
```

| 维度 | Workflow Gate | Workflow Hook | Task Notifier |
|------|---------------|---------------|---------------|
| 典型用途 | 发送前业务校验、合规卡控 | 写业务状态、汇总、结束出单 | 待办提醒、渠道推送 |
| 默认同异步 | **仅 Sync** | Sync 或 Async | **默认 AsyncOutbox** |
| 失败语义 | **Reject**（业务拒绝 → 回前端） | FailFast / RecordAndRetry | 业务自管或 RecordAndRetry |
| 时机 | **推进落库之前** | 推进之中/之后 | 待办生命周期 |
| 性能敏感 | 必须短；禁止调慢外部（或严格超时） | Sync 必须短；重活改 Async | 禁止同步打外部网关 |

混成一个接口会导致：推送被配成 FailFast、校验被配成 fire-and-forget、或「校验失败」与「系统异常」无法区分。**三轨拆开是产品语义。**

### 4.1 为何 Gate 不能只用「Sync Hook + 抛异常」

| 点 | 说明 |
|----|------|
| 时机 | Hook 若挂在写库之后，FailFast 只能靠回滚；财务场景要求**发送动作真正执行前**卡死， ideally 无副作用或可干净回滚。 |
| 语义 | 抛 `Exception` → `Run` 捕获后 `Status=Failed`，前端难区分校验拒绝 vs 引擎事故；文案常被包进通用 `runprocess.error`。 |
| 结构 | 财务常需错误码、多条明细；字符串 `Message` 不够。 |
| 职责 | 「发送前校验」与「通过后汇总」不应塞进同一 `OnActivityExecuting`。 |

因此 Gate 使用显式结果类型 `HookResult`（Ok / Reject），由分发器映射到 `WfExecutedResult`，**不当事故异常**。

## 5. 同步 vs 异步

### 5.1 定义（本特性用语）

| Mode | 含义 | 主路径行为 |
|------|------|------------|
| **Sync** | 在当前流转调用栈内执行 handler | 等待完成；异常按 OnFailure 处理 |
| **AsyncOutbox** | 主路径只持久化「待执行记录」 | 不调用外部系统；提交后由 Worker 执行 |

明确反对：

- 在 Sync handler 内自行 `Task.Run` / `ThreadPool.Queue` 当作「异步」（不可靠、难观测）。
- 在 `TaskManager.Insert` 后同步 `HttpClient.Post` 推企微。

### 5.2 选型建议

| 场景 | 推荐 Mode | OnFailure |
|------|-----------|-----------|
| 待办推送 | AsyncOutbox | RecordAndRetry |
| 必须与流程同事务的业务写库 | Sync | FailFast |
| 及时性高但可补调的外部同步 | Sync 短超时 **或** AsyncOutbox + 高优先级队列 | RecordAndRetry |
| 审计日志 | AsyncOutbox | RecordAndRetry |

### 5.3 事务边界（推荐默认）

- **理想**：流程写库与 Outbox insert **同一 `SQLBuilder` 事务**；提交后 Worker 才可见 → 避免「流程回滚了还推送」。
- **可接受退化**：若首期 Worker 未就绪，Async 可先「内存 Channel + 进程内消费」，但文档必须标明**进程崩溃会丢**，不得标为生产默认。

## 6. 按流程注册与性能

### 6.1 过滤必须是一等公民

注册选项概念：

```text
HookRegistration / NotifyRegistration
  - Id / Name
  - Events: EventFireTypeEnum[]   // Hook 用
  - TaskKinds: TaskNotifyKind[]   // Notifier 用
  - ProcessCodes: string[]        // 流程**定义**唯一编码（非实例字段）；推荐业务稳定键
  - ProcessIds: string[]          // 可选；定义 Id；与 Codes 为 OR
  - ActivityCodes: string[]       // 可选；节点级过滤（场景：财务领导审批等）
  - Match: Whitelist | All        // 默认 Whitelist；All 需显式
  - Mode: Sync | AsyncOutbox
  - OnFailure: FailFast | RecordAndRetry  // 推送轨可弱化：失败日志由业务自管
  - Order: int
```

分发伪逻辑：

1. 从上下文取实例上的 `ProcessId`（+Version），经**流程定义**解析/缓存得到 `ProcessCode`（定义唯一编码，不是实例表字段）。
2. **先按 `Match` / ProcessCodes|ProcessIds 白名单过滤**，再按 `ActivityCodes`（若配置），再按 `Events` / `TaskKinds`。
3. 未命中 → **零分配或极少分配后返回**（禁止先创建重型 `EventService` 再判断）。
4. 命中列表按 `Order` 执行 Sync；Async 只写 Outbox。
5. 同一次流转建议顺序：**Sync Hook → 写 Outbox（Async Hook / Notifier）→ 返回**。

### 6.2 为何默认 Whitelist

- 业务系统往往 80% 流程无自定义钩子；全局 `All` 会让每次流转扫一遍宿主里所有 handler。
- 白名单把成本收敛到「配置了钩子的流程」。
- 若确需全局审计，显式 `Match = All` 且优先 AsyncOutbox。

### 6.3 与 BPMN Action 的分工

| 手段 | 何时用 |
|------|--------|
| BPMN Action/Service | 逻辑属于**该流程版本定义**的一部分，随 XML/JSON 发布 |
| Client Hook 白名单 | 逻辑属于**业务宿主横切**（多流程共用一套推送/一套状态机同步） |
| `Subscribe` | 单次 API、测试、临时诊断 |

三者可叠加；文档约定：**同一业务不要在三处各写一份**。

### 6.4 性能预算（建议验收指标）

- 无命中钩子的流转：相对基线额外开销 &lt; 可测量噪声（目标：仅几次字典查找）。
- Sync 单钩子：建议硬超时（如 2s）可配置；超时视为失败并走 OnFailure。
- Async：主路径 Outbox insert 批量可后续优化；首期单条 insert 即可。

## 7. 失败、记录与补调

### 7.0 Gate Reject vs Hook FailFast（先分清）

| | Gate `Reject` | Hook FailFast（异常） | Hook/Notify 补调失败 |
|--|---------------|----------------------|----------------------|
| 含义 | 业务规则不通过 | 推进后强依赖执行失败 | 旁路/弱依赖失败 |
| 是否推进 | **否**（卡在 Gate） | 已推进则回滚事务 | 主流程已成功 |
| 回前端 | `WfExecutedResult` 带校验消息/码 | `Failed` + 异常信息 | 一般不挡本次 Run |
| 是否记 Outbox 死信 | 否（正常业务结果） | 可选 | 是 |

### 7.1 OnFailure 语义（仅 Hook / Notifier）

| 策略 | Sync | AsyncOutbox |
|------|------|-------------|
| **FailFast** | 抛错 → 参与当前事务回滚（若在事务内） | 不适用（或仅表示「写入 Outbox 失败则回滚」） |
| **RecordAndRetry** | 捕获异常 → 写失败记录 → 主流程继续（需产品确认是否允许「业务未执行完流程仍成功」） | Worker 执行失败 → 更新重试状态 |

**产品警告**：Sync + RecordAndRetry 意味着「流程已成功推进，但业务钩子没跑成」。只适用于弱依赖；强一致必须 FailFast。Gate **不适用** RecordAndRetry。

### 7.2 执行日志 / Outbox 表形状（逻辑模型，非最终 DDL）

建议字段（可合并为一表 `wf_hook_outbox`，用 `kind` 区分 hook/notify）：

| 字段 | 说明 |
|------|------|
| id | 主键 |
| kind | Hook / Notify |
| handler_name | 注册名 |
| event_type | 事件枚举或字符串 |
| process_id / process_code | 过滤与排查 |
| process_instance_id / activity_instance_id / task_id | 关联 |
| payload_json | 幂等重放所需快照（控制体积） |
| status | Pending / Succeeded / Failed / Dead |
| attempt | 重试次数 |
| next_retry_at | 退避 |
| last_error | 截断错误信息 |
| created_at / updated_at | |

### 7.3 幂等

- 补调必须可重入：handler 应用业务幂等键（如 `task_id + handler_name + event`）。
- Outbox 消费用 `status` CAS 或租约，避免双 Worker 重复成功旁路（推送可接受「偶发重复」时需渠道侧去重）。

### 7.4 退避与死信

- 指数退避 + 上限；超过 `max_attempts` → `Dead`，人工或运维 API 重放。
- 首期可不做管理 UI，但要有查询与「重置为 Pending」的扩展点。

## 8. 事件模型与触发点

### 8.1 复用 `EventFireTypeEnum`，并新增 Gate 时机

短期：

- Hook 继续复用 `EventFireTypeEnum`，避免两套「业务事件」枚举膨胀。
- **新增（或明确）Gate 时机**（名称待最终定稿，语义固定）：

```text
OnValidating   // 发送/同意/Run 等「将要推进」之前；仅 Gate；通过后才落库推进
```

与现有节点事件分工：

| 时机 | 谁用 | 可否改库推进 | 典型 |
|------|------|--------------|------|
| `OnValidating` | Gate | **否**（只读校验） | 财务发送前合规校验 |
| `OnActivityExecuting` | Hook | 是（已通过 Gate） | 进入节点后汇总计算 |
| `OnActivityExecuted` / `OnTask*` / `OnProcessCompleted` | Hook / Notifier | 是 | 回写字段、结束出单、推送 |

实施时必须：

- 在待办创建/完成（及如有：转交、撤回任务）处触发 `OnTask*`；枚举直接使用正确拼写 `OnTaskCreated`（重构初期，不做旧名兼容）。
- 在 `Run` / 等效发送路径上，**CompleteWorkItem / 推进写库之前**调用 Gate 分发；任一 `Reject` 立即返回。
- 收紧或修复 `EventExecutor`：凡对外宣布会 Invoke 的类型，必须真正调用 handler；或文档标明「仅下列类型有效」。

Notifier 可用更窄枚举，避免与流程事件混淆：

```text
TaskNotifyKind: Created | Completed | Cancelled | Entrusted | ...
```

### 8.2 上下文

统一上下文（概念）应包含：

- 应用：`AppInstanceId`、`AppName`
- 流程：`ProcessId`、`ProcessCode`、`ProcessInstanceId`、`Version`
- 节点/任务：`ActivityId`、`ActivityCode`、`ActivityInstanceId`、`TaskId`、指派人
- 操作：`Operation`（Run / Start / …）便于 Gate 区分「同意」与其它动作
- 资源：Gate **默认只读**（禁止写变量/写业务表）；Sync Hook 可写变量；Async 默认只读快照

Async 只能依赖 **payload 快照**，不能假设 Worker 里还能拿到同一请求级 `SQLBuilder` 事务。

### 8.3 Gate 结果映射到 `WfExecutedResult`

```text
HookResult.Ok          → 继续主路径
HookResult.Reject(...) → Status = Failed（或新增 ValidationRejected）
                         Message = 主文案
                         （扩展）ValidationCode / ValidationDetails → 前端表单提示
                         不记引擎 Error 级事故日志（可 Info/Warn）
```

现状 `Run` catch 会把异常包进 `workflowservice.runprocess.error`；Gate 路径应**绕开该模板**，直接填业务拒绝文案，避免用户看到「系统错误：余额不足」。

## 9. 注册与管道形态（对齐 SailClient）

### 9.1 契约骨架（设计级，非最终签名）

三轨刻意拆开：Gate 校验、Hook 业务、Notifier 推送。

```csharp
/// <summary>发送前闸门：仅 Sync；用结果拒绝，不抛业务校验异常。</summary>
public interface IFlowGate
{
    string Name { get; }
    HookResult Validate(FlowHookContext ctx);
}

/// <summary>业务钩子：默认可同步；上下文带事件类型。</summary>
public interface IFlowHook
{
    string Name { get; }
    void Handle(FlowHookContext ctx); // Sync 当场调；Async 由 Worker 调同一方法
}

/// <summary>待办旁路：默认异步投递后再调业务实现。</summary>
public interface ITaskNotifier
{
    string Name { get; }
    Task NotifyAsync(TaskNotifyContext ctx, CancellationToken ct);
}

public sealed class HookResult
{
    public bool IsOk { get; init; }
    public string Message { get; init; }           // 主文案 → WfExecutedResult.Message
    public string Code { get; init; }              // 业务错误码
    public IReadOnlyList<HookValidationItem> Details { get; init; }

    public static HookResult Ok() => new() { IsOk = true };
    public static HookResult Reject(string message, string code = null,
        IEnumerable<HookValidationItem> details = null) => new()
    {
        IsOk = false,
        Message = message,
        Code = code,
        Details = details?.ToList()
    };
}

public sealed class HookValidationItem
{
    public string Field { get; init; }    // 可选：表单字段
    public string Message { get; init; }
}

public enum TaskNotifyKind
{
    Created,
    Completed,
    Cancelled,
    Entrusted,
}

public enum HookMatch { Whitelist, All }
public enum HookMode { Sync, AsyncOutbox }

public sealed class HookRegistrationOptions
{
    public HookMatch Match { get; set; } = HookMatch.Whitelist;
    public string[] ProcessCodes { get; set; }
    public string[] ProcessIds { get; set; }
    public string[] ActivityCodes { get; set; }
    public EventFireTypeEnum[] Events { get; set; } // Hook；Gate 固定 OnValidating 可不填
    public TaskNotifyKind[] TaskKinds { get; set; }
    public HookMode Mode { get; set; }              // Gate 忽略，恒 Sync
    public int Order { get; set; }
}
```

注册：

### 9.2 高频需求示例

#### 场景 1：任意待办变化 → 异步调推送接口

- **轨**：`ITaskNotifier`
- **Match**：`All`（任意流程）
- **Mode**：默认 `AsyncOutbox`（可不写）
- **失败**：业务在 `NotifyAsync` 内自行记日志/重试；引擎保证不堵主路径即可

```csharp
public sealed class BizPushTaskNotifier : ITaskNotifier
{

        // 业务侧：组包、调推送 API；失败日志/重试自管

        {
            ctx.TaskId,
            ctx.ProcessInstanceId,
            ctx.ProcessCode,
            Kind = ctx.Kind,
            AssigneeUserId = ctx.AssignedUserId,
            ctx.AppInstanceId,
        }, ct);
    }

builder.Services.UseTaskNotifier(new BizPushTaskNotifier(), o =>
```

#### 场景 2：全局业务表流程字段回写（待办人 / 进度）

- **轨**：`IFlowHook`
- **Match**：`All`（全系统字段名统一 → 全局一份逻辑）
- **Mode**：`Sync`（列表页立刻看到待办人/进度）
- **失败倾向**：FailFast（回写失败应被感知）；弱依赖勿走此轨

#### 场景 3：特定节点逻辑 + 流程结束启动后续业务

拆成 **Gate（发送前）+ Hook（通过后）+ 结束 Hook**，避免一个方法里又校验又重算。

**3a-Gate. 财务领导节点「发送前」校验（Reject → 回前端）**

```csharp
public sealed class FinancePreSendGate : IFlowGate
{
    public string Name => "finance.pre-send";

    public HookResult Validate(FlowHookContext ctx)
    {
        var check = _finance.ValidateBeforeApprove(ctx.AppInstanceId, ctx.ProcessInstanceId);
        if (check.Passed)
            return HookResult.Ok();

        return HookResult.Reject(
            check.Summary,                    // 如「科目余额不足，无法提交」
            code: check.ErrorCode,            // 如 FIN_BALANCE

            {
                Field = i.Field,
                Message = i.Message
            }));
    }
}

builder.Services.UseFlowGate(new FinancePreSendGate(), o =>
{
    o.Match = HookMatch.Whitelist;

    o.ActivityCodes = new[] { "finance_leader_approve" };
    // 事件固定 OnValidating，由 UseFlowGate 约定
});
```

前端约定：`result.Status != Success` 且存在业务 `Code`/`Details` 时展示校验 UI，而非通用异常页。

#### 场景 4：内建邮件降级为「准可用」能力（构建期激活 / 业务替换激活）

现状 `TaskManager.SendTaskEMails` + `SendEmailFlag` 写死在引擎待办创建路径上，应**迁出**为可选 `ITaskNotifier`（默认 Mail 实现），不再在 Manager 内直连 SMTP。

| 用法 | 含义 |
|------|------|
| **构建期一键激活（准可用）** | 配置好 `SailConfig` 的 Smtp* 后，`UseDefaultTaskMail()` / `UseBizTaskNotify(o => o.EnableMail = true)` 挂上引擎（或 hooks 包）自带的 `DefaultMailTaskNotifier`，用默认模板即可发待办邮件 |
| **业务具化后再激活** | `UseTaskNotifier(new MyCorpMailNotifier())`：自定义模板、发件通道、收件人解析；**不**调用默认 Mail 即完全关掉内建邮件 |
| **都不注册** | 待办创建不发信（重构不保留 `SendEmailFlag` 兼容） |

```csharp
// A. 准可用：构建期显式打开默认邮件（AsyncOutbox）
builder.Services.UseDefaultTaskMail(); // 内部 UseTaskNotifier(new DefaultMailTaskNotifier(), ...)

// B. 业务侧替换：不用默认，改挂自有实现
builder.Services.UseTaskNotifier(new MyCorpMailNotifier(), o =>
{
    o.Match = HookMatch.All;
    o.TaskKinds = new[] { TaskNotifyKind.Created, TaskNotifyKind.Completed };
});
```

落地约束：

- 默认 Mail 必须走 **AsyncOutbox**（与其它 Notifier 一致），禁止再在 `Insert` 后直接 `SendEMailAsync`。
- 「准可用」= 有 SMTP 配置即可亮灯；生产级多租户/品牌模板由业务 Notifier 覆盖。
- `DefaultMailTaskNotifier` 放在 **`sailflow.msg`**；**engine 的 `TaskManager` 不再引用发信实现**。
- 重构初期：**删除** `SendEmailFlag` 驱动发信；只认显式 `UseDefaultTaskMail()` / 自有 Notifier。

#### 场景 5：多通道串行（常规邮件 + 内部邮微改 + 微信等），彼此默认互不影响

Notifier / Hook / Gate 均为**列表注册**（非单槽覆盖，有别于 `useMessageQueue` 单实例）。同一待办事件可挂多条通道，按 `Order` 串行投递。

```csharp
// 1) 常规/默认邮件
builder.Services.UseTaskNotifier(new DefaultMailTaskNotifier(), o =>
{
    o.Match = HookMatch.All;
    o.Order = 10;
    o.TaskKinds = new[] { TaskNotifyKind.Created, TaskNotifyKind.Completed };
});

// 2) 继承或装饰默认实现后微改（内部系统邮件：改模板/抄送/发件域）
//    实现手法：继承 DefaultMailTaskNotifier 或包装 ITaskNotifier；注册上仍是独立条目
builder.Services.UseTaskNotifier(new InternalMailTaskNotifier(/* 可基于默认逻辑微改 */), o =>
{
    o.Match = HookMatch.All;
    o.Order = 20;
    o.TaskKinds = new[] { TaskNotifyKind.Created, TaskNotifyKind.Completed };
});

// 3) 短消息 / 企微 / 微信等
builder.Services.UseTaskNotifier(new WeComTaskNotifier(), o =>
{
    o.Match = HookMatch.All;
    o.Order = 30;
    o.TaskKinds = new[] { TaskNotifyKind.Created, TaskNotifyKind.Entrusted };
});
```

串行与隔离约定：

| 规则 | 说明 |
|------|------|
| **按 `Order` 串行** | 同一事件命中多个 Notifier，依次入 Outbox / 依次消费（实现可选并行消费，但注册顺序语义保留） |
| **通知轨默认互不影响** | 某一通道失败（业务自管日志或 RecordAndRetry）**不取消**后续通道——邮件挂了微信仍发 |
| **Gate 例外（短路）** | 任一 Gate `Reject` 即中止推进；这是卡控，不是通知 |
| **Sync Hook FailFast** | 抛错会中断后续 Sync 并回滚；弱依赖不要用 FailFast |
| **Name** | 多通道应用**不同 `Name`**；同名策略（后注册覆盖 vs 禁止）见 §9.5 / §14，实施前拍板 |

「继承后微改」只影响**类实现**；在注册表里仍是两个独立 `ITaskNotifier`，不是覆盖同一槽位。

#### 场景 6：在 `ext/msg`（sailflow.msg）内置待办推送实现骨架

**结论：采纳。** 调 HTTP、发邮件、发短信、发站内信在业务侧差异只在「通道怎么发」；共同需求高度同构：

| 共同信息 | 说明 |
|----------|------|
| 哪个流程 | `ProcessId` / `ProcessCode` / `ProcessInstanceId` |
| 谁的待办 | `AssignedUserId`（及解析出的邮箱/手机/openId） |
| 待办还是已办 | `TaskNotifyKind`：Created≈开消息，Completed/Cancelled≈关/撤消息 |
| 业务单据 | `AppInstanceId` / `AppName` 等 |

若每个通道都从零写日志、try/catch、失败钩子，业务成本高且行为不一致。应在 **`sailflow.msg`** 提供**模板方法骨架**，业务只填「怎么发」。

```csharp
// 设计级示意：sailflow.msg 内
public abstract class TaskNotifyChannelBase : ITaskNotifier
{
    public abstract string Name { get; }

    public async Task NotifyAsync(TaskNotifyContext ctx, CancellationToken ct)
    {
        try
        {
            OnBeforeSend(ctx);                 // 可选：埋点
            await SendCoreAsync(ctx, ct);      // 业务/子类：真正发邮件/微信/站内信/调接口
            OnSucceeded(ctx);                  // 默认打 Info 日志
        }
        catch (Exception ex)
        {
            OnFailed(ctx, ex);                 // 默认打 Error；可 override 写库/告警/进补调
            // 不向分发器抛出 → 保证多通道失败隔离（场景 5）
        }
    }

    protected abstract Task SendCoreAsync(TaskNotifyContext ctx, CancellationToken ct);

    protected virtual void OnBeforeSend(TaskNotifyContext ctx) { }
    protected virtual void OnSucceeded(TaskNotifyContext ctx) { /* 结构化日志 */ }
    protected virtual void OnFailed(TaskNotifyContext ctx, Exception ex) { /* 结构化日志 */ }
}

// 业务侧极简
public sealed class WeComTaskNotifier : TaskNotifyChannelBase
{
    public override string Name => "biz.wecom";
    protected override Task SendCoreAsync(TaskNotifyContext ctx, CancellationToken ct)
        => _wecom.SendTodoCardAsync(Map(ctx), ct); // Map：开/关消息由 Kind 决定
}
```

骨架职责边界：

| 放在骨架（msg） | 留给业务 / 子类 |
|-----------------|-----------------|
| 统一入口、异常吞掉（隔离）、默认日志字段 | `SendCoreAsync` 通道协议 |
| `Kind` → 开/关消息语义约定（文档 + 辅助方法） | 模板文案、收件人扩展属性 |
| 可选：失败回调虚方法 / `ITaskNotifyFailureHandler` | 覆盖 `OnFailed` 写业务失败表 |
| 与 Outbox Worker 消费对接 | 具体 HttpClient / SDK |

与场景 4/5 关系：`DefaultMailTaskNotifier` 亦继承该骨架；多通道均走同一套日志与失败钩子，行为一致。

**包归属**：推送骨架与默认邮件放 **`sailflow.msg`**；Gate/Hook 契约与分发仍在 **engine**（§14.4 已决策）。

### 9.3 与现有 Subscribe 关系

| | Subscribe | Client Gate / Hook / Notify |
|--|-----------|---------------------|
| 生命周期 | 单次 Runner | Client 生命周期 |
| 过滤 | 无（本次全有） | Process / Activity 白名单或 All |
| 发送前拒绝 | 可抛错（语义弱） | **Gate + `HookResult.Reject`** |
| 补调 | 无 | Outbox 可选；推送失败也可业务自管 |
| 去留 | **保留** | 新增 |

迁移建议：宿主横切（含财务预校验）迁到 Client Gate/Hook；调用方临时逻辑继续 Subscribe。

### 9.4 包边界建议

| 内容 | 位置 |
|------|------|
| Gate / Hook / Notifier **契约**、注册表、分发器 | `engine`（必要时再抽 `sailflow.hooks`） |
| **待办推送骨架** `TaskNotifyChannelBase`、默认日志/失败钩子、`DefaultMailTaskNotifier`、`UseDefaultTaskMail` | **`sailflow.msg`（`src/core/ext/msg`）** |
| Outbox 存储 + Worker（若与通知共用） | 优先 `sailflow.msg`；或 engine 抽象 + msg 实现 |
| 企微 / 钉钉 / 站内信 / 业务 HTTP 通道 | 业务系统继承骨架；可选后续再下沉示例到 biz |
| 业务 Sync Hook / Gate | 业务系统程序集 |

**不把**通道 SDK（企微 SDK 等）塞进 engine；msg 只放骨架 + 默认同构能力（邮件可用 BCL/`System.Net.Mail` 或后续可替换实现）。

邮件：`TaskManager` 迁出 → msg 内 **`DefaultMailTaskNotifier`（继承骨架）+ `UseDefaultTaskMail()`**；**不**保留 `SendEmailFlag`。企微等与默认邮件同为列表中的独立 Notifier，且均建议继承骨架（场景 5 / 6）。

### 9.5 API 形态要点（已决策，详见 §14）

1. `ActivityCodes` 一等过滤；委托重载与 class 并存。
2. Sync 仅 FailFast；弱依赖 Async；首期注册 API 不暴露 `OnFailure`。
3. Gate / Async 禁止写变量；仅 Sync Hook 可写。
4. `IFlowGate` + `HookResult`；`WfExecutedResult` 用 `Failed` + `ValidationCode` / `ValidationDetails`。
5. 显式 `UseDefaultTaskMail()`；无 Flag 兼容。
6. 同名后注册覆盖 + Warning；多通道不同 Name；Notifier 失败隔离。

## 10. 安全与稳定性

- Sync Hook **禁止**长时间占用；需超时与（可选）电路熔断。
- Payload 脱敏：通知内容勿默认塞完整表单；Outbox 注意个人数据留存周期。
- 权限：补调 API 仅运维；Worker 使用专用凭证。
- 多租户：若未来多 `SailClient`，注册表必须在 Client 实例上，禁止静态列表。

## 11. 方案对比（决策记录）

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 只修 Subscribe + 文档 | 改动小 | 无全局注册/过滤/补调 | **否** |
| B. 单一 IEventHandler 全局列表 | 实现简单 | 推送与业务耦合；易误用 Sync | **否** |
| C. Hook + Notifier 双轨 + 白名单 + Outbox | 语义清 | 缺发送前 Gate / 结构化拒绝 | **否（不完整）** |
| C′. Gate + Hook + Notifier 三轨 + 白名单 + Outbox | 校验/业务/推送分离；可回前端 | 首期工作量更大 | **采纳** |
| D. 全部靠 MQ Topic | 天然异步 | 强一致与 Gate 难 | 仅作 Async 传输可选实现 |

**选定 C′**。Async 传输首期用**同库 Outbox**；已有 `sailflow.msg` 时可作通知渠道，但不强制业务钩子都进 RabbitMQ。

## 12. 分期实施建议（论证后的落地顺序）

> 本节是实施路线图；**在本文评审通过前不写业务代码。**

### Phase 0 — 文档与契约评审

- §14 **已决策**；进入 Phase 1 编码。
- 重构初期：**无**旧 API / Flag / Obsolete 兼容包袱。

### Phase 1 — 最小可用（MVP）

- engine：`IFlowGate` / `IFlowHook` / `ITaskNotifier` + 注册表 + ProcessCodes|ProcessIds|ActivityCodes 过滤。
- ProcessCode = **流程定义**唯一编码；由 `ProcessId(+Version)` 查定义并缓存填入上下文。
- **Run 路径：推进写库前调用 Gate**；`Reject` → `Failed` + `ValidationCode`/`Details` + 业务 `Message`（不包 `runprocess.error`）。
- `OnTaskCreated` 等正确拼写；`TaskManager` 创建/完成触发 Task 事件 / Notifier。
- Sync Hook 仅 FailFast；Notifier Async；**同库 Outbox 落表**（首选）。
- 默认邮件：仅 `UseDefaultTaskMail()`；删除 `SendEmailFlag` 发信路径；`TaskManager` 去掉直连 SMTP。
- 多 Notifier 列表 + `Order`；失败隔离；同名后覆盖 + Warning。
- 修复/收窄 `EventExecutor` 与文档一致。

### Phase 2 — 可靠异步 + msg 推送骨架

- Outbox Worker 完善；退避、死信、幂等。
- **【任务】`sailflow.msg`：内置待办推送实现骨架**（场景 6）
  - 新增 `TaskNotifyChannelBase`（或等价名）：统一 `NotifyAsync` 模板、结构化日志、`OnBeforeSend` / `OnSucceeded` / `OnFailed` 虚方法（或可注入 `ITaskNotifyFailureHandler`）。
  - 约定 `TaskNotifyKind` → 开消息 / 关消息辅助（文档 + 可选 `TaskNotifyMessageIntent`）。
  - `DefaultMailTaskNotifier` 继承该骨架；`UseDefaultTaskMail` 走骨架路径。
  - 保证骨架内异常默认不向外抛，满足多通道失败隔离。
  - 提供至少 1 个业务侧继承样例（文档或测试：伪微信 / HTTP 回调），证明业务只需实现 `SendCoreAsync`。

## 13. 验收标准（评审用）

1. 未注册任何 Gate/Hook/Notifier 时，主路径无推送、无钩子副作用（无 Flag 残留行为）。
2. 仅注册流程定义 Code=A 的 Hook 时，跑定义 Code=B **不进入**该 Hook。
3. Notifier 不因外部 HTTP 500 导致 `Run` 失败。
4. Sync + FailFast Hook 抛错时，流程事务回滚（有事务路径上）。
5. Outbox 在流程提交前写入；回滚后 Worker 不可见。
6. **Gate**：校验失败时**不推进**；`Message` + `ValidationCode`/`Details` 为业务拒绝文案，不包通用引擎错误壳。
7. **Gate 与汇总拆分**：Reject 时 Executing 汇总 Hook **不执行**。
8. **默认邮件**：仅显式 `UseDefaultTaskMail()` 才发；无 `SendEmailFlag`；不经 `TaskManager` 直连 SMTP。
9. **多通道**：失败隔离；同名后覆盖 + Warning。
10. **msg 骨架**：业务只实现 `SendCoreAsync`；失败默认记日志且不阻断其它通道。
11. 文档明确：Subscribe / BPMN Action / Client Gate·Hook·Notifier 职责边界。

## 14. 决策记录（已拍板）

> 重构初期：**不做**以往兼容、**不**使用 Obsolete / Flag 过渡。下列即为实施约束。

| # | 议题 | 决策 |
|---|------|------|
| 1 | Sync + RecordAndRetry | **禁止**。Sync **仅 FailFast**；弱依赖（含推送）**强制 AsyncOutbox**。首期注册 API **不暴露** `OnFailure`；推送失败用 msg 骨架 `OnFailed`。 |
| 2 | ProcessCode 来源 | **流程定义**的唯一编码（`ProcessEntity.ProcessCode` 等），**不是**流程实例字段。白名单配 `ProcessCodes` 和/或 `ProcessIds`。运行时用实例上的 `ProcessId(+Version)` **查定义并缓存**后填入上下文，供过滤与业务日志。 |
| 3 | Outbox | **Phase 1 同库落表**（首选）。内存队列仅测试。 |
| 4 | 程序集 | **推送骨架 + 默认邮件 → `sailflow.msg`**。Gate/Hook 契约与分发 **暂留 engine**；膨胀后再考虑 `sailflow.hooks`。msg 不承载 Gate。 |
| 5 | 变量写入 | Gate / Async **禁止**写变量；**仅 Sync Hook** 可写。 |
| 6 | ActivityCodes | **一等公民**过滤。 |
| 7 | 委托 `UseXxx` | 与 class 实现 **并存**。 |
| 8 | Gate | **`IFlowGate` + `HookResult`**；Reject 映射结果对象，不当事故异常、不包 `runprocess.error`。 |
| 9 | 校验回传 | `WfExecutedResult.Status = Failed`；新增 **`ValidationCode` / `ValidationDetails`**。首期 **不**新增 Status 枚举值。 |
| 10 | 默认邮件 | 仅 **`UseDefaultTaskMail()`**。**删除** `SendEmailFlag` 发信路径；无自动挂载、无 Obsolete。 |
| 11 | 同名注册 | **后注册覆盖**同名 + **Warning** 日志。多通道须不同 `Name`。 |
| 12 | Notifier 失败 | **隔离**：一通道失败不取消后续通道。 |

## 15. 宿主注册写法（最佳实践）

引擎提供 `UseFlowAspects`（总包）、`UseFlowGate` / `AddGate<T>`、`UseFlowHook` / `AddHook<T>`、`UseTaskNotifier` / `AddNotifier<T>`、`UseHookOutboxDrain` 的 **Builder + Collection** 双轨（Client 仍保留小写 `useFlowGate` 等）。宿主落地时：

| 推荐 | 避免 |
|------|------|
| `builder.UseMyHook()` / `builder.UseMyNotifier(sp)`，开关与建表在扩展内 | `Build()` 后大段 `if (enabled) { client.useTaskNotifier… }` |
| PostBuild 再 `new XxxService(client)` + 注册 | 在未 Build 时假装已有 `SailClient` |
| Notifier 启用时扩展内连带 Drain | 组合根另写一份 `if` 开 Drain |

全文：[最佳实践-宿主能力包UseXxx.md](./最佳实践-宿主能力包UseXxx.md)。宿主仓示例：`sleveen-admin/doc/sailflow-host-capability-pack.md`。

## 16. 总结

- 采纳 **Gate + Hook + Notifier 三轨**；主路径：**Validating → 落库推进 → Sync Hook → Outbox → 返回**。
- **ProcessCode = 流程定义唯一编码**；过滤与日志均基于定义（经 Id 解析缓存）。
- 内建邮件仅显式激活；**`sailflow.msg` 提供推送骨架**；多通道串行且失败隔离。
- 宿主挂载遵循 **能力包 UseXxx**（§15），与业务管道 Builder 一致。
- 重构无旧兼容包袱；§14 已决策；Phase 1–3b 已落地。
