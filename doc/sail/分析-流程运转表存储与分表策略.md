# 分析：流程运转表存储、分表与归档策略



> 状态：**策略已拍板，可开实施**（2026-11-01）；下文「待定」仅为实施参数，不挡开工  

> 场景假设：上报类流程，**数年运营、每年约 10 万次流程发起**；对照现场「约两年后待办/发送 3～7s」  

> 对照源：`sailflow` 引擎实体/Manager；`n_flowable` Activiti 形 RU/HI 历史策略  

> 关联：[特性说明-引擎能力基线.md](./特性说明-引擎能力基线.md)；对照仓 `bee-bpmn/nflow/n_flowable/doc/persistence.md`

## 0. 结论先行



| 维度 | 结论 |

|------|------|

| **Sail 现行模型** | **同表生命周期**：运行中与已结束共存于 `wf_*`；靠 `*_state` / `ended_*` 区分；**无**独立历史表 |

| **NFlow 对照模型** | **RU 热表 + HI 历史表**：结束实例从 RU 删除，审计/追溯写 HI；`history` 级别控制写入量 |

| **10 万次/年量级** | 5 年累计约 **50 万实例**；明细行级约 **数百万～千万**。热库**不必**分库；冷侧**首版按年分表并预留冷库** |

| **不建议照搬 HI 双写** | Sail 已在热表中保留全程轨迹；再抄 Activiti 双写会放大写入且改动引擎面大。更贴合的是：**热表只留活跃 + 近窗；冷数据迁归档表/分区** |

| **归档时机** | **办结不立刻迁表**；保留窗后定时迁（默认 30～90 天，覆盖办结后一周热查） |

| **轨迹/变量按流程分表** | **查询面适用、引擎成本偏高**；可作为 P2+ 局部优化，**不能替代**冷热归档，也**不宜**先于待办热表治理 |

| **对核心引擎影响** | 冷热分表后 **热路径不查归档** → 引擎推进/待办 **无需**附带分表路由（局部分表除外）；复杂度落在 **历史查询与归档作业/钩子** |

| **办结写归档扩展点** | 可用既有 **Hook**（建议 `OnProcessCompleted` + **AsyncOutbox**）注册独立归档逻辑，**不必改 Manager 核心**；热表删行仍建议保留窗后做 |

| **热表删除调度** | **Sail 内置可调用执行逻辑**（按保留窗迁出/删热表）；**默认由业务侧定时器唤起**；若需办结立刻执行则 **另挂 Hook 调同一套 API**（默认不挂） |

| **冷表形态（首版即定）** | **按年分表**（`*_hist_YYYY`）；路由键 `ended_datetime` 年；**预留冷库**（独立连接，热路径永不访问） |

| **引擎日志** | **契约化**；现行写 `wf_log`/`wf_job_log` 仅为**默认 Sink**；默认实现的**库位置、分表方式均可配置**；可替换为文件 / Host 日志等 |

| **首推路径** | P0 索引+分页+TTL → P1 按年冷表+冷库抽象+日志契约 → P2 热侧局部分表（暂缓） |

## 2. Sailflow：现行存储语义



### 2.1 运转相关表（热路径）



建表入口：`SailSchemaInitializer.EnsureCoreTables`。



| 表 | 实体 | 角色 | 结束时行为 |

|----|------|------|------------|

| `wf_process_instance` | `ProcessInstanceEntity` | 流程实例主记录 | `process_state`→Completed 等；写 `ended_*`；**行保留** |

| `wf_activity_instance` | `ActivityInstanceEntity` | 活动/节点实例（含会签子实例） | `activity_state`→Completed；**行保留** |

| `wf_task` | `TaskEntity` | 人工任务 | `task_state`→Completed/Closed/…；**行保留** |

| `wf_transition_instance` | `TransitionInstanceEntity` | 转移轨迹（偏追加写） | 不因完成删除 |

| `wf_process_variable` | `ProcessVariableEntity` | 运行变量（按 scope/name upsert） | 完成后仍留在表内；仅强制删除实例时级联删 |

| `wf_log` | `LogEntity` | 引擎异常日志（**默认 Sink**，契约见 §6.6） | 库/分表可配 |

| `wf_job_log` | `JobLogEntity` | 作业诊断日志（同日志契约） | 库/分表可配 |

| `wf_job_info` | `JobInfoEntity` | 定时/作业运行信息 | 作业生命周期 |

| `wf_hook_outbox` | `HookOutboxEntity` | Hook/Notify 异步投递 | Succeeded/Dead 可清理 |

| `sf_process_instance_copy` | `SailProcessCopyEntity` | 产品抄送（非引擎） | 随业务增长 |



定义类表（`wf_process`、`wf_variable`、`wf_rule_set`、表单等）体量与发起量弱相关，本文不展开。



### 2.2 状态机即「历史」



关键枚举：



- 流程：`ProcessStateEnum` — Ready=1 / Running=2 / Completed=4 / Suspended=5 / Canceled=6 / Discarded=7 / Terminated=8  

- 任务：`TaskStateEnum` — Waiting=1 / Reading=2 / Completed=4 / … / Closed=32 / Canceled=48  

- 活动：`ActivityStateEnum` — Ready=1 / Running=2 / Completed=4 / …



完成路径（摘要）：



- `ProcessInstanceManager.Complete`：同表更新状态与结束人时，不迁表。  

- `TaskManager.Complete`：`EndTaskState` 写 `task_state` + `ended_*`。  

- 删除：`ProcessInstanceManager.Delete` 仅在 **Canceled 或 isForced** 时级联删除 task / transition / activity / variable / instance；**正常办结不会自动物理删除**。



因此 Sail 的「历史」= **热表内的终态行**，不是第二套 schema。



### 2.3 查询面（与容量强相关）



`WorkflowQueryService` + 视图 `vw_wf_task_details`（task ⋈ activity ⋈ process_instance）：



- 待办/运行任务：过滤 `process_state=Running(2)` + `activity_state` + `task_state` 组合。  

- 已办列表实现上常落在「仍 Running 的流程内已完成活动/任务」；**跨年已结束实例的已办/追溯**最终仍要扫同一批 `wf_*` 大表。  

- 视图三表 JOIN 意味着：**任务表膨胀会直接拖慢待办**，除非索引能让优化器先收窄 `wf_task` / `process_state`。



### 2.4 变量与附属增长点



- `wf_process_variable`：同 key upsert，**非版本历史**；结束后仍占用行，且 `value` 可为大 JSON（AI `chat_history` 等场景会放大单行）。  

- `wf_transition_instance`：路径审计型追加，随退回/跳转增多。  

- `wf_hook_outbox`：成功行若不 TTL 清理，会与发起量近似线性增长。  

- `wf_log`：异常高峰时可能超过业务表写入。

## 3. NFlowable：历史表策略（对照）



### 3.1 模型



| 域 | 代表表 | 语义 |

|----|--------|------|

| 运行时 RU | `ACT_RU_EXECUTION` / `TASK` / `VARIABLE` / `IDENTITYLINK` / Job* | **仅活跃**；实例结束后从 RU 删除相关行 |

| 历史 HI | `ACT_HI_PROCINST` / `ACT_HI_ACTINST` / `ACT_HI_TASKINST` / `ACT_HI_VARINST` / … | 审计与列表追溯；持续膨胀 |

| 配置 | `history` = none / activity / audit / full | 控制 HI 写入粒度；生产慎用 `full` |



产品侧已体现：我发起的分页可走 `HistoryService`（含已结束），无历史则退回 Runtime（仅未结束）。见 n_flowable Host `BpmProcessRuntimeService.GetMyPage`。



运维共识（n_flowable `persistence.md`）：**定期归档 HI 表**；避免长期 `full`。



### 3.2 与 Sail 的本质差异



```text

NFlow:  推进中只碰 RU ──结束──► 删 RU +（按级别）落 HI

Sail:   推进与结束都在同一套 wf_* ──结束──► 改 state，行仍在

```



| 点 | NFlow RU/HI | Sail 同表 |

|----|-------------|-----------|

| 待办表体积 | 近似「在办存量」 | 「累计全历史任务」 |

| 已办/我发起 | 默认查 HI | 同表按 state 过滤 |

| 写入放大 | 生命周期双写（RU+HI） | 单写 + 更新 |

| 归档对象 | 主要是 HI | 必须按 **实例捆绑** 迁整组 `wf_*` |

| 引擎改造成本 | 已内建 | 若抄 HI 需大改 Manager/查询 |



**启发**：NFlow 的价值是 **热路径表永远瘦**；归档对象清晰。Sail 要达到同等效果，不必先造 HI，而应 **把终态数据移出热表（或分区冷区）**。

## 4. 容量估算（10 万次/年）



### 4.1 倍率假设（上报审批中位）



| 对象 | 每实例约 | 说明 |

|------|----------|------|

| 流程实例 | 1 | — |

| 活动实例 | 8～15 | 含网关、自动节点、会签子实例取中位 **10** |

| 任务 | 3～8 | 取 **5** |

| 转移 | 6～12 | 取 **8** |

| 变量行 | 10～40 | upsert 稳态；取 **20**（含表单/系统字段；AI 另计） |

| 抄送 | 0～3 | 产品侧；取 **1** |



### 4.2 年增量 / 5 年累计（量级）



| 表 | 年增量（约） | 5 年累计（约） |

|----|--------------|----------------|

| `wf_process_instance` | 10 万 | 50 万 |

| `wf_activity_instance` | 100 万 | 500 万 |

| `wf_task` | 50 万 | 250 万 |

| `wf_transition_instance` | 80 万 | 400 万 |

| `wf_process_variable` | 200 万 | 1000 万 |

| `sf_process_instance_copy` | 10 万 | 50 万 |



粗算行存储：若平均行 0.5～2 KB（变量/日志偏大），5 年引擎运转数据大约 **数 GB～十几 GB** 量级（未计大字段膨胀与索引）。对 SQL Server / PostgreSQL / MySQL 单库均可承载；瓶颈更可能是 **待办索引是否命中** 与 **大字段 I/O**，而非绝对行数。



### 4.3 在办存量（热数据）



若平均在办周期 3～14 天、并发在办占比约年发起量的 1%～5%：



- 在办实例：约 **1k～5k**  

- 在办任务：约 **数 k～2 万**



→ **热数据其实很小**；痛点是冷数据混在同表拖累过滤与 JOIN。

| # | 风险 | 影响 | 触发条件（本场景） |

|---|------|------|--------------------|

| R1 | 待办扫全历史 `wf_task` | 待办 P99 上升 | 无覆盖索引；视图 JOIN 先扫大表 |

## 6. 策略选项对比



### 6.1 选项总览



| 选项 | 做法 | 对引擎改动 | 热表瘦身 | 10 万/年适配度 |

|------|------|------------|----------|----------------|

| A. 索引 + 查询约束 | 覆盖待办/已办/实例条件；禁止无 state 的全表扫 | 极小 | 否 | **必做基线** |

| B. TTL 清理附属表 | Outbox Succeeded、过期 JobLog、低频 wf_log | 小（Host 作业） | 部分 | **必做** |

| C. 冷热归档表 | 终态实例捆绑迁入 `wf_*_hist` 或按年表 | 中（归档作业 + 查询路由） | **强** | **首推演进** |

| D. DB RANGE 分区 | 按 `created_datetime`/`ended_datetime` 年分区 | 小～中（DDL + 分区键约束） | 中（分区裁剪） | 库支持时可选 |

| E. Activiti 式 HI 双写 | 运行 RU 形表 + 历史 HI 形表 | **大** | 强 | 不推荐作为第一刀 |

| F. 应用分片（按年库/按租户库） | 多连接串路由 | 大 | 强 | 远超本场景；暂缓 |

| G. 热表局部按流程定义分表（仅轨迹/变量） | `wf_transition_instance_{process}` / `wf_process_variable_{process}` | **中～大**（Manager 动态路由） | 中（定义间隔离） | 查询面合适；**排在归档之后** |



### 6.2 选项 C 细节（推荐形态）



**归档时机：延迟定期，办结瞬间不迁。**



- 办结后约 **1 周内** 已办/详情仍常查 → 数据留热表。  

- **1～3 个月后** 极少再查 → 由定时任务迁出。  

- 默认保留窗建议 **90 天**（可配收到 30 天）；**禁止** Complete 事务内同步切表（拉长发送路径、干扰短窗撤回/复活）。



**归档单元 = 一个 `process_instance_id` 的闭包**：



1. 筛选：`process_state IN (Completed, Canceled, Discarded, Terminated)` 且 `ended_datetime < now()-保留窗`。  

2. 同事务或可重入批次：复制/移动  

   `wf_process_instance` → `wf_task` → `wf_activity_instance` → `wf_transition_instance` → `wf_process_variable`（及可选抄送）。  

3. 热表删除对应行（或先软标记再删）。  

4. 查询路由：  

   - 待办/在办：**只查热表**；  

   - 已办/详情/监管：热表 UNION 归档表，或 Host 按时间窗分流。



与 NFlow 的对应关系：归档表 ≈ HI；热表 ≈ RU。差别是 **异步迁出** 而非引擎内同步双写。



#### 6.2.1 对核心引擎的影响面（可确认）



| 层次 | 冷热分表后是否加分表/双读逻辑 |

|------|------------------------------|

| Run / 发送 / 待办（热路径） | **否**（只碰热表；与「局部分表」无关时引擎零路由） |

| 已办 / 详情 / 监管（历史路径） | **是**（热 ∪ 归档，或按时间窗路由）— 宜落 Host / `WorkflowQueryService` |

| 归档写入本身 | **不必改引擎核心**；挂 `IWorkflowHook` 即可 |



办结时刻若要 **写入归档表**（副本或预归档）：



- 扩展点已具备：`EventFireTypeEnum.OnProcessCompleted` + `RegisterHook`（见 `特性设计-回调与事件.md`）。  

- **推荐 AsyncOutbox**：同事务只落 Outbox，Worker 再拷闭包 → 不拖长 Complete/发送 P99。  

- **Sync Hook + FailFast** 仅适合极轻标记；全量拷贝变量/轨迹不宜同步。  

- 重要区分：**「办结写入归档」≠「热表已瘦」**。热路径要瘦，仍须在保留窗外 **删热表行**（或迁出）；仅双写会使存储加倍，待办仍可能被热表内终态行拖累。  

- 短窗撤回/复活：若已预写归档，钩子或作业需可重入（覆盖写 / 按 instance 幂等），避免双份脏数据。



#### 6.2.2 热表删除：内置逻辑 + 业务定时唤起（已拍板形态）



职责切开（与现有 Hook / Host 定时模式一致）：



| 层 | 职责 |

|----|------|

| **Sail 侧（内置）** | 提供可调用的归档/清热表执行体：按保留窗筛选终态闭包 → 写入归档（若尚未有）→ 删热表行；批大小、幂等、可重入、失败可续跑 |

| **业务 / Host 侧** | **默认**：定时器（Hangfire / 系统作业等）周期性唤起上述 API；配置保留窗与批次 |

| **可选 Hook** | 仅当某流程需要「办结立刻迁出/删热」时，注册 `OnProcessCompleted`（优先 AsyncOutbox）**调用同一套 API**（如 `retention=0` 或针对当前 `process_instance_id`）；**产品默认不注册** |



因此：



- 核心推进路径仍不内嵌「删热表」；定时与立刻两条入口 **复用同一执行逻辑**，避免两套迁出代码。  

- 「立刻」走钩子时仍避免在 Complete 同步事务里做重拷贝；Outbox 消费再调内置 API。  

- 默认定时 + 保留窗，覆盖「办结后一周仍热查」；立刻模式留给特例白名单流程。



#### 6.2.3 冷表按年分表 + 预留分库（首版策略，避免几年后打补丁）

**判断：同意。冷路径按年拆应在 P1 一次性定死；热表保持单表。**

理由：

- 冷数据按自然年增长，体量与运维（备份、清理、只读库）都按年切最顺。  

- 历史查询几乎总能带时间窗或 ended_datetime → 可定位到 1～N 张年表，**无需**扫全部历史。  

- 热路径仍零感知；复杂度只在归档写入与历史读路由。  

- 「几年后再分区/再拆表」成本远高于首版就按年建表模板。

**命名约定（示例）**：

| 热表 | 冷表（按办结年） |

|------|------------------|

| wf_process_instance | wf_process_instance_hist_2026 |

| wf_task | wf_task_hist_2026 |

| wf_activity_instance | wf_activity_instance_hist_2026 |

| wf_transition_instance | wf_transition_instance_hist_YYYY |

| wf_process_variable | wf_process_variable_hist_YYYY |

- 年取自实例 **ended_datetime 的日历年**（整闭包同一年后缀，避免同实例拆到两年）。  

- 跨年保留窗边界：以 ended 年为准写入对应年表即可。  

- 新年自动 ENSURE TABLE（与现有 createTable/Initializer 同风格）；旧年只读。

**冷库（分库）预留**：

| 阶段 | 做法 |

|------|------|

| 首版 | 归档 API / 历史查询经 **IColdStore（或第二 DBLive/连接名）** 访问；默认可仍指向主库 |

| 扩容时 | 仅改冷库连接串，把按年冷表放独立库/只读副本；**热库与热路径代码不动** |

| 约束 | 热→冷为 **异步迁出**（非分布式事务）；冷库故障不得阻断 Run/待办 |

**历史查询路由**：

1. 待办/Run：只热库热表。  

2. 已办/详情：先热表；未命中再按 ended 年（或查询时间窗展开的年份集合）查冷表。  

3. 跨多年报表：显式年份列表 UNION，禁止无时间条件的全冷库扫。

相对「单张 wf_*_hist + 以后再分区」：按年物理表在运维上更直观（整年 detach/备份/删），且与「可分库」同一套路由抽象。

### 6.3 选项 D 细节（分区）



- 适合：SQL Server / PostgreSQL / MySQL 8 分区表。  

- 建议分区键：`created_datetime`（或 `ended_datetime`，但进行中行为 NULL 时不利）。  

- 待办过滤若带 `process_state=Running`，仍需 **局部索引**（或热表不分区、仅归档表分区）。  

- 注意：`vw_wf_task_details` 在分区表上要验证分区裁剪是否生效。



### 6.4 为何不优先 E（HI 双写）



1. Sail 完成路径是 Update state，不是 Delete runtime；改成 RU 删除会触及退回/撤回/复活（Reverse）等语义。  

2. 已办与轨迹产品已依赖同表字段；双源易不一致。  

3. 10 万/年写入压力不足以证明双写收益。  

4. 若未来要 HistoryService 形 API，可用 **归档表只读适配** 冒充 HI，而无需运行期双写。



### 6.5 选项 G：轨迹 / 变量「热表按流程定义分表」是否适用



**结论：查询语义上较适用；作为架构默认项不适用；仅在归档+索引仍不够、且单定义流量极不均衡时局部启用。**



#### 6.5.1 为何「比 task 更适合」



Sail 现行访问几乎都是 **实例内 / 定义内**，没有待办那种「按人跨所有流程聚合」：



| 表 | 典型访问 | 是否跨流程定义聚合 |

|----|----------|--------------------|

| `wf_task` / 待办视图 | `assigned_user_id` + 多定义 | **是** → 按定义分表会迫使待办 UNION |

| `wf_transition_instance` | `process_instance_id` / `app_instance_id+process_id`；网关计数、上一跳、轨迹图 | **否**（代码路径均带 process/instance） |

| `wf_process_variable` | `process_instance_id` + name（及 activity） | **否** |



源码侧：`TransitionInstanceManager.GetTransitionInstanceList`、`GetWorkItemTransitonInstance`、网关分支统计；`ProcessVariableManager.GetVariable*` / `SaveVariable` 均以实例为键。因此「只对轨迹+变量按 `process_id` 分表、task/instance 仍单表」在 **查询形状** 上说得通。



#### 6.5.2 仍要注意的成本与陷阱



| 点 | 说明 |

|----|------|

| 引擎改动面 | 所有 Insert/Select/Delete 需 `process_id → 物理表` 路由；`NodeMediator`、删除级联、子流程（父子不同 `process_id`）同一事务跨表 |

| `GetById(id)` | 仅有自增 Id、无 `process_id` 时无法定位分表 → 需路由元数据、或 Id 含分片信息、或保留全局定位索引 |

| 表爆炸 | 定义多、启停频繁时建表/迁移/权限运维成本上升 |

| 与归档正交 | 分表只隔离「定义 A 与定义 B」；**同一热门定义**上冷行仍堆积，两年后该分表照样肥 → **不能替代延迟归档** |

| 对「待办 3～7s」 | 待办慢在 task/视图路径；轨迹分表 **几乎不直接治愈待办**，只减轻发送时读变量/写转移的大表压力 |

| PK / 监控 | 多分表 identity 不宜直接 UNION；监控要从「一张表行数」改为「分表汇总」 |



#### 6.5.3 更轻的替代（多数情况优先）



在仍用单表的前提下，这两张表用好下面两招通常足够：



1. **必建** `(process_instance_id)` / `(process_instance_id, name)` 窄索引（推进与详情都是点查）。  

2. **延迟归档** 把终态闭包（含轨迹、变量）迁出热表 → 热表行数≈在办+近窗，与「按定义拆表」目标重叠且改动更小。  

3. 若单定义变量极大：优先 **大字段外置**（chat_history 等），而不是先拆表。



#### 6.5.4 何时才值得做 G



同时满足再考虑：



- P0+P1 已落地，热表仍因 **某一两个定义** 的轨迹/变量行数过高导致 Run/详情 P99 差；且  

- 该定义占写入量明显头部分布（例如 >50%）；且  

- 愿意承担 Manager 动态表名与子流程路由测试。



落地形态建议：**白名单制**——仅对头部 `process_id` 建 `wf_transition_instance__{code}` / `wf_process_variable__{code}`，其余仍走默认单表；避免「每个定义一张表」一刀切。

   - `wf_task(assigned_user_id, task_state, process_instance_id)` — 待办按人

3. 变量治理：限制大 JSON 入 `wf_process_variable`（外置对象存储 / 截断 chat_history）。



### P1 — 附属清理 + 归档作业（建议 1 年内有）



1. Outbox：Succeeded/Dead 超 N 天删除或迁审计库。  

2. `wf_log` / `wf_job_log`：按时间滚动清理。  

3. **实例归档作业**（选项 C）：保留窗外终态捆绑迁出；Host 已办/详情加归档读路径。  

4. 监控：热表行数、待办 P95、归档滞后天数。



### P2 — 物理隔离增强（可选，二选一或组合）



- **按年 RANGE 分区**：归档表或仍偏大的热明细表；运维友好。  

- **选项 G（轨迹/变量按定义分表）**：仅在头部流程写放大、且已确认无跨定义查询债时白名单启用；**task / process_instance 仍单表**（待办聚合不能拆）。  

- 10 万/年 × 5 年在做好 P0+P1 后，多数部署 **用不到 P2**。



### P3 — 产品级 History API（可选）



- 若要对齐 n_flowable「Runtime vs History」产品语义，用归档表实现只读 History Facade，**仍避免引擎内双写**。

## 9. 决策建议（给实施）



在 **每年 10 万发起、数年**，且现场已出现「两年后待办/发送 3～7s」类症状的前提下：



1. **现在**：P0 索引 + 待办库端分页 + Outbox/Log TTL；**不要**上分库，**不要** HI 双写，**不要**先做全量按流程分表。

2. **归档**：办结不切表；**保留窗后定时迁**（默认 90 天，可配 30～90）。这是热路径与历史行数解耦的主杠杆。

3. **轨迹/变量按流程分表**：承认「无跨流程查询」前提成立，但定位为 **P2 白名单增强**；不能代替归档，也不能解决待办聚合表膨胀。

4. **task / process_instance / activity_instance**：保持单热表 + 归档；待办必须跨定义。

5. 量级到 **百万发起/年** 或头部定义独占写放大时，再评估 G 或独立历史库。

## 6.6 引擎日志：契约 + 默认可配置写表（已拍板）



与流程冷热归档**分开**：日志不是流程实例闭包的一部分，但必须避免与业务热表同库无限膨胀。



### 现状（代码）



- LogManager → 硬编码异步 Insert wf_log（引擎同库）。

- LogService → 硬编码 Insert wf_job_log。

- **无**可替换 sink；Initializer 默认建表。



### 目标形态



`

引擎调用点（RecordLog / RecordErrorLog…）

        ↓

   IEngineLogSink（契约，Client 可注入）

        ↓

   ┌────────────────默认实现（可配）──────────────┐

   │  TableLogSink：写库表                         │

   │    - Connection / 库名可配（可与热库分离、可 SQLite）│

   │    - 分表策略可配：单表 | 按月 | 按年（如 wf_log_2026）│

   │    - TTL / 保留窗可配                         │

   └─────────────────────────────────────────────┘

        ↓ 亦可注册

   FileLogSink / HostILoggerSink / 时序或其它自定义

`



| 原则 | 说明 |

|------|------|

| 契约优先 | Manager 只依赖 sink；禁止再写死 useRepo<LogEntity>().Insert |

| 写表=默认 | 开箱与今行为兼容；**不是**唯一路径 |

| 默认可配 | 写哪个库、表名模式、是否按年/月分表、保留天数 → Options |

| 不挡主路径 | 保持异步/失败吞掉；与现 Hook Outbox 哲学一致 |

| 与流程冷表无关 | 日志分表/分库 **不**走流程实例归档 API |



默认建议（实施时可配）：日志库可与热库分离；分表默认 **按月或按年**；保留 **30～90 天** 后删或弃年表。







## 6.7 性能分表参数：Client Options（已落地骨架）



与 SailConfig / HookOutboxOptions 同模式：



- 默认：client.DataLifecycleOptions（保留窗 90 天、冷库同库、日志按月 Table Sink）

- Builder：`builder.UseDataLifecycle(o => { ... })`

- 运行期：client.useDataLifecycle(...)

- 配置文件：宿主 Bind 节（如 Sail:DataLifecycle）后传入；引擎不读 IConfiguration



类型：SailDataLifecycleOptions。后续归档 API / Log Sink 必须读该 Options。
