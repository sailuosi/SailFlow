# 专题 · 对象生命周期与复用边界

> 状态：**讨论草案 / 未定型**（2026-11-06）  
> 用途：先立「类必须有明确寿命档位」的设计思想与利弊；再给引擎关键类型**拟定位**表，供评审拍板。**禁止**在未定型前大范围改 `new XxxManager(client)` 等调用形态。  
> 关联：[架构设计-项目依赖与分层.md](../架构设计-项目依赖与分层.md) · [业务管道特性设计.md](../业务管道特性设计.md) · [开发手册-OA命令执行链路.md](./开发手册-OA命令执行链路.md) · [特性设计-回调与事件.md](../特性设计-回调与事件.md) · [草案-引擎异步化.md](../草案-引擎异步化.md)  
> 触发背景：办理链路上大量 `new ActivityInstanceManager(client)` 等；`client` 为应用单例、Manager 仅持 Client → 语义上无请求态，但**寿命档位从未立法**。

---

## 1. 一句话

**设计一个类时，必须同时定死其生命周期档位**（应用单例 / 请求壳 / 命令次级 / 瞬时门面等）。寿命含糊时，后续加缓存、关联 Id、租户、指标都会把状态塞错层，比「多几次 `new`」危险得多。

本稿只定思想与拟定位；**定型 → 再改代码**。

---

## 2. 为什么要立法（问题）

### 2.1 现状症状

```text
SailClient          ← Host AddSingleton（应用单例，契约相对清楚）
WorkflowService     ← Host AddScoped，但内部 _wfAppRunner 可变（壳与命令态叠在一起）
*Manager(client)    ← 仅持 Client，却处处 new；Mediator 内又懒缓存同寿于一次 Execute
WfRuntimeManager*   ← 按次 new，持 Runner / 结果（命令次级，合理）
NodeMediator*       ← 按次 new，持 Kit / LinkContext / Runner 上下文（命令次级，合理）
SQLBuilder kit      ← 命令入口 beginTransaction，参数下传（调用/事务级，合理）
```

同一类型（如 `ActivityInstanceManager`）出现两种叙事：

- Factory / Service：**瞬时** `new`；
- `NodeMediator`：**与本次 Mediator 同寿**的懒字段。

两边都不「错」，但**没有统一立法** → 新人无法判断「能不能在 Manager 上加实例缓存 / 当前用户」。

### 2.2 含糊寿命的典型后果

| 后续想加的能力 | 若误当应用单例 | 若误当瞬时且又加了字段 |
|----------------|----------------|------------------------|
| 请求 Correlation / User | 串请求、数据串户 | 字段写了却每次 new 丢掉，或半缓存半不缓存 |
| 定义/上一跳缓存 | 未做线程安全则竞态 | 缓存永远冷启动，行为不一致 |
| 指标 / 诊断计数器 | 全局累加 OK；若夹带请求维度则脏 | 无法挂稳定计数器 |
| 非线程安全懒资源（类旧 `ManagerBase.Repository`） | 多线程炸 | 「偶发」复用路径才炸，更难查 |

根因不是性能，是**依赖方向与状态归属失去裁决标准**。

## 3. 设计思想

### 3.1 原则

1. **一类一档**：每个对外/对内核重要的类型，在文档（定型后可到类注释）写明寿命档位；新增类型评审时必问「同寿于谁」。  
2. **依赖只指向更长寿或同寿**：短寿对象可持有长寿引用；**禁止**长寿对象持有短寿可变态（Runner、kit、LinkContext、HTTP User）。  
3. **状态跟寿命走**：请求态 → 请求/命令对象；应用配置与无请求门面 → 应用单例。  
4. **立法先于优化**：先选档位并写红线，再谈挂在 `SailClient` 上还是 DI `AddSingleton`；禁止「先到处复用再补契约」。  
5. **与分层正交**：程序集分层（pure/ext/biz）回答「代码放哪」；本文回答「实例活多久」——二者同时约束演进。

### 3.2 寿命档位（词汇表）

| 档位代号 | 含义 | 同寿于 | 典型例子（拟） |
|----------|------|--------|----------------|
| **L-App** | 应用单例 | 进程内一个 `SailClient`（或等价 Host 根） | `SailClient`、拟挂载的无状态 `*Manager`、Assignee 管道骨架 |
| **L-Scope** | 宿主请求壳 | ASP.NET Scope / 一次 Host 解析 | `IWorkflowService` 注册形态（见 §5 争议） |
| **L-Cmd** | 办理命令次级 | 一次 `Start/Run/…` 的 Execute 链（含事务与实例锁） | `WfRuntimeManager*`、`NodeMediator*`、`WfAppRunner`（入参）、一次事务的 `kit` |
| **L-Call** | 调用/语句级 | 单次 SQL / 单次 Sibling | `SailSqlAccess.Sibling(kit)` 产出的临时 builder |
| **L-Ephem** | 瞬时门面（可选档） | 任意次构造、无实例状态、禁止加字段缓存 | *仅当*明确拒绝应用单例时使用；与「处处 new」对齐但**写死红线** |

**推荐默认**：无请求态、只依赖 `SailClient` 的数据门面 → **L-App**，而不是长期停留在未立法的 L-Ephem。

### 3.3 依赖方向（硬边界）

```text
L-App  ─────────────────────────────────────────────► 最长寿
  ▲ 可依赖
L-Scope（可选壳）
  ▲ 可依赖
L-Cmd（Runner / Runtime / Mediator / 事务 kit）
  ▲ 可依赖
L-Call
```

禁止箭头向上「吸」短寿状态进 L-App。

```text
┌─ L-App：SailClient +（拟）Managers / 管道插槽 ─────────┐
│  无 Runner、无 kit 字段、无 HTTP User                   │
└───────────────────────────┬───────────────────────────┘
                            │ 注入 / 属性读取
┌─ L-Scope：WorkflowService（Host Scoped）──────────────┐
│  可持 Sail；_wfAppRunner 视为 L-Cmd 态（见开放问题）   │
└───────────────────────────┬───────────────────────────┘
                            │ 一次动词
┌─ L-Cmd：Factory → Runtime → Mediator + kit 事务 ──────┐
│  可 new；可懒持 L-App 门面；结束即弃                    │
└───────────────────────────────────────────────────────┘
```

## 4. 利弊（选型时对照）

### 4.1 将无状态 Manager 定为 L-App（推荐方向）

| 利 | 弊 |
|----|----|
| 寿命与「只依赖 Client」语义一致；Mediator/Factory 叙事统一 | 改动面：调用点从 `new` 改为 Client 门面或注入 |
| 后续横切（只读缓存、指标）有合法挂点，且强制线程安全评审 | 误加请求字段会造成全局事故（需红线 + Code Review） |
| 与 Host `SailClient` Singleton 自然对齐 | 测试需可替换 Client / 门面，避免隐式全局 |

### 4.2 将 Manager 明定为 L-Ephem（处处 new）

| 利 | 弊 |
|----|----|
| 零装配、现状改动小；「绝无实例缓存」简单粗暴 | 横切能力无处安放，只能堆到 Client / 静态 / 管道 |
| 不会出现 Singleton 吸请求态 | 与 Mediator 懒缓存矛盾，需同时改掉懒字段或承认「例外」 |
| | 新人仍易在「临时对象」上加字段，债换皮不换骨 |

### 4.3 WorkflowService：Scoped 壳 + 命令态 Runner

| 利 | 弊 |
|----|----|
| 链式 `CreateRunner…Start()` 方便 | `_wfAppRunner` 使「Scoped ≠ 无状态」；不可升 L-App |
| 与 ASP.NET 请求边界大致同寿 | 同 Scope 内并发调两个动词会踩 Runner（开放问题） |

### 4.4 Runtime / Mediator：坚持 L-Cmd

| 利 | 弊 |
|----|----|
| 天然隔离一次办理的图推进状态 | 每次分配；相对 DB 可忽略 |
| 不会把 AI/Task 中间态泄漏到全局 | 禁止「缓存 Mediator 跨请求」 |

**结论倾向（待拍板）**：Manager 类 → **L-App**；Runtime/Mediator/kit → **L-Cmd**；`WorkflowService` → **L-Scope 壳 + 内部 L-Cmd Runner**（或远期收敛链式态）。

## 5. 架构落位（与分层、管道的关系）

| 主题 | 关系 |
|------|------|
| 程序集分层 | pure 内可同时存在 L-App 与 L-Cmd 类型；寿命 ≠ 包边界 |
| `SailClient` / UseXxx | L-App 能力的组合根；Manager 若 L-App，优先挂 Client 门面，避免第二套 Service Locator |
| Gate / Hook / Notifier | 注册在 Client（L-App）；**调用上下文**（kit、Runner）由 L-Cmd 每次传入 |
| 事务约定 | 无事务 `UseRunSQL()`；有事务只认入口灌入的同一 `kit`（已有 Client 注释）——kit 永不为 L-App 字段 |
| DI | Host 对 `SailClient` Singleton、`IWorkflowService` Scoped 已存在；引擎内核**不强制**把每个 Manager 再注册进 MS.DI，避免双轨；定型后二选一写清 |

## 6. 相关类型：现行用法 vs 拟定位

> **拟定位**为讨论稿，定型前不得当实施依据。  
> **现行**：代码真实用法；**红线**：该档位下禁止事项。

### 6.1 应用根与管道（L-App）

| 类型 | 现行 | 拟定位 | 定位说明 / 红线 |
|------|------|--------|-----------------|
| `SailClient` | Host Singleton | **L-App** | 运行根；挂 Dialect、管道、UseXxx。禁止持本次 Runner/kit |
| `IAssigneePipeline` 及已注册 Resolver/Filter | 挂在 Client | **L-App** | 无请求字段；解析入参每次传入 |
| `FlowCapabilityDispatcher` / Gate·Hook 注册表 | 挂在 Client | **L-App** | 执行时 ctx/kit 由命令传入 |
| `InstanceExecutionLock` 相关 | 应用级字典 + 可选 Cleaner | **L-App**（机制） | 锁 key 来自 Runner，机制本身应用级 |

### 6.2 数据门面 Manager（争议焦点 → 拟 L-App）

| 类型 | 现行 | 拟定位 | 定位说明 / 红线 |
|------|------|--------|-----------------|
| `ActivityInstanceManager` | 处处 `new`；Mediator 懒缓存 | **L-App** | 仅 `Sail`；CRUD 一律 `kit` 或临时 `UseRunSQL()`。禁止实例缓存未评审线程安全 |
| `TaskManager` | 同上 | **L-App** | 同上；`Transfer` 等写操作仍吃传入 kit |
| `ProcessInstanceManager` | 同上 | **L-App** | 同上 |
| `TransitionInstanceManager` | 同上 | **L-App** | 同上 |
| `ProcessManager` | 同上 | **L-App** | 定义读取；可日后挂定义只读缓存（须定型后） |
| `ProcessVariableManager` / `VariableManager` | `new(client)` | **L-App** | 同上 |
| `HookOutboxManager` | `new(client)` | **L-App** | InsertPending 吃 kit；Worker 侧另议 |
| `JobInfoManager` / `LogManager` / `RuleSetManager*` | `new(client)` | **L-App** | 同门面族 |
| `ProcessVariableResolver` | `new(client)` | **L-App** 或并入门面 | 无请求字段则随 Manager 族 |

**装配形态（定型后二选一，本稿不拍）**：

- A. `SailClient` 懒属性：`client.Activities` / `client.Tasks` / …  
- B. Host `AddSingleton` 各 Manager，Service/Factory 构造注入  

内核调用点统一禁止散落 `new XxxManager(Sail)`（测试可例外）。

### 6.3 解析 / 辅助（拟随门面）

| 类型 | 现行 | 拟定位 | 说明 |
|------|------|--------|------|
| `PreviousStepChecker` | `new(client)` | **L-App** | 仅 Client；内部勿存 kit 字段 |
| `NextStepParser` / `SignForwardStepMaker` | `new(client)` | **L-App** | 同上 |
| `ProcessModelFactory` | 静态工厂 | **L-App 工具**（静态可保留） | 产出的 `IProcessModel` 多为 **L-Cmd** 使用期缓存 |

### 6.4 命令入口与壳

| 类型 | 现行 | 拟定位 | 说明 |
|------|------|--------|------|
| `IWorkflowService` / `WorkflowService` | Scoped + `_wfAppRunner` | **L-Scope 壳**；Runner **L-Cmd** | 开放：是否取消字段 Runner、改为纯参数入参 |
| `WorkflowQueryService` 等 Host Scoped | Scoped + Client | **L-Scope** | 无 Runner 字段则更干净 |
| `WfRuntimeManagerFactory` | 静态类 | **L-App 工具**（静态） | 内部应取 L-App Manager，而非每次 `new` |
| `NodeMediatorFactory` | 静态 | **L-App 工具** | 产出 **L-Cmd** Mediator |

### 6.5 办理命令次级（L-Cmd）— 必须按次创建

| 类型 | 现行 | 拟定位 | 红线 |
|------|------|--------|------|
| `WfAppRunner` | 入参 / 链式写入 | **L-Cmd** | 不进 Client 字段 |
| `WfExecutedResult` | 按次 | **L-Cmd** | — |
| `WfRuntimeManager` 及 Run/Startup/SendBack/… | 按次 `new` | **L-Cmd** | 禁止跨请求复用 |
| `ActivityForwardContext` / `BackwardContext` / `SendBackOperation` | 按次 | **L-Cmd** | — |
| `NodeMediator` 及派生 | 按次；内懒 Manager | **L-Cmd** | 可持 L-App Manager 引用；弃用「为缓存而 new 的私有 Manager」当寿命叙事 |
| `NodeSendBack*` | 按次 | **L-Cmd** | 同上 |
| `ActivityResource` | 按次 | **L-Cmd** | — |
| 入口 `SQLBuilder kit`（事务根） | 按次 | **L-Cmd** | 不赋给 L-App |

### 6.6 调用级（L-Call）

| 类型 | 现行 | 拟定位 | 说明 |
|------|------|--------|------|
| `SailSqlAccess.Sibling(kit)` 结果 | 临时 | **L-Call** | 同事务、短用 |
| mooSQL `useRepo` / `useClip` 句柄 | 临时 | **L-Call** | 勿存 L-App |

### 6.7 Host 侧（对照，非引擎内核）

| 类型 | 现行 | 拟定位 | 说明 |
|------|------|--------|------|
| `SailOperationDispatcher` / Handlers | 通常 Singleton/Scoped | **L-Scope 或 L-App**（无状态则 App） | Handler 只调 `IWorkflowService`，不持 Runner 字段 |
| `Wf2XmlController` | 请求级 | Host 请求 | — |

## 7. 与 OA 命令链的对照（读法）

```text
ButtonsOperation（Host 请求）
  → WorkflowService（L-Scope 壳）
      → kit + Lock（L-Cmd）
      → Factory（静态工具）用 L-App Manager 读库
      → Gate（L-App 注册，L-Cmd 上下文）
      → WfRuntimeManager*（L-Cmd）
          → NodeMediator*（L-Cmd）→ 写库经 L-App Manager + L-Cmd kit
      → Hook（同上）
```

链路文档见 [开发手册-OA命令执行链路.md](./开发手册-OA命令执行链路.md)；**寿命标签以本专题定型结果为准**回写该手册。

## 8. 开放问题（讨论清单）

1. Manager 挂载：**Client 懒门面** vs **MS.DI Singleton** vs 两者只保留其一？  
2. `WorkflowService._wfAppRunner`：保留链式 DX，还是收敛为「纯方法参数」、壳真正无状态？  
3. Mediator 内懒 `new Manager`：定型 L-App 后改为读 `Sail.Xxx`，删除「半同寿」叙事？  
4. `ProcessModel` / XPDL 解析结果：L-Cmd 持有还是允许 L-App 带失效策略的定义缓存？  
5. 旧 `ManagerBase.Repository`：引擎路径是否已完全脱离；若残留，寿命与线程安全如何收口？  
6. 测试与多 `SailClient`（多租户/多库）场景：L-App 是否严格「每 Client 一套 Manager」？
