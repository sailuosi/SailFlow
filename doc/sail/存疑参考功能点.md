## 1. AntFlow「承办」——或签先认领再审批

| 项 | 内容 |
|----|------|
| 来源 | AntFlow.NET · `ProcessOperationEnum.BUTTON_TYPE_UNDERTAKE` · `UndertakeProcessService` |
| 对照日 | 2026-11-01 |
| 建议态度 | **不跟产品按钮**；若要独占，挂 `Leave=Race` 的 UX/可选认领命令，勿做成可绕过会签的全局按钮；候选编码见 OA 要素文档 `Claim` |

### 1.1 对方实际语义（源码）

触发条件（`BpmVariableSignUpService.IsMoreNode`）**同时**满足：

- 当前节点多人人员记录且 `UndertakeStatus` 为空或 `0`
- 过滤后人数 `> 1`
- **`SignType == 2`（或签）**

此时办理条：`auditButtons.Clear()`，**只剩「承办」**（同意/驳回等先不给）。

点承办（`UndertakeProcessService`）做的事：

1. 删掉同实例下其他人的代理待办  
2. 将多人变量 `UndertakeStatus` 置 `1`（且代码路径偏或签）  
3. 将 execution `TaskCount` 收成 `1`  
4. **不推进流程**——认领后 `IsMoreNode` 变 false，再露出正常审批按钮  

会签 / 顺序会签：**不出现**承办。

### 1.2 为何存疑

| 观感 | 说明 |
|------|------|
| 像「越过办理模式」 | 机制上先强行删人、收成单人，再审批，看起来像 Leave 短路 |
| 实际意图更窄 | 只服务**或签**的两段式：**先 Claim，再 Agree/Reject**，不是通用「无视会签」开关 |
| 与「办完即离开」重叠 | 或签本就可在同意时清掉他人任务；承办把「独占」拆成显式按钮，多一步 UX |
| 命名易误解 | 「承办」在公文语境常指主办单位/主办人，与「抢办认领」不完全同义 |

意图可概括为：

```text
或签多人 → [承办：独占] → [同意/驳回：按或签离开]
会签 / 顺序会签 → 不走承办
```

### 1.3 与 Sail 对照

| Sail | 关系 |
|------|------|
| Leave `Race`（抢办） | 概念最近：谁办完（或谁认领）谁独占离开 |
| Leave `Collaborate` / 会签路径 | **不应**被「承办」类按钮绕过 |
| 按钮码表 | 刻意未进转办/委派；承办同属「未澄清前禁止空壳」类 |
| 产品缺口 | 若业务要「打开表单前先锁人」，应设计为 **Race 可选认领命令**，并写清仅 Race 可见 |

**结论：** AntFlow 的承办不是「越过任意办理模式」，而是或签 Claim 前置；对 Sail 仍属**怪异 UX 拆分**，默认不抄按钮名与全局语义，避免和 Resolve×Leave 正交模型打架。

### 1.4 若未来要做（可选草案，非承诺）

- 仅当节点 Leave=`Race`（或等价或签）时，Host 可提供「认领」  
- 认领 = 取消/关闭同活动其他待办 + 审计；**不等于** `RunProcess`  
- Collaborate / 会签 / 队长：**永不**露出认领  
- 禁止做成「任意节点可点、点完变单人」的万能按钮
