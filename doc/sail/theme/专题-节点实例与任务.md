## 0. 结论先行

| 项 | 口径 |
|----|------|
| **ActInstance** | 流程跑到某个 BPMN **活动/节点**时的一次激活（令牌落点）；表 `sf_act_instance` |
| **Task** | 该活动下按 **办理对象**拆分的人工待办/工作项；表 `sf_task` |
| **外键** | `sf_task.tk_act_instance_id` → `sf_act_instance.ai_id` |
| **基数** | **ActInstance : Task = 1 : N**（常为多，亦可 0）；**不是**严格一对一 |
| **≈1:1** | 仅单办理人、且无沟通/代批并人时的常见特例，非引擎硬约束 |
| **结构 A 扁平** | 一 AI 下多 Task（普通多人用户任务 + Leave） |
| **结构 B 主/子** | 主 AI 容器 + 每人（根席）子 AI（+Task）：`SignTogether` / `SignForward` |
| **ActivityState** | 管 **节点**进出、挂起、退回/撤销等流转态 |
| **TaskState** | 管 **个人待办**开闭；`EndType` 细分办结原因，**不替代** TaskState |
| **Leave** | 管「多人时怎样才算出节点」——**不负责建图** |
| **建子 AI** | 仅 **SignTogether（会签拓扑）** 与 **SignForward（加签）**；转办/沟通/委派/代批 **不建** |
| **主/子判定** | 会签/加签子：`MainActInstanceId`→主容器；主容器常 `Suspended`。`MainActInstanceId` 空 ≠ 一定是会签主——也可能是普通节点或 **AndSplitMI 兄弟顶层 AI** |
| **多条顶层 AI** | 并行网关多支路、**AndSplitMI** 同活动复制、子流程×MI；**不是**「多个 SignTogether 主」 |
| **多单位下发** | 组间 Leave（1 AI·N Task）或 AndSplitMI（N 兄弟 AI）或 SubProcess（各单位子流程）；按意图选型，见 §4.2 |
| **办理权（本人任务）** | **以当前待办 `Task.SignId`（`TaskView`）为准**；活动 `SignIds`/`SignNames` **仅汇总展示**，不作权限判定 |

```text
ProcessInstance
  └─ ActInstance（节点令牌 / 会签·加签席位）
        └─ Task × N（每人 / 每席一条待办）

记法：
  改「离开规则」→ Leave（Collaborate / Race …）
  改「审批拓扑」→ SignTogether / SignForward（主+子 AI）
  改「人 / 信息」→ Transfer / Consult / Delegate / Surrogate（同 AI 动 Task）
  问「能否办理 / 加签 / 退回」→ Task.SignId == 当前用户（勿读 AI.SignIds）
```

## 1. 两层职责

### 1.1 ActInstance（节点实例）

- **含义**：流程运行中每个节点（含会签子实例、网关、开始/结束）**激活一次对应一行**。
- **典型字段**：`ActivityId` / 名称快照、`ActivityState`、`WorkItemType`、`SignIds`/`SignNames`（活动级汇总）、会签/加签 `ComplexType`·`MergeType`·`CompleteOrder`、`MainActInstanceId`、退回源/原点、`ApprovalStatus`、网关 token 等。
- **谁有 Task**：`WorkItemType=IsWorkItem`（任务/多实例等）才生成待办；开始/结束/网关等 **NonWorkItem** 通常 **0 条 Task**。

### 1.2 Task（任务 / 待办）

- **含义**：活动实例下按办理对象拆分的工作项；含委托、沟通参与者、发送/下达/激活与个人超期。
- **典型字段**：`SignId`/`SignKind`、`TaskState`、`EndType`/`EndText`、`Msg`、`EntrustedTaskId`、`ProxySignId`、`AssigneeRole`/`ConsultSrcTaskId`、个人时钟 `SendAt`/`GotAt`/`ActiveAt`/`DueAt`/`CompletedAt`。
- **视图**：待办查询常 `sf_task` ⋈ `sf_act_instance` ⋈ `sf_proc_instance`（如 `TaskViewEntity`）。

### 1.3 两层怎么配合

| 问题 | 看哪一层 |
|------|----------|
| 流程卡在哪个节点？ | ActInstance + `ActivityState` |
| 张三还有没有待办？ | Task + `TaskState` |
| **当前用户能否 Run / 加签 / 退回？** | **Task（`TaskView.SignId`）**，见 §1.4 |
| 多人怎样才算出节点？ | Leave（读 Seats：优先 Task 投影）→ 结果写回 AI |
| 会签/加签主容器为何常 Suspended？ | 主 AI 挂起等子；可办的是子 AI + 其上 Task |
| 活动上显示「谁在办」汇总？ | ActInstance.`SignIds`/`SignNames`（冗余展示，可与 Task 短暂不一致） |

### 1.4 约定 · 办理权以 Task 为准

**口径（2026-11-21）：** 引擎「是否本人任务」统一看 **当前待办**，与转办 / 撤回 / 委派既有口径一致。

| 项 | 约定 |
|----|------|
| **权威字段** | `sf_task.tk_sign_id`（视图 `TaskView.SignId`） |
| **判定** | `TaskManager.IsMine(taskView, runner.UserId)` → `SignId == userId` |
| **适用** | Factory 创建运行时：`Run`（同步/异步）、`SignForward`、`SendBack`；以及 `ActivityInstanceManager.IsMineTask` / `IWorkflowService.IsMineTask` |
| **活动 `SignIds`** | **仅冗余汇总/展示**（如时间线、工作台活动行）；由建待办、`RefreshActivitySignFromOpenTasks`（转办/改派/减签后）等维护 |
| **禁止** | 用 `runningNode.SignIds.Contains(userId)`（或「空 SignIds 则跳过」）做办理权；Substring 命中且会与 Task 错位 |

**错位示例（合法但须按 Task 放行）：** 待办 `SignId=admin`，活动仍 `SignIds=zhangsan`（改人后汇总未刷）→ **admin 可加签/通过**；不得因活动汇总拒掉。

```text
Runner.UserId + TaskId
  → 加载 TaskView
  → SignId == UserId ? 允许 : 拒（非本人任务）
AI.SignIds ──仅──► 展示 / 汇总（可滞后）
```

实现锚点：`RuntimeInstanceCreator`（Run / SignForward / SendBack）、`TaskManager.IsMine`、`ActivityInstanceManager.IsMineTask`（内部改为查本人打开待办，不再读 `SignIds`）。

## 2. 两种结构（扁平 vs 主/子）

与 [专题-办理人权重与委托体系.md](./专题-办理人权重与委托体系.md) §2、[专题-多人办理模式.md](../OA/专题-多人办理模式.md) §3 同口径。

### 2.1 结构 A · 扁平（一 AI · 多 Task）

```text
ActivityInstance（1）
  ├─ Task 张三
  └─ Task 李四
```

- **适用**：普通用户任务上多人；Leave=`Collaborate` / `Race` / 组模式等。
- **Leave**：Seats 从同 AI 下 Task 投影。
- **建图方**：`NodeMediator.CreateNewTask` → `TaskManager.Insert(AI, performers)`——**只插多 Task，不拆子 AI**。

### 2.2 结构 B · SignTogether / SignForward（主 + 子 AI）

```text
主 ActivityInstance（容器，常 Suspended）
  ├─ 子 AI 张三 → Task 张三
  └─ 子 AI 李四 → Task 李四
       （委托代批：代理人 Task 仍挂原人子 AI，不为代理人新建子 AI）
```

- **SignTogether**：进会签节点时 `CreateMultipleInstance`——主 AI 写 `ComplexType=SignTogether` 并挂起；**仅根席**（无 `ProxySignId`）建子 AI + Task；有 `ProxySignId` 的代理人在对应根子 AI 上 **追加 Task**。
- **SignForward**：办理时加签——当前 AI **升级**为加签主节点并挂起；再建本人与加签人子 AI+Task（前/后/并节奏不同）。
- **Leave**：Seats 优先 Task；兼容子 AI 人头；加权代批同根 `EffectiveWeight` 去重。

### 2.3 基数速查

| 形态 | ActInstance | Task |
|------|-------------|------|
| 网关 / 开始 / 结束 | 1 | **0** |
| 单人普通审批 | 1 | **1**（特例） |
| 多人扁平（会签 Leave / 抢办） | **1** | **N** |
| SignTogether | **1 主 + N 子** | 每根席 ≥1；代批同子 AI 可再 + |
| SignForward 加签后 | **1 主 + 本人子 + 加签人子…** | 各子上 Task |
| 沟通进行中 | 不变 | 原审批 Task + Participant Task×M |
| 转办 / 委派后 | 不变 | 关开同 AI 上 Task |

## 3. OA 原语落库对照

> **会签 / 抢办** 首先是 **Leave**，不是办理条按钮；**加签**才改拓扑建子 AI。口语「委托」见三分表，勿混成一种。

### 3.1 会签（Leave = `Collaborate`）

| 场景 | AI | Task | 建子 AI？ |
|------|----|------|-----------|
| 普通用户任务 + Collaborate | **1** | **N** | ❌ 扁平 |
| MultiSign / SignTogether 节点 | **1 主 + N 子** | 每根席 Task（代批可同子多 Task） | ✅ |

- 本人办结 → Task（及对应子 AI）Completed；**凑齐** Leave 条件才离开节点；旁人待办不因一人通过而关。

### 3.2 抢办 / 或签（Leave = `Race`）

| 场景 | AI | Task | 建子 AI？ |
|------|----|------|-----------|
| 普通用户任务 + Race | **1** | **N** | ❌ |
| SignTogether + Race（可配） | 主+子 | 各子 Task | ✅（拓扑仍 SignTogether） |

- 一人同意且 Leave 通过 → 完结 AI 时旁关同活动其余打开审批 Task（`RaceTaken` / 同链 `ProxyTaken`）。
- **≠ 转办**：抢办是离开规则；转办是交自己的待办。

### 3.3 加签（`SignForward` 三子型）

**会改活动拓扑**（Transition 族），**一定**形成主/子 AI。

```text
原当前 AI ──升级──► 主 AI（Suspended, ComplexType=SignForward）
                      ├─ 子 AI（本人）→ Task
                      └─ 子 AI（加签人…）→ Task
```

| 子型 | 节奏要点 |
|------|----------|
| 前加签 Before | 加签人先审；本人子 AI 常先挂起，审完再回 |
| 后加签 Behind | 本人先；加签人子 AI 先挂起 |
| 并加签 Parallel | 本人与加签人并行（子 `CompleteOrder` 常 -1） |

- **≠ 设计期会签节点**：会签进节点即 SignTogether；加签是办理时把当前 AI 升级为 SignForward 主容器。
- **≠ 沟通**：加签人有完整审批权；沟通参与者无推进权。

### 3.4 转办（`Transfer`）

| 项 | 行为 |
|----|------|
| AI | **不新建**；活动仍 Ready/Running |
| Task | 原人 `Closed` + `EndType=TransferredOut`；接手人 **同 AI Insert** |
| 推进 | ❌ 不经 Runtime；对方再 Approve 才走 Leave |
| Sign | **刷新**打开待办上的 SignIds/Names |

### 3.5 沟通（`Consult` / `Acknowledge` / `RecallConsult`）

| 项 | 行为 |
|----|------|
| AI | **不新建** |
| Task | 同 AI 建 `AssigneeRole=Participant`；`ConsultSrcTaskId`→源审批 Task |
| Leave | 参与者 **不进** SignIds / 席位分母 |
| 推进 | 源待办硬锁至参与者阅完或收回；三动词均不推进节点 |

抄送（`Copyto`）**不进** `sf_task`、不锁审批——勿与沟通混称。

### 3.6 委托三分

| 产品 | 机制 | AI | Task | 子 AI？ |
|------|------|----|------|--------|
| **转办** | `Transfer` | 同 AI | 关己开人，**不还回** | ❌ |
| **委派** | `Delegate` + `EntrustedTaskId` | 同 AI | 关己；新人挂回转链；办完 **回转**原人 Waiting，**不**完结 AI | ❌ |
| **委托代批** | Surrogate Filter + `ProxySignId` | 不另建 | 建待办时 **追加**代理人 | ❌；SignTogether 上挂 **原人子 AI** |

两条链禁止混谈：`EntrustedTaskId`（委派回转）⊥ `ProxySignId`（代批计权根）。

### 3.7 总表

| 原语 | 典型落库 | 一句话 |
|------|----------|--------|
| 会签 Leave=`Collaborate`（扁平） | 1 AI · N Task | 多人同节点，凑齐才走 |
| 抢办 Leave=`Race`（扁平） | 1 AI · N Task | 一人过，旁人 Closed |
| 会签拓扑 SignTogether | 主+子 AI；根席 ≈ 1 子 : 1 Task | 设计期会签图 |
| 加签 SignForward | 主+子 AI；每人一子+Task | 办理时临时插审批拓扑 |
| 转办 | 同 AI 关开 Task | 交人，不建 AI |
| 沟通 | 同 AI 加 Participant Task | 要信息，不进 Leave |
| 委派 | 同 AI 关开 Task + 回转 | 代办还回，不推进 |
| 委托代批 | 同 AI（或同子 AI）多 Task | 配置并人，不建子 AI |
| 单人普通审批 | ≈ 1 AI : 1 Task | 特例，非硬约束 |

## 4. 主 / 子 AI 判定

> **「主」有两义，勿混：**  
> ① **会签/加签主容器**：`ComplexType`∈{SignTogether, SignForward}，常 Suspended，子靠 `MainActInstanceId` 挂上。  
> ② **顶层 AI**：`MainActInstanceId` 为空——含普通单节点、并行分支上的各节点、以及 **AndSplitMI 同活动的多条兄弟实例**（彼此不是父子）。

| 规则 | 含义 |
|------|------|
| **`MainActInstanceId` 为空** | **顶层** AI：普通任务 / 网关 / 并行支路上的节点 / AndSplitMI 各分支副本；**若**再带 SignTogether/SignForward ComplexType，才是会签·加签**主容器** |
| **`MainActInstanceId` = 某 AI Id** | 会签/加签 **子**实例，挂在该主下 |
| **主容器常 `Suspended`** | 等子办；真正可办的是子 AI（串行时未轮到的子也会 Suspended） |
| **`ComplexType`** | `SignTogether` 会签拓扑；`SignForward` 加签拓扑 |
| **`MergeType` + `CompleteOrder`** | Sequence：子序 1,2,3…；Parallel：子多为 -1；主上可存通过阈值 |
| **Leave 入口** | 办结后问节点能否离开；扁平看同 AI Seats；主/子则办结子后看主上完成度 / Leave → 主 Completed → ContinueForward |

```text
谁是会签/加签「主容器」？  MainActInstanceId 空 + ComplexType=SignTogether|SignForward
谁是其子？                 MainActInstanceId == 主.ai_id
谁是并行「多条顶层 AI」？  多行 MainActInstanceId 皆空，且彼此无主从（见 §4.1）
何时出节点？
  扁平：Leave 直接看同 AI 上 Seats（Task）
  主/子：办结子 → 看主上子完成度 / Leave → 主 Completed → ContinueForward
  并行多支：各支各自办结，到 AndJoin / AndJoinMI 用 token 汇聚
```

实现锚点（会签建图）：`NodeMediator.CreateMultipleInstance`——根席建子并 `MainActInstanceId=主`；代理人只 `TaskManager.Insert` 到原人子 AI。  
加签建图：`NodeMediatorSignForward`——`UpgradeToMainSignForwardNode` + `CreateSignForwardTasks`。

### 4.1 什么情况会出现「多条顶层 AI」？

同一流程实例里，**同时 Ready/Running、且 `MainActInstanceId` 皆空** 的多条活动实例，常见如下（**不是**「多个 SignTogether 主容器」那种主从）：

| 场景 | 落库形态 | 说明 |
|------|----------|------|
| **AndSplit** 并行网关 | 各出边目标节点各 1 条 AI（**ActivityId 通常不同**） | 流程图上多条并行支路；汇聚靠 AndJoin + Tokens |
| **AndSplitMI** 并行多实例 | **同一 ActivityId** 复制出 **N 条兄弟 AI**，每人/每席一条，各挂 1 Task | `NodeMediatorTask`：来自 AndSplitMI 网关时 `for plist` 循环 Insert，**不写** `MainActInstanceId` |
| 子流程 × AndSplitMI | 每人/每席一个子流程节点 AI + **子 ProcessInstance** | `NodeMediatorSubProcess` 同模式循环 `CreateSubProcessNode` |
| 退回后再前进 / 节点重入 | 历史 Completed AI 保留 + 新 Ready AI | 「多条」含历史行；活着的通常仍按状态过滤 |
| SignTogether / SignForward | **只有 1 个主容器** + N 子 | 子不是「多个主」 |

```text
AndSplitMI（同活动多实例）示意：

  Gateway AndSplitMI
       ├─ AI#1（ActivityId=审批, MainActInstanceId=null, Sign=单位甲）→ Task
       ├─ AI#2（ActivityId=审批, MainActInstanceId=null, Sign=单位乙）→ Task
       └─ AI#3（…单位丙）
  → 汇聚 AndJoinMI（token）

对照 · SignTogether（一个主容器）：

  主 AI（Suspended, ComplexType=SignTogether）
       ├─ 子 AI（MainActInstanceId=主）→ Task
       └─ 子 AI → Task
```

**并行会签（MergeType=Parallel）≠ 多主 AI：** 仍是 **一个** SignTogether 主 + 多个子。

### 4.2 多单位下发、各单位各自审批 —— 怎么建模？

口语「上级发给多个下级单位，各单位内部各自审批」在 Sail 里**至少三种**，落库差很大：

| 产品意图 | 推荐建模 | AI / Task | 算不算「多主 AI」 |
|----------|----------|-----------|-------------------|
| 同一节点：多单位并行收件，单位内抢办/协办，**组间都过才离开** | **1 个用户任务** + Resolve 带齐 `GroupId`（可双写 Unit）+ Leave=`GroupRace`/`GroupCollaborate` + `groupJoin=And` | **1 顶层 AI · N Task**（按 Group 投影） | ❌ |
| 同一节点定义：按人选 **复制出 N 条并行实例**，各办各的，到 MI 汇聚 | 前接 **AndSplitMI**，目标用户任务（或子流程） | **N 条兄弟顶层 AI**（同 ActivityId） | ✅ 多顶层，**无**主从 |
| 各单位要走 **自己的多步审批子流程** | **SubProcess**（可叠加 AndSplitMI：每单位一子流程实例） | 父上 N 个子流程节点 AI；子 PI 内再各自 AI/Task | ✅ 父上多顶层；子内另算 |

```text
高频「怪需求」正确拆法（管道文档口径）：
  Resolve → Performer[] 每行 Unit* + GroupId(=单位时双写)
  Leave   → GroupRace / GroupCollaborate + groupJoin=And
  → 只要 1 个 AI，不要按单位拆出 N 个「主 AI」

要「各单位内部多节点审批流」：
  → SubProcess（或独立流程），不要指望扁平 GroupLeave 冒充子流程
```

**勿混：**

- 多单位 GroupLeave ≠ AndSplitMI 多兄弟 AI ≠ SignTogether 主+子。  
- 「并行」三词：网关并行支路 / MI 同活动多实例 / 会签子并行——结构不同。

## 5. 状态各管什么

### 5.1 `ActivityState`（节点层）

| 值 | 含义（摘要） |
|----|----------------|
| Ready=1 | 已激活，可办 |
| Running=2 | 办理中 |
| Completed=4 | 节点完成 → 可向下流转 |
| Suspended=5 | 挂起（会签/加签主、串行未轮到等） |
| Withdrawed=6 | 撤销 |
| Sendbacked=7 | 退回 |
| Cancelled=8 | 系统取消 |
| Terminated=9 | 非正常结束（如超时终结） |

另：`ApprovalStatus` 偏同意/拒绝结论；会签比较字段偏离开规则参数，**不替代** ActivityState。

### 5.2 `TaskState`（待办层）

| 值 | 含义（摘要） |
|----|----------------|
| Waiting=1 | 等待办理 |
| Reading=2 | 办理中 |
| Completed=4 | 本人正常办结 |
| Withdrawed=8 | 撤销 |
| SendBacked=9 | 退回 |
| Closed=32 | 多人场景下他人办完后本待办关闭（抢办旁关、转办关己等） |
| Canceled=48 | 未办直接取消 |

- **`EndType` / `EndText`**：办结原因细分（`RaceTaken`、`TransferredOut`、`DelegatedOut`、`ProxyTaken`…）；**不替代** `TaskState`。
- 转办关原人用 **Closed** 而非 Completed，避免被会签计为已办。

### 5.3 配合关系

```text
Approve/Run
  → 办结本人 Task（及结构 B 下对应子 AI）
  →（委派回转则拆链还回，不问离开）
  → Pipeline.TryCanLeave（读 Seats）
  → Passed → 完结活动（Race 等旁关他人 Task）→ ContinueForward
  → Waiting → 停本节点
```

## 6. 选型心智图

```text
多人怎样才算出节点？           → Leave（会签/抢办）——可配在扁平或 SignTogether 上
进节点就要一人一席拓扑？       → SignTogether（主+子 AI）
办理时临时插人先/后/并审？     → 加签 SignForward（升级主+建子 AI）
只要换人 / 问信息 / 代办还回 / 配置并人？
                              → 全是同 AI 动 Task，不建子 AI
```

**红线（与邻域专题一致）：**

1. 勿把 Leave 当成办理条按钮；勿把转办当成抢办。  
2. 勿为委托代批代理人新建会签子 AI。  
3. 勿把沟通参与者计入 Leave / SignIds。  
4. 勿用 `EntrustedTaskId` 描述代批，勿用 `ProxySignId` 描述委派回转。  
5. 勿假设「一节点永远一条 Task」。  
6. **勿用活动 `SignIds` 判定办理权**；本人任务以 `Task.SignId` 为准（§1.4）。
