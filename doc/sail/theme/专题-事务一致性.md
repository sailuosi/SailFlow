## 0. 一句话

**一次流转动词（Start / Run / Transfer / SendBack / Suspend…）在引擎库上的关键写路径，必须落在同一个 DB 事务里：要么整段成功提交，要么整段失败回滚；没有「半成功」的合法终态。**

旁路副作用（推送、对账、BestEffort 日志）可以晚、可以丢、可以重试——但**不得**成为「关键写路径只完成一部分」的补偿借口。

---

## 1. 为何对流程引擎极其重要

### 1.1 半成功是生产常态威胁

生产环境同时存在：复杂网络、多系统、高并发、慢 SQL、宿主钩子阻塞、连接池耗尽、进程崩溃。若一次「同意 / 发起 / 退回」的关键写路径**拆成多段各自提交**，极易出现：

| 半成功形态 | 典型残局 | 无事务时的代价 |
|------------|----------|----------------|
| 待办已办结，活动未推进 | 人已点同意，节点停在原地 | 对账扫「已办未走」、人工补推 |
| 活动已推进，下一待办未生成 | 节点空转、无人可办 | 残余活动判定、补建 Task |
| 引擎实例已终态，业务表未回写 | 列表仍「审批中」 | 业务 Status 治理 Job |
| 引擎已回滚，外部已推送 | 幽灵待办 / 误通知 | 推送撤销、对账消噪 |
| 父流程已写子，子另连接失败 | 父子不一致 | 子流程清理 / 重试编排 |

没有**同一 DB 事务的回路**，上述残局无法靠「抛异常自动撤销」收口，只能堆：数据治理脚本、残余判定、异常清理、人工运维。成本与漏网概率随办理量指数上升。

### 1.2 sailflow 的立场

| 做 | 不做 |
|----|------|
| **关键路径同事务**：PI / AI / Task / 变量 / Transition / Outbox 入队 / Sync Hook 写引擎库 | **不**把「半成功 + 事后补偿」当作核心动词的默认语义 |
| 失败 **FailFast** → 事务不 commit（`CommitOnSuccess` 仅 Success 才提交） | **不**首期做跨库 Saga / 分布式事务冒充同事务 |
| Async 副作用与主路径至多「**同库 Outbox 同事务写入**」 | **不**用 Outbox / Channel 替代必须同事务的业务回写 |
| 实例级 `InstanceExecutionLock` 降低同实例并发交错写 | **不**用锁代替事务（锁防交错，事务防半成功） |

一句话对照：**一致性优先于「钩子方便另开连接」；可观测性优先于「闷锅后再猜」。**

## 2. 决策表（本专题口径）

| 编号 | 决策 | 口径 |
|------|------|------|
| **T1** | 流转动词关键写路径 **严格同事务** | `WorkflowService.CommitOnSuccess` / `RunAction`：`beginTransaction` → 执行 → **仅** `Status==Success` 才 `commit` |
| **T2** | 事务边界 **仅在 Service** | Action / 族群 / Manager Core **禁止**自开 `beginTransaction`、禁止自抢实例锁；吃已开 `kit` |
| **T3** | 同事务可写集合 | 引擎运转表 + 同库 Sync Hook 业务写 + **Outbox INSERT Pending**；外部 HTTP/IM **不得**进 Sync 当唯一真相 |
| **T4** | Sync = FailFast 参与回滚 | Sync Hook / CreateHook 异常或软超时 → 包装抛出 → 主事务不提交 |
| **T5** | Async = 账本同事务、执行提交后 | `EnqueueAsyncHooks` / `EnqueueTaskNotifiers` 与流转同 kit 入队；Drain 在提交后独立短事务消费 |
| **T6** | kit 传递是契约 | 有事务时只用传入的同一个 kit（或 `kit.useSQL()` 同连接新 builder）；禁止 `Sail.UseRunSQL()` 另开连接碰未提交行 |
| **T7** | Gate 在写前，不当事故 | Gate `Reject` → 无推进副作用或干净回滚；与 Sync FailFast（事故/超时）语义分离 |
| **T8** | 可观测是同事务的护栏 | Sync BEGIN/END、超时必抛、禁止空吞——详见钩子治理专题；本专题规定「为何必须有」 |
| **T9** | 事务生命周期钩子（信封外） | `OnTransactionCommitted`（commit 后）/ `OnTransactionFailed`（异常或 `Status!=Success`）；仅 Sync **BestEffort**；`Kit=null`；不做 AsyncOutbox；仅 `CommitOnSuccess` 路径 |

## 3. 事务信封：一次动词包住什么

### 3.1 入口形状（代码锚点）

```text
XxxProcess / XxxProcessAsync
  → WorkflowService.RunAction / RunActionAsync
       → CommitOnSuccess(runner, kit => {
            beginTransaction
            InstanceExecutionLock.Acquire(实例键)
            new XxxAction(Sail, kit, runner).Execute()
                 Gate → ExecuteCore（Manager 写库，吃 kit）
                      → OnFireFlowHook
                           RunSyncHooks(kit)          // ctx.Kit = kit；FailFast
                           EnqueueAsyncHooks(kit)     // Outbox 同事务
                           EnqueueTaskNotifiers(kit)  // 同上
            if Success → commit → OnTransactionCommitted（Kit=null；BestEffort）
            else / catch → OnTransactionFailed（Kit=null；BestEffort；catch 后再 throw）
         })
```

代码：`WorkflowService.ProcessExecution.cs`（`CommitOnSuccess` / `RunAction`）；动作时序见 [专题-流转动作骨架.md](./专题-流转动作骨架.md)。  
`Xxx(SQLBuilder kit, …)` 重载**不**唤起事务生命周期钩子（事务归属调用方）。

| 层 | 事务语义 |
|----|----------|
| `WorkflowService` | **唯一**开事务 + 实例锁；commit/失败后唤起生命周期钩子 |
| `*Action` / 族群 | 无事务语义；只吃已开 `kit` |
| `*Manager` | 「有事务只用传入 kit；无事务才 `UseRunSQL`」 |
| Sync Hook（成功事件） | 挂 `ctx.Kit`；写库必须走 kit；FailFast |
| Outbox 入队 | 同 kit INSERT；**Kit 不入序列化载荷** |
| Tx 生命周期 Hook | **信封外**；`Kit=null`；BestEffort |

### 3.2 信封内 / 信封外

| 信封内（同事务） | 信封外（提交后 / 旁路） |
|------------------|-------------------------|
| 流程/活动/待办/变量/流转实例写库 | Outbox Drain 调外部 HTTP / IM |
| Gate 通过后的 Core 写路径 | BestEffort Channel 日志埋点 |
| Sync Hook 业务状态回写（同库） | Reconcile 对账 Job 补推 |
| Async Hook / Notifier **入队行** | 已提交后的重试 / Dead / 复活 |
| CreateHook 改 Title / 发号等落库前同步改写 | 跨系统补偿（产品自管，非引擎默认） |
| | **`OnTransactionCommitted` / `OnTransactionFailed`**（观测、审计旁路；不可当强一致写回） |

**强一致回写不得只丢进 Outbox 当唯一保障**——见 [OA/专题-业务状态回写.md](../OA/专题-业务状态回写.md) 与副作用可靠性 §4.2。

### 3.3 成功才提交

```csharp
// CommitOnSuccess 语义（示意）
kit.beginTransaction();
try {
  result = action(kit);
  if (result.Status == Success) {
    kit.commit();
    RunTxLifecycleHooks(OnTransactionCommitted); // BestEffort
  } else {
    RunTxLifecycleHooks(OnTransactionFailed);    // BestEffort
  }
} catch (ex) {
  RunTxLifecycleHooks(OnTransactionFailed);      // BestEffort
  throw;
}
// 非 Success 或异常 → 不 commit；连接释放即回滚
```

Gate `Reject`、Core 业务失败、Sync 抛错 / 软超时，均不得留下「半截运转行」。  
生命周期钩子**不能**回滚已提交事务，也**不得**改变已返回的 `WfExecutedResult` / 原异常。

### 3.4 事务生命周期钩子（T9）

| 事件 | 触发 | Mode | Kit | 失败语义 |
|------|------|------|-----|----------|
| `OnTransactionCommitted` | `commit` 成功之后 | **仅 Sync** | `null` | BestEffort：异常/超时只记日志 |
| `OnTransactionFailed` | 异常，或 `Status != Success`（含 Gate Reject） | **仅 Sync** | `null` | 同上；不吞原异常、不改原结果 |

上下文旁路字段：`FailureException` / `ExecutedStatus` / `FailureMessage`（`[JsonIgnore]`）。  
配 `AsyncOutbox` 订阅这两事件 → **跳过并 Warning**（首期不做入队）。

## 4. 同事务如何延伸到钩子与旁路

### 4.1 主路径时序（与事件教程对齐）

```text
Gate（落库前，Reject 干净停）
  → 内核流转写库（同 kit）
  → Sync Hook（同线程、同 kit；异常 FailFast）
  → Outbox INSERT（Async Hook / Notifier；同 kit）
  → commit → 返回 WfExecutedResult
后台 Drain：认领 Pending → 调 Handler → Succeeded / 重试 / Dead
```

这样保证：

- **流程回滚 ⇒ 无 Pending 推送行**（不会「引擎没办成、外部已推」）；
- **流程提交 ⇒ Outbox 至少有账**（Reliable 档可崩溃续跑）；
- Sync 写业务失败 ⇒ 整笔办理回滚，避免「流程终态与业务 Status 永久分叉」。

### 4.2 Mode 选型（事务视角）

| 需求 | 模式 | 事务含义 |
|------|------|----------|
| 必须看见**未提交**的 PI/Task/变量并改库 | **Sync** + `ctx.Kit` | 参与主事务；失败回滚 |
| 可延后；可与外部系统最终一致 | **AsyncOutbox** | 仅入队同事务；执行在提交后 |
| 丢了只少统计 | **BestEffort** | 不进主事务关键路径 |
| 有业务真相表 + 对账 | **Reconcile** | 推送可晚；不以 Outbox 为唯一保险 |

细则与档位表：[特性说明-副作用可靠性.md](../特性说明-副作用可靠性.md)；钩子超时/日志：[专题-钩子治理与同事务可观测.md](./专题-钩子治理与同事务可观测.md)。

### 4.3 第二连接 = 自锁（同事务的死敌）

主事务未提交时，钩子 / Filter / 子流程若再 `Sail.UseRunSQL()` 读写刚写入的行：

```text
Conn1（流转 kit）          Conn2（UseRunSQL）
  beginTransaction
  INSERT …
  Sync Hook / 选人 …
       │                     SELECT/UPDATE 未提交行
       │◄── 等 Conn1 提交 ───┤
       │ 等钩子返回
       ▼
     自锁闷锅（SQLite 5/6；SQL Server 锁等待）
```

**正确**：`ctx.Kit` / `kit.useSQL()` / 带 kit 的 Service·Manager 重载。  
案例与评审单：[专题-Bug治理-Sync钩子同事务自锁.md](./专题-Bug治理-Sync钩子同事务自锁.md)。

## 5. Manager / 子流程 / 变量：kit 契约

引擎 Manager 终态注释口径（如 `ProcessVariableManager`、`TransitionInstanceManager`）：

> **无事务**从 Client 取 kit；**有事务**只用传入的同一个 kit。

| 场景 | 正确 | 错误 |
|------|------|------|
| Action / Runtime 内写库 | 构造注入的 `kit` 下传 | Manager 内再 `beginTransaction` |
| 链式 select 互污染 | `kit.useSQL()` 同事务新 builder | 新开 `UseRunSQL()` |
| 子流程 Execute | `subKit = kit.useSQL()` | `subKit = Sail.UseRunSQL()` |
| Sync 钩子读写变量 | `Get/Save*(kit, …)` 或 `ctx.Kit` | 无 kit 的变量 API |
| Assignee Filter 读未提交 PI | `AssigneeInvokeRequest.Kit` | Filter 内自建连接 |

`kit.useSQL()`：**同库同连接同事务**的新 `SQLBuilder`，不是新事务。用于避免一条 kit 上链式状态互相踩踏，同时保持 T1。

## 6. 并发与锁：和事务的分工

| 机制 | 防什么 | 不防什么 |
|------|--------|----------|
| **DB 事务** | 单次动词写路径半成功 | 两请求交错改同一实例 |
| **`InstanceExecutionLock`**（按 BizPK / ProcessId） | 同实例并发动词交错 | 跨实例；跨库；钩子另连接自锁 |
| **Outbox CAS + lease** | Drain 双消费同一 Pending | 主路径半成功 |

锁在 Service 与事务**同层**获取（`RunAction` 内）；Action 内禁止再 `Acquire`。异步路径：`AcquireAsync` 仍包在 `CommitOnSuccessAsync` 内。

## 7. 衍生规约（钩子 · 可观测 · 扩展插件）

同事务要求**必然**带出下列约束——违反即回到 §1 的残局或闷锅。

### 7.1 钩子治理（摘要）

| 规约 | 说明 |
|------|------|
| Sync 必须短 | 禁同步打慢外部；重活改 AsyncOutbox |
| 有 `ctx.Kit` 必复用 | 读写引擎库走 kit；见 T6 |
| 异常可见 | 禁止空 `catch`；上抛或经 `Sail.Log` 打 Error |
| 软超时 FailFast | 返回后超时仍抛，参与回滚（不保证打断阻塞 SQL） |
| 进度日志 | BEGIN/END；卡死时「有开始无结束」定位钩子名 |

完整决策表 D1–D10：钩子治理专题。本专题强调：**这些不是锦上添花，而是同事务模型可运维的前提。**

### 7.2 可观测性（事务视角要看见什么）

| 信号 | 用途 |
|------|------|
| `同事务Kit=是/否` | 确认钩子是否在信封内 |
| Sync 开始 / 结束 / 偏慢 / 失败 | 区分「慢」与「死」；归因钩子名 |
| Outbox 入队失败即抛 | 避免「流程以为入队成功、实际无账」 |
| Drain Succeeded / Failed / Dead | 提交后旁路健康度；与主事务解耦 |

宿主 DevConsole / `SailClient.Log` 契约见钩子治理专题 §3。

### 7.3 扩展插件用法规约

| 扩展点 | 同事务要求 |
|--------|------------|
| `IFlowGate` | 仅 Sync；短校验；**尽量不写库**；Reject 非异常 |
| `IFlowHook` Mode=Sync（成功事件） | 用 `ctx.Kit`；FailFast；适合同库回写 |
| `IFlowHook` + `OnTransactionCommitted`/`Failed` | **必须 Sync**；`Kit=null`；BestEffort；勿当强一致回写 |
| `IFlowHook` Mode=AsyncOutbox | 勿假设未提交行仍可见；载荷无 Kit；**勿**订事务生命周期事件 |
| `IProcessInstanceCreateHook` | **固定 Sync**；改 Title 等必须同事务；用 `ctx.Kit` |
| `ITaskNotifier` | 默认 Outbox；禁止「Channel 写完就 MarkSucceeded」双异步 |
| Assignee Filter / Resolver | 请求带 `Kit` 时复用；读发起未提交实例必须走 kit |
| 自定义 Manager 调用 | 办理中传入的 kit 优先；无 kit 重载仅只读已提交数据 |
| BPMN 子流程 / 嵌套 | 子执行用 `kit.useSQL()`，勿另连接 |

宿主能力包注册形态见 [最佳实践-宿主能力包UseXxx.md](../最佳实践-宿主能力包UseXxx.md)。

## 8. 反模式清单（评审用）

| # | 反模式 | 后果 |
|---|--------|------|
| A1 | Action / Manager 内 `beginTransaction` | 嵌套事务或提前提交 → 半成功 |
| A2 | Sync 钩子 `UseRunSQL` / 无 kit API 碰引擎库 | 自锁闷锅 |
| A3 | 业务终态只写 Outbox、不 Sync | 流程提交、业务永远审批中 |
| A4 | Notifier 内先标 Outbox 成功再丢内存队列 | 崩溃 → 幽灵待办 |
| A5 | Sync 里同步调 HTTP 当强一致 | 拉长锁、超时、外部已副作用无法回滚 |
| A6 | 捕获 Sync 异常后吞掉当成功 | 主路径假成功或残局不可见 |
| A7 | 放大全局超时掩盖锁等待 | 治标；有 kit 自锁时仍可能永不返回 |
| A8 | 子流程 / 变量 / 选人另连接读未提交 | 同 A2 |
| A9 | 靠「治理 Job」补核心动词半成功 | 把引擎缺陷产品化；成本爆炸 |

## 10. 验收口径（自检）

一次新的办理动词或宿主插件，满足即可认为对齐本专题：

1. 写路径是否只经 `RunAction` / `CommitOnSuccess`（或文档记载的已开 kit 重载）？
2. Success 之外是否保证**无**残留运转行 / Outbox Pending？
3. Sync 扩展是否只用 `ctx.Kit` / `kit.useSQL()`？
4. 须与办理原子一致的业务写，是否在 Sync（或主路径），而非唯一依赖 Outbox？
5. Async 入队是否与流转同 kit？Drain 是否在提交后？
6. 卡死/超时时，日志能否指出钩子名与 `同事务Kit`？
7. 若订了 `OnTransactionCommitted`/`Failed`：是否 Sync、是否接受 `Kit=null`、是否未当强一致回写？
