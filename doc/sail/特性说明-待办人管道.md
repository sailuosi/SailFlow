# 待办人管道（Assignee）— 引擎侧架构与扩展基准

> 状态：**现行基准**（S0–S4 已落地；2026-11-01）  
> 包：`src/core/pure/assignee`（`saiflow.assignee`）· 薄契约：`saiflow.engine.Assignee`  
> 动机：业务「奇葩」算人/完成需求极多；**扩展必须挂在两大时刻 + ConfigPair 注册表上**，禁止改 AIM/Mediator 堆分支  
> 讨论溯源（产品/现场场景口述）：宿主仓 `sleveen-admin/doc/sailflow-assignee-candidate-design.md`  
> 关联：[特性说明-引擎能力基线.md](./特性说明-引擎能力基线.md) · [架构设计-项目依赖与分层.md](./架构设计-项目依赖与分层.md) · [业务管道特性设计.md](./业务管道特性设计.md)

本文是引擎演进的**硬基准**：新 Type、覆写内置、接 HR/单位映射、会签收口，均先对照本文。设计讨论稿可继续改产品口径；**与本文冲突时以本文 + 代码契约为准**。

## 1. 目标与非目标

### 1.1 目标

- 用户任务「谁来办 / 办完能否离开」有统一、可注册、可覆盖的管道。  
- **两维正交**：定范围（Resolve）× 办理模式（Leave）。  
- **三根基**可落地：传入即派发、办理模式（含组/身份/人数比例）、算人可注册。  
- 业务扩展只加 **string Type** 或同码覆盖，不 fork 调度内核。

### 1.2 非目标

- 不实现完整组织中台 / HR 主数据（JobRelative、UnitMap 只提供挂钩与内置骨架）。  
- 不把芋道 `CandidateStrategy` 枚举或 Flowable Identity 原样搬进 pure。  
- 不做抄送人、通知人配置（另轨；勿与待办人 ConfigPair 混用）。  
- 金额分流等走**网关**，禁止塞进算人 Type。

## 2. 概念（勿混用）

| 术语 | 含义 |
|------|------|
| **办理人 / 待办人** | 任务已指派的执行者（`AssignedUserId` 等） |
| **Performer** | 运行时办理人条目：`UserId` / `UserName` / **`GroupId`** / **`GroupName`** / **`GroupRole`** |
| **ConfigPair** | `{ Type: string, Params: dict }`；**禁止用 enum 作分发键** |
| **时刻 A · Resolve** | **创建待办前**算出 `Performer[]` |
| **时刻 B · Leave** | **流出前**判定能否离开本节点 |
| **参与者 sf:Performer** | 设计器旧挂载；可由 Legacy 适配推断 ConfigPair，**不是**完整策略模型 |
| **NextPerformerType** | Runner 上 Specific/Definition/… 运行时选人来源；与 Resolve Type **不同维** |

易混：

- **发起人自选 (StarterPick)** ≠ **审批人自选 (ApproverPick)**。  
- **A 不决定几人办完能走；B 不负责下一跳找谁**（下一跳是下一节点的 A，或 Specific 预填）。

## 3. 三根基与两大时刻

### 3.1 三根基（F1–F3）

| # | 根基 | 引擎要求 |
|---|------|----------|
| **F1** | 发送时传入办理人 | `Specific`（及已写入的 Starter/Approver 载荷）**透传**；已传列表不得静默改写 |
| **F2** | 办理模式完整 | Leave：`Race` / `Collaborate` / `GroupRace` / `GroupCollaborate` / `Captain`；完成可用 **人数或比例**；关卡按 **GroupRole 码集**，禁用 Bool `IsLeader` |
| **F3** | 算人可注册 | `IAssigneeResolver` 按 Type 注册；内置 + 业务后写覆盖；输出必须带齐组/身份字段约定 |

```text
F1 传入（含 GroupId / GroupRole）
F2 LeaveJudge 执行
F3 Resolver 注册表
        │
        ▼
挂到 Client 时刻 A / B；业务只扩 Type 与 Params
```

### 3.2 生命周期

```text
到达用户任务
创建 Task 之前 ──► 时刻 A  TryResolveForTaskCreate
                         → Performer[]（含组别/身份）
                         → 创建待办 / 写入指派
某人办理提交后
（完成检查）   ──► 时刻 B  TryCanLeave
                         → Passed | NotPassed | Waiting
                         → Allow 则离开 → 下一节点再走 A
```

### 3.3 节点上两套 ConfigPair

| 配置对 | BPMN（现行） | 驱动 |
|--------|--------------|------|
| **AssigneeResolve** | `sf:assigneeResolve` | 时刻 A |
| **LeaveJudge** | `sf:leaveJudge` | 时刻 B |

无显式扩展时：`BpmnAssigneeConfigReader` + Legacy（Performers / MultiSign）可推断；**新流程应显式写 ConfigPair**。

## 4. 架构与分层

### 4.1 包边界（铁律）

```text
宿主 / 客户程序集
  → useAssigneeResolver / useLeaveJudge / useAssigneeBusinessCallback
sailflow.biz
  → UseBizAssignees()（UseAssignees + 产品样例 Type）
core/ext（可选）
  → 依赖表单/规则/HTTP 的扩展 Type
core/pure/assignee     ★ 重量：ConfigPair、Registry、内置（非 seal）、Pipeline、BPMN 适配
core/pure/engine       ★ 极薄：IAssigneePipeline、InvokeRequest、LeaveJudgeResult、Performer 字段
                         Mediator/AIM 仅调用，不认识具体 Type 实现
```

| 层 | 放什么 | **禁止** |
|----|--------|----------|
| **engine** | `IAssigneePipeline`；`AssigneeInvokeRequest` / `LeaveInvokeRequest`；`LeaveJudgeResult`；`Performer`(+Group*)；Mediator **一行**调用 | Type 注册表、内置策略、Params 解释、会签通过率业务改写 |
| **assignee** | ConfigPair；Resolver/LeaveJudge；Type 常量；Registry（后写覆盖）；Pipeline；`UseAssignees`；Legacy 适配 | MQ/脚本/NRules 等重依赖；被业务反向改调度 |
| **biz / 宿主** | `UseBizAssignees`；`Business.*` Type；同码覆盖内置 | fork NodeMediator / AIM 写 if-else 算人 |
| **FE** | 双 ConfigPair 面板；选人带 GroupId/GroupRole | 在前端「判定能否离开」 |

依赖方向：`biz/宿主 → assignee → engine`。engine **只持插槽**，由 `UseAssignees` 注入实现。

### 4.2 与会签 / Definition 双轨

- 旧 `Definition`（偏 Role）与 MultiSign 完成逻辑：**过渡双轨**；Pipeline `Try*` 返回 false 时走既有路径。  
- **演进方向**：新定义统一 ConfigPair；会签通过率迁入 LeaveJudge；最终收口到管道，而不是在 AIM 继续堆分支。  
- **禁止**：为「快速满足某业务」在 Mediator 再开第三条算人路径。

### 4.3 注册与覆盖规则

1. Type 比较：`OrdinalIgnoreCase` 字符串。  
2. 同 Type **后注册覆盖先注册**（业务可覆写内置 `Collaborate` 等）。  
3. 内置 Resolver/LeaveJudge 类 **禁止 `sealed`**；可继承后同码再注册。  
4. 未挂载管道：调用方应能感知需 `UseAssignees()`（勿静默空实现假装成功）。

## 5. API 形态

### 5.1 engine 薄契约

```csharp
// saiflow.engine.Assignee
public interface IAssigneePipeline
{
    /// <returns>false = 本节点未由管道处理 → 调用方走既有逻辑（双轨）</returns>
    bool TryResolveForTaskCreate(AssigneeInvokeRequest request, out PerformerList performers);

    bool TryCanLeave(LeaveInvokeRequest request, out LeaveJudgeResult result);
}
```

| 类型 | 职责 |
|------|------|
| `AssigneeInvokeRequest` | ProcessId/Version、实例、Activity、Runner、`NextActivityPerformers`；**不含 Type 分发** |
| `LeaveInvokeRequest` | 实例/活动、主/子活动快照、Runner；Pipeline 自行读 Leave ConfigPair |
| `LeaveJudgeResult` | `Decision` = `Passed` / `NotPassed` / `Waiting`（string 常量 `LeaveDecisions`） |

ConfigPair **优先只存在于 assignee**：engine 请求尽量不带 Type，由 Pipeline + `BpmnAssigneeConfigReader` 读定义。

### 5.2 assignee 处理器

```csharp
public interface IAssigneeResolver
{
    string Type { get; }
    PerformerList Resolve(AssigneeResolveContext ctx);
}

public interface IActivityLeaveJudge
{
    string Type { get; }
    LeaveJudgeResult CanLeave(LeaveJudgeContext ctx);
}

public class ConfigPair
{
    public string Type { get; set; }
    public IDictionary<string, object?> Params { get; set; }
}
```

### 5.3 挂载 API

```csharp
builder.Services.UseAssignees();          // 或 UseBizAssignees()
// Build 后 / 对 client：
client.useAssigneeResolver(new MyResolver());
client.useLeaveJudge(new MyLeaveJudge());
client.useAssigneeBusinessCallback(new MyCallback()); // Params.callback → 注册表
```

委托重载：`useAssigneeResolver(type, Func<…>)` / `useLeaveJudge(type, Func<…>)`。

### 5.4 Performer 载荷合同

```text
UserId      必填
UserName    建议
GroupId     组别（单位/部门/业务组…；扁平时可空或同组常量）
GroupName   可选展示
GroupRole   组内身份码（默认 Member）
```

**GroupRole 内置码**（`GroupRoles`）：`Organizer` · `Leader` · `DeputyLeader` · `Member`。  
可扩展（如 `Secretary`）；Leave 用 `gateRoles` 引用，**禁止** Bool 是否组长。

Resolver 输出须填齐组/身份约定；**禁止**靠逗号拼接 `AssignedUserIds` 事后猜组。

| `sf:assigneeResolve` | Resolve ConfigPair（Type + Params JSON/属性） |
| `sf:leaveJudge` | Leave ConfigPair |
| `sf:Performers` | Legacy；可推断 RoleGroup 等 |

### 5.6 真实实现侧（对照讨论稿 §11.3，已落地）

> 讨论稿 API 草稿见宿主 `sleveen-admin/doc/sailflow-assignee-candidate-design.md` §11.3。  
> **扩展、联调、改管道以本节为准**；勿按草稿里的无 `Try` 强制 `ResolveForTaskCreate`/`CanLeave` 去改 Mediator。

#### 5.6.1 与讨论稿草稿的关键差异

| 讨论稿草稿 | 真实实现 | 说明 |
|------------|----------|------|
| `ResolveForTaskCreate` / `CanLeave` 直接返回 | **`TryResolveForTaskCreate` / `TryCanLeave` → `bool`** | `false` = 未由管道处理 → Mediator/AIM **双轨回落**既有逻辑 |
| 未挂载则 `GetAssigneePipelineRequired()` 硬失败 | 调用点先读 **`Sail.AssigneePipeline`**，null 或 Try=false 则回落 | `GetAssigneePipelineRequired()` 仍保留，供必须强制管道的场景 |
| Registry 仅 `Get*` 抛错 | 另有 **`TryGetResolver` / `TryGetLeaveJudge`**；Pipeline 用 Try | 无 Type / 未注册 → 不炸主路径 |
| Resolve 空列表仍算「已处理」 | **`resolved.Count == 0` → return false** | Specific/StarterPick 无数据、RoleGroup 空集交回既有路径 |
| ConfigPair 仅 assignee | engine **Activity** 存 Type/Params 字符串；assignee **读**定义后分发 | Convertor 解析 BPMN；策略实现仍在 assignee |
| 业务回调未单列 | **`useAssigneeBusinessCallback`** + `AssigneeBusinessCallbackRegistry` | `BusinessCallback` + `Params.callback` |
| Type 常量仅草稿子集 | 另有 `UnitMap` / `JobRelative` / `BusinessCallback` / `Expression` / `Fallback` | `AssigneeTypeCodes.cs` |
| 草案独立 `GroupRoles.cs` | **合入 `AssigneeTypeCodes.cs`** | — |

#### 5.6.2 engine 契约与 DTO（现行代码）

```csharp

// SailClient
```

| 类型 | 字段（现行） |
|------|----------------|
| `AssigneeInvokeRequest` | `ProcessId` · `Version` · `ProcessInstanceId?` · `ActivityId` · `ActivityCode` · `Runner` · `NextActivityPerformers` |
| `LeaveInvokeRequest` | `ProcessInstanceId` · `ActivityInstanceId` · `ProcessId` · `Version` · `CurrentActivityInstance` · `MainActivityInstance` · `ChildActivityInstances` · `Runner` |

#### 5.6.3 薄调用落点

| 时刻 | 位置 | 行为 |
|------|------|------|
| **A** | `NodeMediator.GenerateActivityAssignedUserInfo` | `pipeline?.TryResolve…` 成功且非空 → 写回 `NextActivityPerformers` + AssignedUser*；否则 Specific / Definition / … |

## 6. 内置 Type 清单与场景映射

### 6.1 时刻 A · Resolve（定范围 1–9）

| 场景 | Type | 落层 | Params 要点 |
|------|------|------|-------------|
| F1 传入 | `Specific` | 内置 | Runner 已传列表 |
| 1 固定人 | `FixedUsers` | 内置 | `users[]` |
| 2 流程相对 | `ProcessRelative` | 内置 | `relative`: Starter / PrevSender / … |
| 3 岗位相对 | `JobRelative` | 内置骨架 → 接 HR | `jobCode`；可 override 查找 |
| 4/6 单位 | `UnitMap` | 内置骨架 → 接映射 | `unitField` + maps；单位写入 GroupId |
| 5 群组/角色 | `RoleGroup` | 内置 | `roleIds[]`（经资源服务扩用户） |
| 7 缺省 | `Fallback` | 内置 | `onEmpty` + 可选下一 Type |
| 8 发起人自选 | `StarterPick` | 内置 + FE | `required`、`allowMultiGroup` |
| 审批人自选 | `ApproverPick` | 内置 + FE | 办理页写入载荷 |
| 9 业务动态 | `BusinessCallback` 或 `Business.*` | 回调注册表 / 业务类 | 如 `Business.ClassStudents` |
| 表达式 | `Expression` | 内置 | 从 Conditions 取值 |

第一维坐标系（扩展时先归类，再起 Type 名）：

```text
绝对钉死     → FixedUsers · RoleGroup
流程相对     → ProcessRelative
组织/人力    → JobRelative · UnitMap · Fallback
运行时补全   → StarterPick · ApproverPick · Specific
业务相对     → BusinessCallback / Business.*
```

### 6.2 时刻 B · Leave（办理模式）

| 模式 | Type | Params 要点 |
|------|------|-------------|
| 抢办 | `Race` | 完成≈1；可选认领语义 |
| 协办 | `Collaborate` | `completeCount` / `completeRate` |
| 组内抢办 | `GroupRace` | 按 GroupId；组内 1 人；`groupJoin` AND/OR |
| 组内协办 | `GroupCollaborate` | 组内人数/比例；可按身份过滤 |
| 队长 | `Captain` | `gateRoles` 默认 `["Leader"]` |

组间默认倾向 **全部完成 (AND)**；OR 须显式配置。

### 6.3 组合场景（扩展时的正确拆法）

**多单位发起人自选 + 组内抢办 + 组间 AND**（现场高频「怪需求」）：

```text
Resolve: StarterPick（或 Specific 已带矩阵）
  → Performer[] 每行带 GroupId=单位、GroupRole
Leave:   GroupRace + groupJoin=AND
```

**错误方向：** 在 Host 把多人拼成一个 `AssignedUserId` 字符串，或在 AIM 写「按单位拆任务」特例。  
**正确方向：** F1 传入结构化列表 + Leave 按组判定；任务/活动实例落库保留 Group* 以便 B 可读。

**班级学员签字（场景 9）：**

```text
Type = Business.ClassStudents（biz 样例）
Params.classIdField → 查学员 → Performer[]（GroupId=班级）
可继承 LookupStudents；勿改 engine
```

同码覆盖样例：biz `TenantCollaborateLeaveJudge` 覆盖 `Collaborate`。

## 7. 扩展指引（防走错）

### 7.1 允许

| 需求 | 做法 |
|------|------|
| 新定范围 | 新 `IAssigneeResolver`，唯一 Type 字符串，`useAssigneeResolver` |
| 改内置行为 | 继承非 seal 内置类，或同 Type 重新注册 |
| 接学籍/订单子表 | `Business.*` 或 `useAssigneeBusinessCallback` |
| 接 HR/单位主数据 | 扩展 `JobRelative` / `UnitMap`（override 查找），主数据在宿主 |
| 自定义完成公式 | 新 `IActivityLeaveJudge` 或覆盖 Leave Type |
| 表达式/规则算人 | `Expression` / 未来 ext 的 RuleSet Type，**仍是 Resolve Type** |

### 7.2 禁止

| 反模式 | 原因 |
|--------|------|
| 在 `NodeMediator` / AIM 增加「若流程码=XX 则…」算人 | 破坏薄调用与可测性 |
| 把定范围 + 抢办揉成**一个**下拉/一个 Type | 两维正交被破坏，组合场景无法表达 |
| Resolve/Leave Type 改成 **C# enum** 分发 | 业务无法无感加码；违反 string 铁律 |
| 内置类 `sealed` | 无法继承覆盖 |
| 用 Bool `IsLeader` 替代 GroupRole | 关卡身份无法扩展 |
| 空办理人静默当发起人/管理员 | 必须绑定 Fallback / onEmpty 策略 |
| 抄送/通知复用 Assignee ConfigPair | 语义污染 |
| 照搬芋道策略数字枚举进 pure | 与 Sail 载荷/身份模型不兼容 |

### 7.3 空结果与未命中

Resolve 得到空集或单位未命中时：**禁止静默**。通过 `Fallback` / Params.`onEmpty`（Error / Suspend / 再 Resolve）显式配置；部署期校验可作为 Host/校验器增强，但不替代运行时政策。

### 7.4 诊断（演进宜保留）

调试应能看到：Resolve/Leave 的 Type+Params、命中人数、GroupId/GroupRole、Leave Decision+ReasonCode、是否发生同码覆盖。缺诊断时优先补日志/结果字段，而不是加旁路。

## 8. 设计原则（摘要）

1. Client 两大时刻契约优先于一切旁路脚本。  
2. 三根基落在契约上：F1→A 透传；F2→B；F3→A 注册表。  
3. 策略配置与 Runner Specific **分离又协作**（Specific 是 A 的一种来源）。  
4. 定范围 × 办理模式正交 → **两套** ConfigPair。  
5. 单一真源在流程定义（BPMN），不靠前端临时状态。  
6. 算人与流出必须可解释。  
7. 空办理人 / 未命中不可静默。  
8. 用户身份、单位→GroupId、HR、GroupRole **勿混为一谈**。  
9. 扩展只挂注册表；Type 仅 string；后写覆盖；内置不 seal。
