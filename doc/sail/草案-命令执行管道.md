# 草案 · 命令执行管道（Middleware 思想引子）

> 状态：**草案 / 未立项**（2026-11-02）  
> 用途：从 Elsa Workflow/Activity **执行中间件链**对照中抽出可吸收点，供后续「命令入口 DRY / 引擎横切」挂钩；**不**纳入现行能力基线，**禁止**用通用中间件替换 Gate/Hook 产品语义。  
> 灵感来源：elsa-core `WorkflowExecutionPipeline` / `ActivityExecutionPipeline`（ASP.NET 式洋葱模型）；对照 Sail `WorkflowService` 各动词 + `WorkflowCapabilityPipeline.TryGate` + Gate/Hook/Notifier。  
> 关联：[特性设计-回调与事件.md](./特性设计-回调与事件.md) · [业务管道特性设计.md](./业务管道特性设计.md) · [草案-挂起与统一Resume.md](./草案-挂起与统一Resume.md) · [特性说明-引擎能力基线.md](./特性说明-引擎能力基线.md)

---

## 1. 一句话

在 **WorkflowService 办理命令入口** 外包一层薄的「执行管道」（可叫 Command Pipeline，不必叫 Middleware）：统一异常/结果形态、诊断指标、并**适配调用**现有 Gate——**不**再造业务钩子，**不**改 NodeMediator 调度内核。

---

## 2. 为什么要记一笔（问题）

Elsa 在「跑一次工作流 / 跑一个活动」上使用可组装中间件：

```text
Workflow：ExceptionHandling → ActivityScheduler → …
Activity：ExceptionHandling → Invoker（可加 Logging / Notifications）
```

横切（异常、日志、指标）挂在管道上，Activity 实现保持干净。

Sail 侧**业务横切已经正确拆开**（见回调设计）：

```text
命令 → Gate（可 Reject）→ 写库/AIM/Mediator → Hook → Notifier/Outbox
```

痛点不在缺 Gate，而在：

1. **命令入口样板重复**：`Start/Run/SendBack/Withdraw/…` 各自 `BuildGateContext` + `TryGate` + try/catch，新动词继续复制。  
2. **引擎级横切无处安放**：关联 Id、耗时、CapabilityMetrics、审计若再加，易继续散落或渗进 Mediator。  
3. **概念易混**：若直接「上 Elsa Middleware」，容易把财务 Gate Reject 做成异常管道，毁掉已拍板的三轨语义。

---

## 3. 边界（红线）

| 做 | 不做 |
|----|------|
| 装饰 **命令入口**（WorkflowService 动词 / 等效 ExecuteCommand） | **不**用中间件替代 `UseFlowGate` / `UseFlowHook` / Notifier |
| 管道内 **调用** 现有 `TryGate`（适配器） | **不**把 Reject 改成抛异常当失败 |
| 引擎诊断：耗时、Metrics、Correlation | **不**在 Mediator 里堆全局埋点替代管道 |
| 命名可用 Command Pipeline | **不**为对齐 Elsa 上 ActivityScheduler 级整链 |
| 与 Wait/Resume 草案正交：Resume 成功后仍可走本管道 | **不**把 UserTask Leave / Assignee 塞进中间件 |

与 [存疑参考功能点.md](./存疑参考功能点.md) 同态度：外来形态先记边界，默认不进基线 API 面。

---

## 4. 和现有三轨的分工

| 机制 | 层 | 时机 | 失败语义 |
|------|-----|------|----------|
| **Command Pipeline（本草案）** | 引擎运输层 | 每次命令执行外包 | 系统异常规范化；**透传** Gate Reject |
| Workflow Gate | 产品校验 | 推进落库前 | `HookResult.Reject` → `WfExecutedResult` |
| Workflow Hook | 产品业务 | 推进中/后 | FailFast / Outbox |
| Task Notifier | 旁路通知 | 待办生命周期 | 默认 AsyncOutbox |

```text
┌─ Command Pipeline（可选洋葱）─────────────────────┐
│  Exception / Result 规范化                         │
│  Diagnostics（耗时 / Metrics / Correlation）       │
│  GateAdapter → 现有 TryGate                        │
│  ┌─ Core Delegate ─────────────────────────────┐ │
│  │  真正的 Run/SendBack/…（AIM / Mediator）      │ │
│  │  路径内仍触发 Hook / Outbox（保持现行语义）   │ │
│  └─────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
```

**学洋葱外壳，不学换心。**

## 5. 目标形状（概念，非 API 定稿）

```text
ExecuteCommand(operation, runner, core: Func<…, WfExecutedResult>)
  → 管道头：进入诊断
  → GateAdapter（BuildGateContext + TryGate；Reject 则短路返回）
  → core()          // 现有各动词主体，逐步迁入
  → 管道尾：耗时、Metrics
  → 返回 WfExecutedResult
```

开放命名：`ICommandExecutionPipeline` / `WorkflowCommandPipeline` / 内部 `ExecuteWithPipeline`——**立项时再定**。

### 5.1 建议管道槽位（由外到内）

| 顺序 | 槽位 | 说明 |
|------|------|------|
| 1 | Exception / Result | 区分事故异常 vs 已构造的 ExecutedResult；避免吞掉 Reject |
| 2 | Diagnostics | Correlation、耗时、`IWorkflowCapabilityMetrics` |
| 3 | GateAdapter | **仅适配**现有 Gate；无注册则透传 |
| 4 | Core | 命令主体 |
| （可选后置） | 审计只读 | 成功/拒绝码落审计；**不**再跑业务 Hook（Hook 仍在 core 内） |

Activity/Mediator 级 Elsa 式 Invoker 链：**不在本引子范围**（调度模型不同）。

## 6. 建议分期（仅路线图，未排期）

| 阶段 | 内容 | 验收直觉 |
|------|------|----------|
| **C0 本稿** | 文档引子 + 红线 | 评审认同「管道 ≠ Gate」 |
| **C1 内聚** | 抽 `ExecuteCommand` 私有辅助，1～2 个动词（如 Run + SendBack）去样板 | 行为与现网一致 |
| **C2 槽位** | Diagnostics + Metrics 正式进管道 | 指标不进 Mediator |
| **C3 全动词** | 其余 Start/Withdraw/… 迁入 | 入口无重复 TryGate 样板 |
| **C4** | 与 [草案-挂起与统一Resume.md](./草案-挂起与统一Resume.md) 的 Resume 入口复用同一外壳（若已立项） | 自动续跑也可观测 |

任一阶段若把业务校验改挂「自定义中间件」而绕开 `UseFlowGate`，**停**并退回红线。

## 7. 与 Elsa / DependsOn / Resume 的关系

| 主题 | 关系 |
|------|------|
| Elsa Middleware | 形态参考（洋葱 + Use 组装）；不搬 Activity 调度管道 |
| Feature DependsOn | Build 期组合；本草案是 Run 期入口 |
| Wait / Resume | 挂起恢复；Resume 外可套同一 Command Pipeline |
| SailClient UseXxx | 管道若可配置，优先挂 Client/Builder，避免静态全局 |
