# 讨论 · 办理人「操作模式 × 人员范围」是否正交

> 状态：**讨论稿**（2026-11-26；Mode×Scope；对象解析器；动词代表；**§12 IStorage 库连接器**）  
> 用途：办理人正交与对象解析相关讨论；并收录引擎侧存储分层口述；**不**改代码、不升格基线。

## 1. 一句话结论

**现状**：模式与范围折叠在同一 `assigneeResolve.type` 里，并非二维配置。  
**收敛方向（本稿倾向）**：Type = 人员集合（Scope）；另挂闭集 Mode（选人 / 固定 / 超前选）。固选与预选对引擎是**同形取人契约**，实现交注册解析器；拿到办理对象即走下一步。选人 = 参数必备人员。存储偏 **`mode` 属性旁挂**（§6.5）。  
**延伸（§10）**：对象解析器（Mode×范围×存储×跨动词）；**动词代表类**见 §10.7。  
**存储管理（§12）**：按表 `IStorage<T>` 纯库交互层；`kit` 首参；敏感路径专属 API；默认实现在 ext；唯一注册、后注册覆盖；引擎仿 DI、宿主真 DI。

## 2. 你的心理模型（本稿采纳为讨论坐标系）

### 2.1 操作模式（何时 / 如何定人）

| 模式 | 口语 | 含义 |
|------|------|------|
| **固定** | 无需选择 | 节点到达时按规则直接得到办理人全集，办理条不必再选 |
| **发送前选人** | 当次自选 | 发送（或发起）当次由操作者从候选中挑选，写入本次流转载荷 |
| **其它时刻预设置** | 预选 / 超前选人 | 在到达该节点之前的某一时刻已定好人（发起时、管理改表、上游节点写入预选仓等），到达时只读表派发 |

三者差在**定人时刻与是否人工介入**，不差在「人从哪一类集合来」。

### 2.2 人员范围（人从哪圈定）

按集合定义手段圈定候选或全集，例如：

| 范围手段 | 含义（示例） |
|----------|--------------|
| 固定用户列表 | 直接钉死若干账号 |
| 角色 / 群组 | 展开角色或群组成员 |
| 部门 / 单位 | 部门成员、单位映射、部门领导链 |
| 岗位 | 相对岗位、编制岗 |
| 流程相对 | 发起人、上一发送人等 |
| 表达式 / 业务回调 | 表单字段、宿主算法 |

### 2.3 正交命题

```text
操作模式 × 人员范围  →  可笛卡尔组合

例：范围 = 群组 G
  · 固定     → G 内全部人皆为办理人（无需再选）
  · 发送前选 → 发送人从 G 成员中挑选
  · 预选     → 更早时刻已从 G 成员中挑好，到达时读预选结果
```

**模式不改变范围定义；范围不强制某一种选人时机。**  
Leave（或签/会签/组/队长）仍是**第三维**，与上表无关。

## 3. 现行 sailflow 实际长什么样

### 3.1 已落地的正交轴（与本稿命题不同维）

权威基准见 [特性说明-待办人管道.md](../特性说明-待办人管道.md)：

| 轴 | BPMN / 契约 | 职责 |
|----|-------------|------|
| **Resolve** | `sf:assigneeResolve` | 时刻 A：创建待办前算出 `Performer[]` |
| **Leave** | `sf:leaveJudge` | 时刻 B：办完能否离开 |
| **后置** | Filter / EmptyAction（R10） | 同人、去重、空人拒绝/换人/锚点；**禁止**做成新 Resolve Type |

这是现行架构的硬正交；**不要**把「模式×范围」误写成与 Leave 抢同一套 ConfigPair。

### 3.2 Resolve Type：模式与范围被压进同一枚举

内置码见 `AssigneeResolveTypeCodes`（宿主另有 `deptBoss` 等）：

| Type | 更偏「范围」 | 更偏「模式/时机」 | 说明 |
|------|--------------|-------------------|------|
| `FixedUsers` | ✅ 固定用户 | （隐含固定派发） | Params `users[]` |
| `RoleGroup` | ✅ 角色/群组展开 | （隐含固定派发：展开后全员） | Params `roleIds` |
| `UnitMap` | ✅ 单位映射 | 固定派发 | |
| `JobRelative` | ✅ 岗位 | 固定派发 | |
| `ProcessRelative` | ✅ 流程相对人 | 固定派发 | |
| `Expression` / `BusinessCallback` | ✅ 动态范围 | 固定派发（算完即派） | |
| `StarterPick` | （范围不在 Type 内） | ✅ 发起时当次自选 | 只吃当次 `NextActivityPerformers` |
| `ApproverPick` | （范围不在 Type 内） | ✅ 发送人当次自选；**R6 出厂默认** | 同上实现路径 |
| `Specific` | — | ✅ F1 透传 | 调用方已传入 |
| `Preselect` | （范围不在 Type 内） | ✅ 实例级预选表 | 须宿主 `UsePreselectAssignees` |
| `Fallback` | 组合器 | — | 主策略空后再 Resolve 另一 Type |

文档 §6.1「第一维坐标系」已按**绝对钉死 / 组织人力 / 运行时补全…**分类，但实现上仍是**互斥单选 Type**，不是两字段相乘。

### 3.3 与口语模式的对照

| 你的模式 | 现行落点 | 是否独立配置轴 |
|----------|----------|----------------|
| 固定（无需选择） | `FixedUsers` / `RoleGroup` / `UnitMap` / `JobRelative` / `deptBoss` / … | ❌ 每种范围一个 Type；「固定」是这些 Type 的隐含行为 |
| 发送前选人 | `ApproverPick`（及 `StarterPick`） | ❌ 选 Type=`ApproverPick`；候选范围另靠角色预览 / 选人器 / 宿主 |
| 其它时刻预设置 | `Preselect` + `IPreselectAssigneeStore`；另有 AI `ai_nxt_perf` 网关短缓存（非通用预选仓） | ❌ 另选 Type=`Preselect`，与 RoleGroup **不能**同节点双 Type |

### 3.4 设计器侧的「弱正交」

宿主面板（`SailNodeConfigPanel`）常见三块：

1. **待办人·定范围** → `assigneeResolve` Type + Params  
2. **运行时·选人器** → `candidateSelectorType`（`HostUserSearch` / `InlineList` / `RoleUserSearch`）— 注释写明**与 AssigneeResolve 正交**  
3. **办理模式** → `leaveJudge`

选人器解决的是：**当 Type 需要人机挑选时，UI 怎么搜人**；它**不**写入引擎 Resolve 管道，也**不能**把「ApproverPick + RoleGroup」声明成引擎可校验的契约。

宿主下一跳预览（如 `SleveenUserIdentity`）常靠节点角色展开人数推导 `CandidateMode`（bound / search / anyselect）——范围在**产品侧旁路**，不在标准 Resolve Params 契约里与 Pick 成对。

## 4. 直接回答：当前是如此吗？

| 命题 | 判定 | 说明 |
|------|------|------|
| 模式 × 范围在概念上正交 | **同意（产品直觉）** | 固定/选人/预选与集合定义手段本可独立组合 |
| 现行引擎已按二维配置实现 | **否** | 单字段 `assigneeResolve.type`；组合靠换 Type 或宿主 UX |
| 固定群组 = RoleGroup 全员派发 | **基本是** | `RoleGroup` ≈「范围=角色 + 模式=固定」的打包 |
| 发送前从群组内选 = ApproverPick + 群组范围 | **产品上常能凑** | 靠选人器 / 角色候选；**BPMN 无标准「范围」字段与 Pick 绑定** |
| 预选从群组内提前挑 = Preselect + 群组范围 | **部分是** | Preselect 只管「从表取人」；写入预选表时的候选范围是宿主面板职责 |
| Resolve × Leave 正交 | **是（已定型）** | 勿与模式×范围混为一谈 |
| 空人/同人/去重是第四种「模式」 | **否（R10）** | 后置策略，禁止注册成 Resolve Type |

**一句话给产品：**  
正交坐标系正确；今日是 Type 打包。**下一步不必重做集合算人**——把 Type 当成 Scope，外挂闭集 Mode 即可（见 §6）。

## 6. 收敛方案 · Mode 外挂、Type=集合（倾向）

> **未立项**；与 R2 单轨、R4 禁暗默认、R6 设计默认、R10 后置三分兼容。  
> 相对旧稿选项 A/B/C：本稿**采纳「Mode 外挂」**——不重写集合 Resolver，也不再发明 ScopedPick 组合 Type。

### 6.1 核心命题

1. **现行所有 Resolve Type，均可视为人员集合 Type（Scope）**——负责「圈出一集人 / 定义候选宇宙」。  
2. **Mode 几乎固定，不需扩展注册表**：仅三态。  
3. 增量落在 **设计器 + 判定层**；集合 Resolver 实现尽量不动。  
4. **执行引擎视角**：固定与超前选都是「已有项集 → 派发」；选人则「参数必备人员，否则拒」。

### 6.2 Mode 三态（闭集）

| Mode | 口语 | 执行引擎语义 | 项集来源 |
|------|------|--------------|----------|
| **Fixed** | 固定 / 固选 | 已有项集，直接派发 | 注册解析器按 Scope Type 展开 |
| **Preselect** | 超前选 | **与 Fixed 同形取人**；实现交 pre 解析器 | 先预选仓；**取空时可否看入参**见 §10.2（须显式，默认建议拒） |
| **Pick** | 选人 | **参数必备人员**；空则 R4 拒绝 | 当次入参；Scope 仅候选/越权 |

### 6.2.1 实现路径思路（定稿倾向）

**引擎不内建「固选算法 / 预选算法」两套分支。**  
Fixed 与 Preselect 只是**两个名字不同、形状相同的取人契约**：

```text
契约形状（同构）
  入：ActivityId / 实例语境 / Scope ConfigPair（type+params）/ Runner…
  出：PerformerList（办理对象项集）| 空

名字（Mode）只用于：
  · 选哪一个已注册的解析器（或同一接口下的哪条注册键）
  · 设计器 / 判定层文案与校验策略
```

```text
时刻 A
  ① 按 Mode 找到「取人契约」实现
       Fixed     → 注册表[Scope.type]     （RoleGroup / FixedUsers / …）
       Preselect → 注册表[Preselect键]    （宿主 Store 解析器；形状同 IAssigneeResolver）
       Pick      → 读请求参数中的人员；空则拒（可视为第三契约：MandatoryPerformers）
  ② 拿到 PerformerList（办理对象）
  ③ 其后与今日相同：EmptyAction / Filter 链 → 建待办 → 往下走
       ▲ 引擎核心只认「已有项集」，不再区分这批人从 Scope 展开还是从预选表来
```

要点：

1. **固选 ≈ 预选（对引擎）**：同形契约；实现**全部交给注册解析器**，Mediator / Pipeline 主干不写 if (Preselect) 特判业务。  
2. **拿到办理对象即走下一步**：时刻 A 的唯一产品是 `PerformerList`；后续 Leave、R10、建 Task 与 Mode 无关。  
3. **Pick 仍是例外入口**：不「算人」，只**断言参数已带人**；可选再调 Scope 解析器做 ⊆ 校验（校验也是注册能力，不是内核分支）。  
4. **与现行对齐**：今日 `IAssigneeResolver.Resolve → PerformerList` 已是该形状；收敛后只是把 Mode 从「伪装成 Type」里拆出去，Preselect 继续当**一个注册实现**，而不是管道第三轨。
### 6.3 Type 重归类（集合 vs 历史模式码）

| 现行 Type | 收敛后角色 | 备注 |
|-----------|------------|------|
| `FixedUsers` / `RoleGroup` / `UnitMap` / `JobRelative` / `ProcessRelative` / `Expression` / `BusinessCallback` / `deptBoss` / `Business.*` | **纯 Scope** | Mode=Fixed 时 = 今日行为；Mode=Pick/Preselect 时 = 候选宇宙 |
| `ApproverPick` / `StarterPick` | **废弃为 Mode，不再作 Type** | 映射：Mode=Pick；谁在选（发起/发送）可由子字段或办理语境区分，不必两个 Scope |
| `Preselect` | **废弃为 Mode，不再作 Type** | Mode=Preselect；Store 仍要，但不占 Type 槽 |
| `Specific` | **Mode=Pick 的载荷通道** 或保留为透传 Scope | F1「传入即派」≈ Pick 且已带人；可不再单独暴露给设计器 |
| `Fallback` | **仍属集合/策略组合器** | 与 Mode 正交；或仅挂在 Scope 链上 |

存量 BPMN：无 Mode 属性时，**推断**——

| 旧 Type | 推断 Mode | 推断 Scope |
|---------|-----------|------------|
| RoleGroup / FixedUsers / … | Fixed | 自身 |
| ApproverPick / StarterPick | Pick | 缺省空集合或节点 Roles→RoleGroup |
| Preselect | Preselect | 同上（候选来自设计期另配 Scope，若无则任意/宿主默认） |

### 6.4 落层：谁改、谁几乎不改

| 层 | 做什么 |
|----|--------|
| **设计器** | 先选 Mode（三态），再选 Scope Type + Params；选人器仅在 Mode=Pick（及 Preselect **写入** UX）出现 |
| **判定层**（发布校验 / ProbeNext / 办理条） | Mode=Pick → 未选人不可发；Mode=Fixed/Preselect → 可免选手动；Preselect 未写入 → 设计/发起期拦截 |
| **执行管道** | Mode → 选注册解析器（或 Pick 读参）→ **统一** `PerformerList` 之后路径；**禁止**为 Preselect 另开派发轨 |
| **Leave / R10** | 不动 |

干扰面评估：**小**——内核只多「按 Mode 选契约实现」；固选/预选同形；集合 Resolver 签名可不变；BPMN Mode + 设计器/判定 + 存量推断。
### 6.5 存储形态（**偏 A · 属性旁挂**）

**A. 属性旁挂（本稿选定倾向）**

```xml
<sf:assigneeResolve type="RoleGroup" mode="Pick"
  params='{"roleIds":["R_MGR"]}' />
```

- `type` = Scope（与今 Resolver 注册键一致）  
- `mode` = Fixed | Pick | Preselect（闭集，**禁止**当扩展 Type、**禁止**塞进 params 冒充）  
- Convertor / Activity 实体增读 `mode`（或 `AssigneeResolveMode`）；缺省按 §6.3 存量推断  
- 判定层、设计器、管道分发均读属性，不与业务 Params 键冲突

**B. 仅 Params（不采纳为默认）**

```json
{ "mode": "Pick", "roleIds": ["R_MGR"] }
```

- 少改 Convertor，但 Mode 易被业务 Params 污染；仅可作迁移过渡读，正式契约以 **A** 为准。

### 6.6 与旧选项关系

| 旧选项 | 关系 |
|--------|------|
| A Params 约定 | 被 §6.5B 吸收；但 Type 仍混模式码时不够干净 |

## 7. 易混清单（讨论时先对齐用词）

| 勿混 | 说明 |
|------|------|
| 操作模式 ≠ Leave 办理模式 | 前者何时定人；后者几人办完能走 |
| 操作模式 ≠ NodePolicy 空人/同人 | 后者是 R10 后置 |
| Fixed 与 Preselect（引擎） | Load 同形；**存储不同**：Fixed 不存，Preselect 必存（§10.6） |
| fix.Load vs fix.Store | 相反方向；Pick 可选落库时走 fix 的 Store/Load，Fixed 禁止 Store |
| Scope 解析 vs Mode Store | 范围只圈人；落库是 Mode 处理器职责，不进 Scope |
| `FlowOperation` vs Button Id | 引擎 Gate 枚举 vs 宿主办理按钮编码；非 1:1（如 Copyto、Start） |
| `ActionMethodEnum` vs OA 动词 | 服务任务/脚本动作 ≠ 转办/沟通等办理动词 |
| `contexts` vs 人员范围 Scope | 办理台语境（handle/done/admin）≠ RoleGroup 等取人范围 |
| Pick ≠ 选人器控件 | Pick 是 Mode；选人器是 UX |
| 旧 `StarterPick`/`ApproverPick`/`Preselect` Type | 收敛后是 **Mode**，不是 Scope |
| `RoleGroup` 的 Group ≠ R1 办理分组 GroupId | 角色展开 vs 会签组身份 |
| `ai_nxt_perf` ≠ Preselect 仓 | 网关短缓存 vs 实例预选表 |
| Fallback ≠ 空人 EmptyAction | 再算人 vs 处置空集 |

## 10. 概念延伸 · 对象解析器（整理）

> 本节整理后续口述思路，与 §6 正交模型衔接；**仍为讨论，未改代码**。

### 10.1 概念 1 · 对象解析器

**对象解析器**：负责输出**办理对象**（如 Task 执行人 / 某动词的目标人列表）。  
对内组合三类概念：

| 内含 | 职责 |
|------|------|
| **模式（Mode）** | 如何对待入参与预存项集（见 §10.2） |
| **范围解析器（Scope）** | 圈定候选宇宙或固定全集（见 §10.3） |
| **适用范围** | 本解析配置适用于哪些动词 / 节点 / 场景（发送下一跳、转办目标、加签对象…） |

对外只承诺：**入语境 → 出办理对象项集**；拿到项集后由动词 Lane / Mediator 继续业务（建待办、改签、沟通阅办等）。

与 §6.2.1 对齐：固选 / 预选仍是**同形取人契约**；对象解析器是把该契约**提升为跨动词可复用的一等概念**，而不仅挂在「创建待办前时刻 A」。

### 10.2 模式细化（相对 §6.2 的补丁）

| Mode | 传参要求 | 入参（如 `NextActivityPerformers`） | 注册实现（示意名） |
|------|----------|-------------------------------------|-------------------|
| **Fixed（固定）** | 不传参、**不看入参** | 忽略 | **fix 解析器**：只走范围展开 |
| **Pick（自选）** | **要传参**；主要使用传入参数 | 必备；空则拒 | 可视为「断言入参」契约；范围用于候选/越权 |
| **Preselect（预选）** | 通常不传参 | **取不到预选时再看入参**（回落） | **pre 解析器**：先 Store，空则可选读入参 |

相对此前「Fixed≡Preselect、只差来源」的表述：Preselect 增加**显式回落策略**（Store 空 → 入参）。是否启用回落须可配置，避免与 R4「禁暗默认」冲突——回落应是**声明行为**，不是静默成功。

```text
对象解析器.Load(ctx)     —— 取人（见 §10.6 与存储关系）
对象解析器 / Mode 侧.Store(ctx, 项集)  —— 仅 Pick(可选) / Preselect(必选) 写入路径
```

Load 分派细则与是否读库见 **§10.6**。

### 10.3 范围解析器 · 内置 vs 外置

| 种类 | 典型内容 | 归属 | 规则 |
|------|----------|------|------|
| **内置** | 流程相关对象范围：发起人、上一发送人、流程相对人、表达式读 Conditions、FixedUsers 字面量等 | pure / assignee 可带骨架 | **内置、可覆盖**（同码后注册，守 R9） |
| **外置** | 组织、岗位、角色、群组、部门领导等业务属性范围 | **必须由宿主注册** | 引擎不塞宿主 HR schema（守 R3） |

与今日对照：`ProcessRelative` / `Expression` / `FixedUsers` ≈ 内置向；`RoleGroup` Lookup、`UnitMap`、`JobRelative`、`deptBoss` ≈ 外置向（骨架可在 pure，真数据在宿主）。  
**范围解析器只负责「一集人」**；不决定 Mode，也不执行转办/加签副作用。

### 10.4 概念 2 · 跨 OA 动词复用

对象解析器独立后，**不局限于发送动作**。凡需「先拿到一批执行/目标对象再办事」的动词，均可调用：

| 动词（示例） | 今日取人现状（摘要） | 对象解析器适用性 |
|--------------|----------------------|------------------|
| 发送 / 下一跳建待办 | `IAssigneePipeline.TryResolveForTaskCreate` | ✅ 主场；Mode+Scope 全用 |
| 转办 Transfer | Lane 展平 `NextActivityPerformers`，缺人即错 | ✅ 多为 Pick；可挂范围校验 |
| 加签 / 减签 / 改派 | 同上，入参必备 | ✅ 同上 |
| 委托 / 沟通 | 入参取目标人 | ✅ 同上；沟通产物是参与者角色，仍是「对象列表」 |
| 退回 | 目标多为历史节点办理人，选人规则不同 | △ 可用 Loader，但 Scope/Mode 常另套（历史轨迹） |
| 抄送 | 产品表 / 独立通道 | ⚠️ **可借用「解析出人」能力，禁止写入办理 Performer[]**（**R5**） |
| 通知 | Task Notifier | ❌ 不走办理对象解析器（R5） |

```text
各动词 Lane / 命令
  → AssigneeLoader（或共享内核）拿到对象[]
  → 本动词业务（建待办 / 改签 / 写沟通 / …）
```

**价值**：选人校验、范围展开、预选回落、空人策略，从各 Lane 复制粘贴收拢到一处。  
**边界**：动词差异在「拿到人之后」；不要把 Transfer 的业务写进 Scope。

### 10.5 设计 3 · `AssigneeLoader<T>` 形态草案

```text
abstract class AssigneeLoader<TParams>
  TParams : 本动词解析参数体

  Load(TParams p) → PerformerList（或更中性的 AssigneeObject[]）

子类（按动词，示意）
  SendAssigneeLoader
  TransferAssigneeLoader
  RejectAssigneeLoader
  ConsultAssigneeLoader
  DelegateAssigneeLoader
  AddAssigneeLoader
  …
```

**参数体建议四类信息**（可组成基类字段 + 动词扩展）：

| 类 | 内容（示例） | 用途 |
|----|--------------|------|
| **流程配置** | 定义 Id/版本、节点 `assigneeResolve`（mode+type+params）、Leave 不在此强塞 | Mode/Scope 从哪读 |
| **流程实例信息** | PI / AI / TaskId、当前活动、历史办理人 | Preselect 键、退回目标、相对人 |
| **业务标识** | 业务单号、表单键、宿主业务码 | Expression / BusinessCallback / 外置 Scope |
| **Kit 事务承载体** | 发送同事务 `SQLBuilder` / UoW | Store 读写、锚点入队与 R10 同事务 |

子类差异预期：

- 默认 Mode（发送看节点配置；转办默认 Pick）  
- 入参是否必备、空时 ReasonCode  
- 适用范围过滤（本动词是否允许 Fixed）  
- 输出后是否还要带 GroupRole 等（沟通参与者）
- 是否调用 Mode 侧 **Store**（预选面板写入、自选落库等）

### 10.6 对象解析器 · 存储策略（按 Mode）

> 引擎**核心只定契约与分派**；**表实体、SQL、默认实现**放在 **引擎扩展 ext**（内置一份可运行默认），**允许宿主继承并修改**。不把具体表名塞进 pure。

#### 10.6.1 总表

| Mode | 是否存储 | Load（取办理对象） | Store（写入） |
|------|----------|-------------------|---------------|
| **Fixed** | **不存储** | **永远**直接执行**范围解析器** → 返回；无视入参、不读库 | **无**（禁止写办理人持久化；配置在 BPMN） |
| **Pick** | **可不存，也可存**；**引擎不定死** | 不存 → **直接用入参**；存 → 返回「已选择结果」（优先级由 **fix 解析器实现侧**自定，见下） | 若启用存储 → 由 **fix 解析器**写入 |
| **Preselect** | **必存** | 从存储 **Load** | 预选期间由 **pre 解析器**写入；使用时再 Load |

```text
Fixed
  Load  → Scope.Resolve(...) → 项集
  Store → （无）

Pick（persist=false | 引擎未要求存）
  Load  → 入参项集（必备）
  Store → （无）

Pick（persist=true）
  Store → fix.Store(选择结果, ctx)     // 写入方向
  Load  → fix.Load(ctx)                 // 加载方向；与入参的优先级由 fix 实现决定
         （实现可：库优先 / 入参优先 / 合并；须可文档化、可观测）

Preselect
  Store → pre.Store(预选结果, ctx)      // 预选期间写入
  Load  → pre.Load(ctx)                 // 使用时加载；空是否回落入参见 §10.2，须显式
```

#### 10.6.2 fix / pre：加载与存储两路相反方向

**fix 解析器**、**pre 解析器**在契约上同形，均带**双向**：

| 方向 | 语义 | 典型调用方 |
|------|------|------------|
| **Load** | 语境 → 办理对象项集 | 发送建待办、动词取目标人 |
| **Store** | 办理对象项集 + 语境 → 持久化 | 预选面板提交；自选且开启落库时的确认写入 |

```text
IFixAssigneeModeHandler / IPreAssigneeModeHandler（示意名）
  Load (ctx) -> PerformerList
  Store(ctx, performers) -> void | Result
```

- **同形**：都是「项集 ↔ 某处」；差别在名字、是否必存、Fixed 是否参与（Fixed **不挂 Store**，Load 只接 Scope）。  
- **相反方向**：Store 写入，Load 读出；引擎核心**不**实现表访问，只调注册实现。  
- **Pick 落库走 fix**：口述约定——自选启用存储时，**写/读持久化选择结果由 fix 解析器负责**（与 Fixed 的「只 Scope、不落库」共用「fix」名空间时，实现上宜拆清：`LoadFromScope` vs `LoadOrStorePicked`，避免一个类两种语义缠死；见 §11.2.7）。

#### 10.6.3 分层落位

| 层 | 放什么 | 不放什么 |
|----|--------|----------|
| **pure / 核心契约** | Mode 枚举；`Load`/`Store` 接口；Fixed 禁止 Store；Pick 是否 persist 由配置/宿主策略传入，**不定死**；Preselect 缺 Store 实现 → 硬失败 | 具体表、实体、迁移脚本 |
| **ext（引擎扩展）** | 预选/自选落库的**默认表 + 默认 fix/pre 实现** | 宿主 HR 组织模型 |
| **宿主** | 继承/覆盖默认实现；换表、加审计字段、换库 | 改 Mediator 算人分支 |

与今日对照：现有 `IPreselectAssigneeStore` + 宿主表 ≈ Preselect 必存路径的雏形；Pick 落库、fix 双向契约尚待概念对齐后补。

#### 10.6.4 与「入参」关系（Pick）

| persist | Load 行为 |
|---------|-----------|
| 关 | **仅入参**；空 → 拒（自选必备参） |
| 开 | **fix.Load** 返回已选结果；入参与库的**优先级由 fix 实现自定**（引擎不定死） |

建议实现侧至少文档化一种默认（例如「当次入参非空则覆盖并可选回写 / 否则读库」），并打日志，避免「有时用库有时用入参」不可查。

## 11. 客观建议（中肯对照）

### 11.1 值得采纳的部分

1. **「对象解析器」一等化**：与 §6「拿到项集即走下一步」一致，且补上今日缺口——OA 动词 Lane 大量直接啃 `NextActivityPerformers`，发送才走管道，**校验与范围能力不对称**。  
2. **范围内置 / 外置划分**：与 R3（主数据在宿主）同向；写进文档可减少「RoleGroup 到底算不算 pure」的扯皮。  
3. **参数四类（配置 / 实例 / 业务 / Kit）**：与现行 `AssigneeInvokeRequest`（Runner、NextActivityPerformers、Kit…）同构，升级时有迁移锚点。  
4. **固选 fix / 预选 pre 注册实现**：继续落实「同形契约、名字不同」，避免 Mediator 特判。  
5. **存储按 Mode 分层（§10.6）**：Fixed 永不落库、Preselect 必存、Pick 可选——边界清晰；契约在核心、默认实现在 ext、宿主可覆盖，符合现有分层习惯。  
6. **Load/Store 双向**：比「只有 Resolve」更完整，能覆盖预选面板写入与自选落库，而不把写库塞进 Scope。  
7. **动词代表类（§10.7）**：把按钮码表从「启用+改名」升级为带 Mode/Scope/展示元数据的描述符，能直接喂对象解析器与办理条，结束 OperationBar 硬编码与取人配置分裂。

### 11.2 需要收紧或降风险的部分

1. **预选空时看入参**  
   - 产品上合理（发起未预选完、办理人补传）。  
   - 须**显式开关或 Mode 子策略**（如 `preselectFallback=Input|Reject`），默认建议 **Reject**（贴 R4）；打开回落要可观测 Reason/日志，禁止静默。  

2. **抄送进「对象解析器」**  
   - 解析「抄送候选人」可以共用 Scope 展开。  
   - **输出通道必须分流**：抄送人 → 抄送表/事件，**不得**进入办理 `Performer[]` / 待办 SignIds（**R5 硬边界**）。建议接口上用不同结果类型或 `Usage=Assignee|Copyto`，避免一个 `Load` 被误接到建待办。  

3. **按动词一个 `AssigneeLoader` 子类**  
   - 优点：动词默认值、校验文案清晰。  
   - 风险：子类膨胀、逻辑复制；退回/跳转等「目标人」语义与发送差异大，硬塞同一抽象会别扭。  
   - **建议形态**：  
     - **共享内核** `IAssigneeObjectResolver`（Mode × Scope，§6+§10.1）  
     - **动词适配器**（薄）：只声明「是否允许 Fixed / 入参是否必备 / 结果用途」  
     - 不必先上完整 `AssigneeLoader<T>` 类树；若上，优先 **Send + Transfer + AddAssignee** 三个试点，退回单开。  

4. **Fixed「完全不看入参」**  
   - 与防篡改、防前端误传一致，建议坚持。  
   - 若现场要「固定范围但允许追加」，应是**另一 Mode 或 Params 开关**，不要悄悄读入参。  

5. **适用范围**  
   - 宜做成配置/策略位（哪些动词可用该节点解析配置），避免一个巨型解析器内 `if (verb==Transfer)`。  
   - 节点上的 `sf:assigneeResolve` 默认服务**发送下一跳**；转办等可「复用同一 Scope 做候选校验」或「动词级覆盖配置」，需产品拍板，勿默认处处读同一 XML。  

6. **与现行管道关系**  
   - 短期：对象解析器 = 对 `IAssigneePipeline` 时刻 A 的**概念升级 + 向 Lane 侧输出同一能力**，不要并行再造第三套算人轨（守 R2）。  
   - Leave / R10 Filter 仍在「项集取出之后」，不塞进 Loader 内冒充 Mode。

7. **Pick 落库挂在「fix 解析器」上的命名**  
   - 产品语义成立：自选结果也是「已固定下来的选择快照」。  
   - 风险：与 Mode=Fixed「永不存、只跑 Scope」共用「fix」一词，实现者易把 `Load` 写成「有库读库否则 Scope」。  
   - **建议**：契约上保留 **FixModeHandler / PreModeHandler** 两个注册键；类型内部分方法或拆接口：  
     - Fixed 路径只暴露 `LoadFromScope`  
     - Pick 持久化路径暴露 `StorePicked` / `LoadPicked`（可仍由同一扩展包类实现）  
     - 文档与 API 名避免「Fixed 也会 Store」。  

8. **Pick 是否 persist：谁决定**  
   - 「引擎不定死」正确；须有**显式配置位**（节点 / 租户 / 动词默认），不能运行时猜测。  
   - 默认建议：**发送自选不落库**（与今日 ApproverPick 一致）；需要「选完可改、可审计」再开 persist。  

9. **fix.Load 与入参优先级「实现自定」**  
   - 灵活，但联调成本高。  
   - 建议 ext 默认实现选定一种并写死文档（推荐：**当次入参非空优先，并可回写 Store；入参空则读 Store；皆空则拒**）；宿主覆盖时必须打覆盖日志（类比 R9）。  

10. **Preselect Store 与现有 `IPreselectAssigneeStore`**  
    - 宜让 pre 的 Store/Load **直接演进/包住**现有 Store，避免第二张预选表。  

11. **动词代表类：演进现有按钮码表，勿平行再造**  
    - **现状**：`SailButtonSettingDto` / `SailButtonDef` 已是编码+启用+显示名雏形；缺 Mode/范围/排序/图标。  
    - **建议**：在宿主码表与 `sf:ButtonsSetting` 上**扩展字段**（或 versioned JSON），而不是另起 `VerbConfig` 第三套；引擎侧最多增加**只读描述契约**（如 `SailOperationCapability`），执行仍走 Lane/`FlowOperation`。  
    - **Mode 类型**：口述用 `int` 可以，实现更建议 **闭集 string/枚举**（与 `mode=` 属性一致），避免魔法数字；若必须 int，码表与文档同步。  
    - **排序号 vs 动作优先级**：先定义语义——排序=列表序，优先级=主次按钮/折叠；不要两字段同义重复。  
    - **Approve（通过）**：通常**不**需要本动词 Scope（下一跳人来自**目标节点** assigneeResolve）；代表类上 `needsAssignee=false` 或 Mode 空，避免每人点通过都配一套范围。  
    - **图标/主题**：属宿主 UX，可先只进 FE 码表；pure 不必依赖图标资源。  
    - **办理条**：扩展字段落地后，逐步让 `SailOperationBar` **读配置渲染**，替换硬编码 `type`，否则代表类只写不用。  

### 11.3 建议落地顺序（若立项）

```text
P0  Mode 属性旁挂（§6.5A）+ 存量推断；发送路径 Mode×Scope 跑通
P1  共享取人内核抽出；Transfer/加签/改派改为「调内核」而非只展平 map（先 Pick）
P2  范围内置/外置注册规范 + 宿主必注册清单
P3  Preselect：Load/Store 契约对齐现有 Store；回落策略显式化；默认实现放 ext
P4  Pick 可选 persist（配置位 + fix 侧 Store/LoadPicked）；判定层/设计器
P5  扩展 SailButton* 为动词代表（Mode/Scope/sort/icon/theme）；OperationBar 数据驱动
P6  再评估 AssigneeLoader<T>；抄送通道分离（R5）
P7  IStorage：先契约 + 1～2 张热点表试点（如 ProcessInstance 状态更新），再铺开（§12）
```

### 11.4 一句话建议

**对象解析器 + Mode 存储分层方向正确；动词侧应扩展现有按钮码表为「代表类」，挂上 Mode/范围与展示元数据，而不是另起炉灶。**  
引擎继续用 `FlowOperation`/`Lane` 执行；配置与 UX 在宿主描述符统一。Fixed 不存、Pick 可选存、Preselect 必存；Approve 与 Transfer 的取人来源要在代表类上区分清楚。

库访问演进见 **§12**：在 Manager 之下抽纯 `IStorage`，勿一次性重写全部 Manager。

## 12. 存储管理 · 数据库连接器 `IStorage`（整理）

> 本节超出「办理人」窄题，属引擎数据访问分层口述；与 §10.6（办理人 Mode 落库）不同维——此处是 **sf_* 流程定义/实例套表** 的通用库交互层。  
> 对照现行：`*Manager` 内直接 `kit.useRepo<T>()` + 业务规则混写；寿命见 [专题-对象生命周期与复用边界.md](../theme/专题-对象生命周期与复用边界.md)。

### 12.1 目标形态

```text
Lane / Runtime / 业务规则（可含逻辑）
        ↓
   *Manager（编排、校验、领域规则；可逐步变薄）
        ↓
   IStorage<T> / 专属热点 API（纯库交互）
        ↓
   mooSQL SQLBuilder（kit） / 连接
```

| 要点 | 约定 |
|------|------|
| **概念** | 数据库连接器 `IStorage`；流程定义、流程实例相关**每张表**对应 `IStorage<T>`（T=实体或该表行模型） |
| **定位** | **纯粹数据库交互层**：各类增删改查 + 查询 DTO；**不含任何业务逻辑** |
| **状态** | 连接器**无状态**；可作为应用级可共享实例（见 §12.5 寿命澄清） |
| **事务** | **`kit`（`SQLBuilder`）为第一参数**，支持事务传递；连接器自身不持有 kit/连接会话字段 |
| **热点路径** | 高频、性能敏感操作建**专属方法**（如流程状态更新）；**不**厚封装成「万能仓储」泛化行为 |
| **默认实现** | 放在 **ext**；可继承；通过注册替换 |
| **注册** | **每种库连接器仅唯一注册**；**后注册覆盖先注册**（与 Gate/Resolver 后写覆盖同风格） |
| **DI** | 引擎侧提供**仿 DI 契约**（注册表 / `UseXxx` / `ISailCollection` 一类）；**宿主用真 DI 实现并桥接注册** |

### 12.2 契约示意（非 API 定稿）

```csharp
// 示意：无状态；kit 首参
public interface IStorage<TEntity> // 或按表拆 IProcessInstanceStorage 等
{
    TEntity? GetById(SQLBuilder kit, string id);
    // 通用 CRUD / 列表 / 查询 DTO …
    string Insert(SQLBuilder kit, TEntity row);
    void Update(SQLBuilder kit, TEntity row);
    // …
}

// 热点专属：不要只靠通用 Update(entity)
public interface IProcessInstanceStorage : IStorage<ProcessInstanceEntity>
// 或独立接口，避免为泛化而泛化
{
    int UpdateState(SQLBuilder kit, string processInstanceId, int newState /*, 乐观版本? */);
    // 其它高频列更新…
}
```

```text
注册（仿 DI）
  services.UseStorage<IProcessInstanceStorage, DefaultProcessInstanceStorage>();
  // 或 client.useStorage(new MyProcessInstanceStorage());
  // 同键后注册 → 覆盖
宿主
  真 DI 解析实现 → Build 时写入 Sail 注册表（唯一槽）
```

### 12.3 与现行代码的差距

| 现行 | `IStorage` 目标 |
|------|-----------------|
| `TaskManager` / `ProcessManager` / `ActivityInstanceManager`… 内 `kit.useRepo` + **业务规则同文件** | 库语句下沉 Storage；规则留 Manager/Lane |
| `IPreselectAssigneeStore` 等零散 Store | 可视为 Storage 族特例；宜统一「kit 首参 + 无状态 + 可覆盖」口径 |
| `DefaultManagerFactory` 懒持有 Manager（A） | Storage 同为 A 档可替换依赖；Manager **依赖 Storage 接口**，不 `new` 具体库实现 |
| 宿主偶发直接 Repo | 业务应打 Manager；库细节只打 Storage |

### 12.4 专属方法 vs 厚仓储（红线）

**鼓励：**

- `UpdateProcessState(...)`、`MarkTaskCompleted(...)`、`BatchInsertTasks(...)` 等**语义清晰、可走索引/少列更新**的 API  
- 查询返回**专用 DTO / 投影**（待办列表、轨迹条），避免每次拉全实体  

**避免：**

- 只暴露 `Update(entity)` 却在热路径整行读写  
- 在 Storage 内写「若状态非法则抛业务异常并发 Hook」——那是 Manager/Lane  
- 为每张表复制一套无差别的泛型仓储却零专属方法（空对空封装）

### 12.5 寿命与「单例」（须与现规范对齐）

口述「app 级单例」与现行 **A · 同寿于一个 `SailClient`** 对齐时建议写成：

| 说法 | 建议口径 |
|------|----------|
| 无状态、可共享 | ✅ Storage **不持 kit/Runner**；同一 Client 内可单例持有 |
| 进程级上帝单例跨多个 `SailClient` | ❌ 与 [对象生命周期](../theme/专题-对象生命周期与复用边界.md)「禁止跨 Client 共享同一工厂/Manager」同风险——**默认按 Client/注册表槽**，除非宿主明确单 Client |

`kit` 永远是**调用入参（B）**，不是 Storage 字段。

### 12.6 仿 DI 与唯一注册

| 规则 | 说明 |
|------|------|
| 引擎不强制 Microsoft.Extensions.DI | 保持现有 `ISailCollection` / `SailClientBuilder` / `useXxx` **仿 DI** |
| 宿主真 DI | Host `AddSingleton/Scoped` 解析后，在 `UseSail*` 时 `useStorage` 注入 |
| **唯一注册** | 每一存储键（如 `typeof(IProcessInstanceStorage)` 或表名键）**仅一个实现槽**；后注册覆盖并建议打日志（类比 R9） |
| 禁止 | 同键多实现隐式聚合（Storage 不是 Filter 链） |

### 12.7 与 §10.6 办理人落库的关系

| | §10.6 Mode Store | §12 IStorage |
|--|------------------|--------------|
| 对象 | 预选/自选**办理人项集** | **流程套表**行数据 |
| 接口 | fix/pre 的 Load/Store | `IStorage<T>` / 专属更新 |
| 实现落点 | ext 默认 + 宿主可覆盖 | **同**：ext 默认 + 宿主可覆盖 |
| 关系 | pre/fix 的默认实现**内部应调用**对应 `IStorage`（或专用表 Storage），避免 Store 里手写第二套 SQL 风格 |

### 12.8 客观建议（本节）

**值得采纳**

1. **纯库层 + kit 首参 + 无状态**：与现行 A/B 寿命、事务传递完全同向，是对 Manager 膨胀的正确手术刀。  
2. **热点专属 API**：比「仓储教条」更贴工作流（状态机列更新频繁）。  
3. **ext 默认 + 唯一覆盖**：与 UseAssignees / UseManagerFactory 生态一致。  
4. **仿 DI / 真 DI 分工**：避免 pure 绑死 Host DI，同时让 ASP.NET 宿主好用。

**风险与收紧**

1. **迁移成本**：现 Manager 体量大，宜 **按表试点**（先 ProcessInstance 状态、Task 完成态），禁止大爆炸改写。  
2. **`IStorage<T>` 每表一个**：类型数量上升；可用「按聚合根少数接口」（Process / Activity / Task / Transition / Definition）减轻，不必机械一表一接口——**口述「每表」可落为「每表有主 Storage 入口」，实现允许聚合。**  
3. **业务逻辑泄漏**：Code Review 红线——Storage 文件出现 Gate/Hook/ReasonCode 业务分支即违规。  
4. **与 mooSQL `useRepo`**：Storage 实现内部仍用 mooSQL 即可；对外不把 `useRepo` 泄漏给 Lane。  
5. **逻辑删除**：若某套表有软删语义，删除 API 在 Storage 用 Update 标记还是物理删，须按表约定写清，勿 silently 混用。

**建议落地顺序**

```text
S0  定 IStorage 注册槽 + kit 首参约定 + 覆盖日志
S1  试点 IProcessInstanceStorage.UpdateState（或等价）+ 一处 Manager 改走接口
S2  Task / ActivityInstance 热点方法下沉
S3  预选/自选表 Storage 供 §10.6 pre/fix 默认实现复用
S4  再评估是否全面 IStorage<T> 铺开
```
