# 讨论 · 办理人「操作模式 × 人员范围」是否正交

> 状态：**讨论稿**（2026-11-26；同日补「模式外挂、Type=集合」收敛）  
> 用途：对照产品直觉「模式 × 范围正交」与现行 Assignee 管道，厘清**已对齐 / 未建模 / 可演进**边界；**不**改代码、不升格基线。

## 1. 一句话结论

**现状**：模式与范围折叠在同一 `assigneeResolve.type` 里，并非二维配置。  
**收敛方向（本稿倾向）**：现行 Type **一律视为人员集合（Scope）**；另挂几乎不扩展的三态 **Mode**（选人 / 固定 / 超前选）。对执行引擎，**固定与超前选都是「已有项集」**，只是来源不同；**选人**则要求参数必备人员。干扰面主要在设计器与判定层，不必重写各集合 Resolver。

## 2. 你的心理模型（本稿采纳为讨论坐标系）

### 2.1 操作模式（何时 / 如何定人）

| 模式 | 口语 | 含义 |
|------|------|------|
| **固定** | 无需选择 | 节点到达时按规则直接得到办理人全集，办理条不必再选 |
| **发送前选人** | 当次自选 | 发送（或发起）当次由操作者从候选中挑选，写入本次流转载荷 |
| **其它时刻预设置** | 预选 / 超前选人 | 在到达该节点之前的某一时刻已定好人（发起时、管理改表、上游节点写入预选仓等），到达时只读表派发 |

三者差在**定人时刻与是否人工介入**，不差在「人从哪一类集合来」。

### 2.2 人员范围（人从哪圈定）

按集合定义手段圈定候选或全集，例如：

| 范围手段 | 含义（示例） |
|----------|--------------|
| 固定用户列表 | 直接钉死若干账号 |
| 角色 / 群组 | 展开角色或群组成员 |
| 部门 / 单位 | 部门成员、单位映射、部门领导链 |
| 岗位 | 相对岗位、编制岗 |
| 流程相对 | 发起人、上一发送人等 |
| 表达式 / 业务回调 | 表单字段、宿主算法 |

### 2.3 正交命题

```text
操作模式 × 人员范围  →  可笛卡尔组合

例：范围 = 群组 G
  · 固定     → G 内全部人皆为办理人（无需再选）
  · 发送前选 → 发送人从 G 成员中挑选
  · 预选     → 更早时刻已从 G 成员中挑好，到达时读预选结果
```

**模式不改变范围定义；范围不强制某一种选人时机。**  
Leave（或签/会签/组/队长）仍是**第三维**，与上表无关。

## 3. 现行 sailflow 实际长什么样

### 3.1 已落地的正交轴（与本稿命题不同维）

权威基准见 [特性说明-待办人管道.md](../特性说明-待办人管道.md)：

| 轴 | BPMN / 契约 | 职责 |
|----|-------------|------|
| **Resolve** | `sf:assigneeResolve` | 时刻 A：创建待办前算出 `Performer[]` |
| **Leave** | `sf:leaveJudge` | 时刻 B：办完能否离开 |
| **后置** | Filter / EmptyAction（R10） | 同人、去重、空人拒绝/换人/锚点；**禁止**做成新 Resolve Type |

这是现行架构的硬正交；**不要**把「模式×范围」误写成与 Leave 抢同一套 ConfigPair。

### 3.2 Resolve Type：模式与范围被压进同一枚举

内置码见 `AssigneeResolveTypeCodes`（宿主另有 `deptBoss` 等）：

| Type | 更偏「范围」 | 更偏「模式/时机」 | 说明 |
|------|--------------|-------------------|------|
| `FixedUsers` | ✅ 固定用户 | （隐含固定派发） | Params `users[]` |
| `RoleGroup` | ✅ 角色/群组展开 | （隐含固定派发：展开后全员） | Params `roleIds` |
| `UnitMap` | ✅ 单位映射 | 固定派发 | |
| `JobRelative` | ✅ 岗位 | 固定派发 | |
| `ProcessRelative` | ✅ 流程相对人 | 固定派发 | |
| `Expression` / `BusinessCallback` | ✅ 动态范围 | 固定派发（算完即派） | |
| `StarterPick` | （范围不在 Type 内） | ✅ 发起时当次自选 | 只吃当次 `NextActivityPerformers` |
| `ApproverPick` | （范围不在 Type 内） | ✅ 发送人当次自选；**R6 出厂默认** | 同上实现路径 |
| `Specific` | — | ✅ F1 透传 | 调用方已传入 |
| `Preselect` | （范围不在 Type 内） | ✅ 实例级预选表 | 须宿主 `UsePreselectAssignees` |
| `Fallback` | 组合器 | — | 主策略空后再 Resolve 另一 Type |

文档 §6.1「第一维坐标系」已按**绝对钉死 / 组织人力 / 运行时补全…**分类，但实现上仍是**互斥单选 Type**，不是两字段相乘。

### 3.3 与口语模式的对照

| 你的模式 | 现行落点 | 是否独立配置轴 |
|----------|----------|----------------|
| 固定（无需选择） | `FixedUsers` / `RoleGroup` / `UnitMap` / `JobRelative` / `deptBoss` / … | ❌ 每种范围一个 Type；「固定」是这些 Type 的隐含行为 |
| 发送前选人 | `ApproverPick`（及 `StarterPick`） | ❌ 选 Type=`ApproverPick`；候选范围另靠角色预览 / 选人器 / 宿主 |
| 其它时刻预设置 | `Preselect` + `IPreselectAssigneeStore`；另有 AI `ai_nxt_perf` 网关短缓存（非通用预选仓） | ❌ 另选 Type=`Preselect`，与 RoleGroup **不能**同节点双 Type |

### 3.4 设计器侧的「弱正交」

宿主面板（`SailNodeConfigPanel`）常见三块：

1. **待办人·定范围** → `assigneeResolve` Type + Params  
2. **运行时·选人器** → `candidateSelectorType`（`HostUserSearch` / `InlineList` / `RoleUserSearch`）— 注释写明**与 AssigneeResolve 正交**  
3. **办理模式** → `leaveJudge`

选人器解决的是：**当 Type 需要人机挑选时，UI 怎么搜人**；它**不**写入引擎 Resolve 管道，也**不能**把「ApproverPick + RoleGroup」声明成引擎可校验的契约。

宿主下一跳预览（如 `SleveenUserIdentity`）常靠节点角色展开人数推导 `CandidateMode`（bound / search / anyselect）——范围在**产品侧旁路**，不在标准 Resolve Params 契约里与 Pick 成对。

## 4. 直接回答：当前是如此吗？

| 命题 | 判定 | 说明 |
|------|------|------|
| 模式 × 范围在概念上正交 | **同意（产品直觉）** | 固定/选人/预选与集合定义手段本可独立组合 |
| 现行引擎已按二维配置实现 | **否** | 单字段 `assigneeResolve.type`；组合靠换 Type 或宿主 UX |
| 固定群组 = RoleGroup 全员派发 | **基本是** | `RoleGroup` ≈「范围=角色 + 模式=固定」的打包 |
| 发送前从群组内选 = ApproverPick + 群组范围 | **产品上常能凑** | 靠选人器 / 角色候选；**BPMN 无标准「范围」字段与 Pick 绑定** |
| 预选从群组内提前挑 = Preselect + 群组范围 | **部分是** | Preselect 只管「从表取人」；写入预选表时的候选范围是宿主面板职责 |
| Resolve × Leave 正交 | **是（已定型）** | 勿与模式×范围混为一谈 |
| 空人/同人/去重是第四种「模式」 | **否（R10）** | 后置策略，禁止注册成 Resolve Type |

**一句话给产品：**  
正交坐标系正确；今日是 Type 打包。**下一步不必重做集合算人**——把 Type 当成 Scope，外挂闭集 Mode 即可（见 §6）。

## 6. 收敛方案 · Mode 外挂、Type=集合（倾向）

> **未立项**；与 R2 单轨、R4 禁暗默认、R6 设计默认、R10 后置三分兼容。  
> 相对旧稿选项 A/B/C：本稿**采纳「Mode 外挂」**——不重写集合 Resolver，也不再发明 ScopedPick 组合 Type。

### 6.1 核心命题

1. **现行所有 Resolve Type，均可视为人员集合 Type（Scope）**——负责「圈出一集人 / 定义候选宇宙」。  
2. **Mode 几乎固定，不需扩展注册表**：仅三态。  
3. 增量落在 **设计器 + 判定层**；集合 Resolver 实现尽量不动。  
4. **执行引擎视角**：固定与超前选都是「已有项集 → 派发」；选人则「参数必备人员，否则拒」。

### 6.2 Mode 三态（闭集）

| Mode | 口语 | 执行引擎语义 | 项集来源 |
|------|------|--------------|----------|
| **Fixed** | 固定 | 已有项集，直接派发 | 对 Scope Type 做 Resolve（展开角色/映射/…） |
| **Preselect** | 超前选 | **同 Fixed：已有项集，直接派发** | 预选仓 / 实例表（按 PI+ActivityId）；Scope 只管写入期候选与校验 |
| **Pick** | 选人 | **参数必备人员**；空则 R4 拒绝 | 当次 `NextActivityPerformers`（发起或发送写入）；Scope 定义候选宇宙与越权校验 |

```text
时刻 A（示意）
  mode = Pick
    → 读 NextActivityPerformers；空 → AssigneeEmpty / 缺参
    → （可选）校验 ⊆ Scope.Expand(…)
  mode = Fixed | Preselect
    → 取项集（Fixed←Scope.Resolve；Preselect←Store）
    → 空 → EmptyAction / R4（与今同）
  → Filter 链 → 建待办
```

**关键简化**：引擎不必为 Preselect 另搞一套「派发算法」——与 Fixed 同为「项集已定」；差别只在**读哪里**。Pick 是唯一要求「调用方已带人」的模式。

### 6.3 Type 重归类（集合 vs 历史模式码）

| 现行 Type | 收敛后角色 | 备注 |
|-----------|------------|------|
| `FixedUsers` / `RoleGroup` / `UnitMap` / `JobRelative` / `ProcessRelative` / `Expression` / `BusinessCallback` / `deptBoss` / `Business.*` | **纯 Scope** | Mode=Fixed 时 = 今日行为；Mode=Pick/Preselect 时 = 候选宇宙 |
| `ApproverPick` / `StarterPick` | **废弃为 Mode，不再作 Type** | 映射：Mode=Pick；谁在选（发起/发送）可由子字段或办理语境区分，不必两个 Scope |
| `Preselect` | **废弃为 Mode，不再作 Type** | Mode=Preselect；Store 仍要，但不占 Type 槽 |
| `Specific` | **Mode=Pick 的载荷通道** 或保留为透传 Scope | F1「传入即派」≈ Pick 且已带人；可不再单独暴露给设计器 |
| `Fallback` | **仍属集合/策略组合器** | 与 Mode 正交；或仅挂在 Scope 链上 |

存量 BPMN：无 Mode 属性时，**推断**——

| 旧 Type | 推断 Mode | 推断 Scope |
|---------|-----------|------------|
| RoleGroup / FixedUsers / … | Fixed | 自身 |
| ApproverPick / StarterPick | Pick | 缺省空集合或节点 Roles→RoleGroup |
| Preselect | Preselect | 同上（候选来自设计期另配 Scope，若无则任意/宿主默认） |

### 6.4 落层：谁改、谁几乎不改

| 层 | 做什么 |
|----|--------|
| **设计器** | 先选 Mode（三态），再选 Scope Type + Params；选人器仅在 Mode=Pick（及 Preselect **写入** UX）出现 |
| **判定层**（发布校验 / ProbeNext / 办理条） | Mode=Pick → 未选人不可发；Mode=Fixed/Preselect → 可免选手动；Preselect 未写入 → 设计/发起期拦截 |
| **执行管道** | 薄分支：按 Mode 取项集来源，再共用 Filter/EmptyAction；**各 Scope Resolver 不改签名** |
| **Leave / R10** | 不动 |

干扰面评估：**小**——不动 Leave、不改集合算人公式、不增 Mode 注册表；主要是 BPMN 多一个属性（或 Params.`mode`）+ 设计器/判定 + 存量推断。

### 6.5 存储形态（二选一，待拍）

**A. 属性旁挂（推荐讨论）**

```xml
<sf:assigneeResolve type="RoleGroup" mode="Pick"
  params='{"roleIds":["R_MGR"]}' />
```

- `type` = Scope（与今 Resolver 注册键一致）  
- `mode` = Fixed | Pick | Preselect（闭集，**禁止**当扩展 Type）

**B. 仅 Params**

```json
{ "mode": "Pick", "roleIds": ["R_MGR"] }
```

- 少改 Convertor；Mode 易被业务 Params 污染；发布校验须强制读 `mode`。

### 6.6 与旧选项关系

| 旧选项 | 关系 |
|--------|------|
| A Params 约定 | 被 §6.5B 吸收；但 Type 仍混模式码时不够干净 |
| B 两字段 | **接近本稿**；本稿进一步规定引擎 Fixed≡Preselect（来源不同）且 Mode 闭集不扩展 |
| C 组合器 Type | **不采用**——避免再增 ScopedPick |

### 6.7 仍待拍板（收窄后）

1. **Pick 子类**：发起选 vs 发送选 —— 一个 Mode + `pickWhen=Start|Approve`，还是办理语境隐式？  
2. **越权**：Pick/Preselect 写入是否引擎强制 `⊆ Scope.Expand`？  
3. **Mode 缺省**：对齐 R6——新节点默认 `mode=Pick` + Scope 可空（任意选）或 Scope=RoleGroup？  
4. **Preselect 无 Store**：Mode=Preselect 但未挂 Store → 硬失败（与今一致）还是回落 Fixed？建议硬失败。  
5. 落地后回写管道 §6，本稿进 `done/`。

## 7. 易混清单（讨论时先对齐用词）

| 勿混 | 说明 |
|------|------|
| 操作模式 ≠ Leave 办理模式 | 前者何时定人；后者几人办完能走 |
| 操作模式 ≠ NodePolicy 空人/同人 | 后者是 R10 后置 |
| Fixed 与 Preselect（引擎） | **同为已有项集**；差别只在来源（Scope.Resolve vs Store） |
| Pick ≠ 选人器控件 | Pick 是 Mode；选人器是 UX |
| 旧 `StarterPick`/`ApproverPick`/`Preselect` Type | 收敛后是 **Mode**，不是 Scope |
| `RoleGroup` 的 Group ≠ R1 办理分组 GroupId | 角色展开 vs 会签组身份 |
| `ai_nxt_perf` ≠ Preselect 仓 | 网关短缓存 vs 实例预选表 |
| Fallback ≠ 空人 EmptyAction | 再算人 vs 处置空集 |
