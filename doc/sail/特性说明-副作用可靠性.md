# 特性说明 · 副作用可靠性（Outbox / Channel / 对账）

> 状态：**论证已拍板**（2026-11-05）；**Reliable/Outbox + InProcessThrottle 已落地**；**BestEffort Channel 骨架已落地**（`sailflow.msg.SideEffect`）  

> 目的：按「丢失代价」给 Gate/Hook/Notifier 之外的**旁路副作用**定可靠性档位，明确 Channel 与 Outbox 的分工，避免「一律 Outbox」或「一律内存队列」两极化。  
> 关联：[特性设计-回调与事件.md](./特性设计-回调与事件.md) · [草案-引擎异步化.md](./草案-引擎异步化.md) · [最佳实践-宿主能力包UseXxx.md](./最佳实践-宿主能力包UseXxx.md)  
> 现行实现：`HookOutboxDrainLoop` / `NotifyThrottleOptions` / `NotifierThrottleHub`（引擎）；`ReliableTaskNotifierBase` / `BestEffortFlowHookBase`（msg）；admin：`PortalScheduleTaskNotifier`（含 Throttle）、`FlowEventFileLogHook`

---

## 1. 一句话

**Outbox = 持久账本（可补调）；Channel = 进程内调度阀门（削峰限流）。**  
二者可叠加，不可互相替代。业务宿主还可把「库表真相 + 对账补推」当作一等可靠性手段——**不丢消息不必只押在 Outbox 上**。

---

## 2. 问题从哪来

典型场景：流程后台**批量结束**超时未办结实例（如 1000 条），每实例约 10 个待办人 → 触发 **1500～8000** 次「消除待办 / 推送」外部调用。若在管理 API 请求栈内同步打接口，或消费侧无上限狂打，会导致：

- 管理端请求超时 / 页面假死；
- 连接池、出口带宽、下游待办中心被打满；
- 进程内若仅用无界队列扛突发，又与「崩溃是否可丢」纠缠不清。

需要把「生产（登记要做什么）」与「消费（真正调外部）」拆开，并按副作用类型选择**可靠性档位**。

---

## 3. 现行唤起路径（Reliable / Outbox，已落地）

Notifier / Async Hook **默认不**在主路径调外部系统：

```text
待办生命周期（创建/完成/取消/…）
  → FireTaskLifecycle
      → Sync Hook（当场，同事务）
      → EnqueueAsyncHooks / EnqueueTaskNotifiers
         → 同库同事务 INSERT wf_hook_outbox (Pending)
  → 提交后返回 WfExecutedResult

后台 UseHookOutboxDrain(autoStart) / HookOutboxDrainLoop
  loop:
    ProcessPendingAsync
      → ReclaimStaleProcessing
      → TryClaimPending（Pending → Processing + lease）
      → DispatchClaimedOutboxAsync → NotifyAsync / Handle
      → MarkSucceeded / MarkFailed / Dead
    Task.Delay(PollInterval)   // 默认约 5s；无 Channel 唤醒
```

要点：

| 环节 | 行为 |
|------|------|
| 入队 | 与流转**同库同事务**写 Outbox，避免「流程回滚了还推送」 |
| 唤起 | **定时轮询**认领，非提交后 push |
| 并发 | CAS + lease；僵尸 Processing 可回收 |
| 失败 | 退避重试 → Dead；运维可复活 |

[特性设计-回调与事件.md](./特性设计-回调与事件.md) §5.3 曾写：Worker 未就绪时可用「内存 Channel + 进程内消费」作**退化**，并标明进程崩溃会丢、**不得标为生产默认**。Phase 2/3 已落地的是 DB Outbox + Drain，不是 Channel。

命名辨析：`TaskNotifyChannelBase` = 推送**通道**模板方法；本文件「Channel」特指 `System.Threading.Channels` 进程内队列。

## 4. 可靠性分档（拍板）

按**丢失代价**与**兜底手段**分三档，注册/实现时显式选档，禁止混称「异步」而不加定语（与引擎异步化草案的 Outbox vs IO 维正交）。

| 档 | 代号 | 典型副作用 | 丢了怎样 | 推荐骨架 | 现行状态 |
|----|------|------------|----------|----------|----------|
| **可丢** | `BestEffort` | 日志、效能埋点、非关键审计 | 最多少几条统计 | 有界 **Channel** + 单消费者串行（`BestEffortFlowHookBase`） | **骨架已落地**（msg）；admin：`UseFlowEventFileLog` |
| **可晚、靠对账** | `Reconcile` | 待办消除、IM 提醒（有推送记录表） | 短暂不一致；对账 Job 补 | **Channel 削峰** + 业务库/推送记录；Outbox **可选** | 宿主常见历史模型 |
| **强补调** | `Reliable` | 待办中心推送、须崩溃可续跑 | 不能静默丢 | **同库 Outbox** + Drain；`ReliableTaskNotifierBase` | **已落地**；admin：`UsePortalScheduleTaskNotifier` |

### 4.1 历史宿主模型（Reconcile）仍然有效

许多业务系统**并不**把「不丢推送」押在 Outbox 上，而是：

```text
真相在业务库（待办人 / 办理记录）
  → 推送是尽量做好的旁路
  → 推送结果另表落库
  → 定时核对：该消未消 / 该推未推 → 补调或告警
```

在此模型下：进程内 Channel 队列因回收丢掉若干条，最多变成「晚一点被对账扫出补推」，**不一定是事故**。  
引擎默认 AsyncOutbox，是给**没有对账能力**的宿主的开箱保险，**不否定**「库真相 + 对账」一等公民地位。

### 4.2 与主路径强一致的不要进旁路

须与办结/推进**同事务**的状态回写 → **Sync Hook（FailFast）** 或主路径写库；**不要**只丢进 Channel / Outbox 当唯一保障。

## 5. Channel 的定位

### 5.1 它是什么

`System.Threading.Channels`：**轻量进程内**队列（有界背压、多生产者/多消费者友好）。适合「抗突发 → 按节奏调度消费者」。

### 5.2 适合 / 不适合

| 适合 | 不适合 |
|------|--------|
| 进程内缓冲、限流、控并发 | 跨进程共享；崩溃后仍须续跑的**唯一**真相源 |
| Outbox **认领之后**的执行调度 | 主路径「写入 Channel 即成功」却让 Outbox 立刻 `Succeeded` |
| `BestEffort` / `Reconcile` 档的生产—消费骨架 | 单独替代 `wf_hook_outbox` 冒充 Reliable |

### 5.3 禁止的「双异步」

```text
❌ NotifyAsync 内 Channel.Writer.TryWrite(ctx); return;
   → Outbox 已 MarkSucceeded
   → 后台再慢慢调待办中心
   → 进程一挂 → 外部待办幽灵，且 Outbox 认为已成功
```

正确叠法（Reliable + 限流）：

```text
✅ 办结 → Outbox INSERT → Drain 认领
     → 有界 Channel / 信号量限流
     → 真正执行 NotifyAsync / SendCoreAsync
     → 成功后再 MarkSucceeded
```

**账本（Outbox）与调度（Channel）职责分离**：Channel 只阀门，不提前结案。

## 6. 产品形态

业务只写「怎么调待办中心」；框架管 Outbox 与进程内限流。

### 6.1 Reliable Notifier + InProcessThrottle（已落地）

```csharp
builder.AddNotifier(new TodoCenterNotifier(), o =>
{
    o.TaskKinds = new[] { TaskNotifyKind.Cancelled, TaskNotifyKind.Created, TaskNotifyKind.Completed };
    o.Mode = HookMode.AsyncOutbox; // 默认；持久轨
    o.InProcessThrottle = new NotifyThrottleOptions
    {
        Capacity = 2000,                           // 有界 Channel；满则 Drain 背压等待（不丢行）
        MaxDegree = 2,                             // 同时打待办中心的路数
        MinInterval = TimeSpan.FromMilliseconds(50), // 同车道两次开始执行的最小间隔
    };
});
// 另需 UseHookOutboxDrain(...)
```

实现要点：

- 选项挂在 `HookRegistrationOptions.InProcessThrottle` → `NotifierRegistration`。
- Drain 认领后：有 throttle 的 Notify 行**并行** `WriteAsync` 入 `NotifierThrottleHub` 车道；`MaxDegree` 个 worker 调 `NotifyAsync`；**返回后**才 `MarkSucceeded` / `MarkFailed`。
- `Capacity` 满时写入阻塞（背压），**不**丢 Outbox 行。
- 未配置 `InProcessThrottle` 时行为与原先一致（串行直调）。

BestEffort 仍用 `BestEffortFlowHookBase`（可丢）；`Delivery` 枚举一等公民可后续再收。

业务实现保持不变：

```csharp
protected override Task SendCoreAsync(TaskNotifyContext ctx, CancellationToken ct)
    => todoClient.DismissAsync(ctx.TaskId, ctx.AssignedUserId, ct);
```

### 6.2 批量管理操作（与投递正交）

无论哪一档，**管理 API 请求线程**都不应同步打几千次外部接口：

1. **分片办结**（如每批 20～50 实例）→ 快速返回受理/进度；
2. 每取消一条待办 → 只**入队**（Outbox 或 Channel，视档位）；
3. Worker / Drain / Channel 消费者按 `MaxDegree` / 间隔慢慢打；
4. `Reconcile` 档依赖现有「推送记录 ↔ 待办人表」核对补漏。

卡死排查分层：

| 层 | 现象 | 处置 |
|----|------|------|
| A. 管理栈同步打外部 | 请求挂死 | 立刻改为只入队 |
| B. 单次请求巨型写库 | 事务长、超时 | 分片 Job |
| C. Drain/消费者爆冲 | 管理能回但进程打满 | 降 `BatchSize` / `MaxDegree`，加 Throttle |

## 8. 决策摘要

| # | 决策 |
|---|------|
| D1 | Outbox 与 Channel **叠加不替代**：Outbox 账本，Channel 调度。 |
| D2 | 副作用按丢失代价分 **BestEffort / Reconcile / Reliable** 三档；宿主可选用对账代替 Outbox。 |
| D3 | 引擎 Notifier **默认 ReliableOutbox**；`InProcessThrottle` **已落地**；BestEffort 用 `BestEffortFlowHookBase`。 |
| D4 | 禁止 Outbox `Succeeded` 早于真实外部调用完成（禁止 NotifyAsync 只入 Channel 即返回成功）。 |
| D5 | 批量运维：分片入队 + 限流消费；管理请求禁止同步风暴式推送。 |
| D6 | `TaskNotifyChannelBase` 名称保留「推送通道」语义；文档中进程内队列一律写清 `System.Threading.Channels`。 |

- BestEffort Hook **必须** `Mode=Sync`（`Handle` 只 `TryWrite`）；写文件等在 `ConsumeAsync` **串行**执行。

## 11. 总结

- **不丢**可以来自：Outbox、或业务库真相 + 对账，不必神化单一机制。
- **不卡死**靠：主路径只入队 + 消费限流；Channel 在此非常合适且轻量。
- **Reliable** = Outbox + `ReliableTaskNotifierBase`；**BestEffort** = `BestEffortFlowHookBase`（Channel 串行）；业务只写消费逻辑。
